# Caddie配置ワークフロー

## 目的

プロジェクトごとに、Keep the Ashibaを継続する1つの固定Caddie窓口を置く。
Caddieは個別プロジェクト付きStewardの内部呼称であり、同じ役割を重複配置しない。

この手順は配置と足場の接続を扱う。プロダクト、創作、研究、仕様の採否は扱わない。共通境界は`stewardship_rules.md`を参照する。

## 新規立ち上げと既存プロジェクトの受け入れ

Butlerは一つの受け入れ依頼として配置、担当への引き渡し、登録、結果回収を追う。ただし、一つの依頼を全操作への包括承認とせず、既存の許可境界を使う。

- 既存プロジェクトでは、作業場所、履歴、担当、入口、同等のCaddieを確認して再利用する。受け入れのためだけに作り直さない。
- 新規で作業場所、担当、入口がまだない場合は、Butlerが必要な判断と担当を整理し、許可された作成作業をプロジェクト担当へ渡す。未成立の入口や正本は接続待ちとして残し、用意できたところから以下の配置手順へ合流する。設計相談中の担当へ、未決の構成を確定させたり同じ質問を利用者へ繰り返したりしない。
- プロジェクト固有の`AGENTS.md`や専用Skillは一律に作らず、必要性と内容の設計をプロジェクト担当へ任せる。Butlerはその設計を代行せず、入口から必要な手順・記録へ辿れることと結果回収を引き受ける。担当側が既存の共通資産の管理者へ相談するかを、この手順で義務化も禁止もしない。

Caddieの設置完了と、依頼された立ち上げ全体の完了は分ける。設置条件を満たしても担当側の準備やGit方針確認が残れば、元の受け入れ依頼に残件、担当、戻る条件を保つ。Git管理の実施分担は以下の手順7を使い、重複する手順を作らない。

## 設置済みの条件

次の3点が確認できた時だけ、Caddieを`設置済み`とする。

1. Butlerの非公開対象一覧に、project識別子と固定Caddieの確認先が登録されている。
2. projectの既存入口から、Caddieの役割、trigger、許可境界、project-localな記録先へ辿れる。
3. Caddieが読んでよい範囲をOwnerが承認している。

固定taskや固定チャットの存在だけでは、設置済みにしない。

## 入力

- project名とproject root。
- Ownerまたは判断確認先。
- Butlerの非公開対象一覧。
- 既存のproject入口候補。例: `README.md`、`PROJECT.md`、`AGENTS.md`、governance文書。
- 既存Caddieまたは同等なSteward窓口の確認先。
- 承認済みread範囲。未承認なら、最小案を作る。
- 共通Skillの正本と、Butlerが確認した版。
- Caddieが正本を直接読めるか、実行環境から本文を確認できるか、今回の短い作業契約が必要か。

## 配置手順

### 1. 同一性と重複を確認する

- project名だけでなく、root、既存locator、Ownerの説明から同一性を確認する。
- 同等なSteward窓口または固定Stewardタスクがあれば、同じCaddie候補として扱う。
- 既存Caddieを再利用できる場合は、新しいtaskやチャットを作らない。
- 1つのlocatorが複数projectを含む箱なら、無理に1つのCaddieへまとめない。

同一性が決められない場合は、候補と根拠を示し、Owner判断を1件だけ求める。

### 2. 最小限の足場を浅く確認する

承認済み範囲内で、次だけをread-onlyで確認する。

- project rootの存在と、入口になりそうなファイル名。
- `.git`の有無。Git管理済みならbranch、浅いstatus、最新commit。
- 入口から辿れる現在地、正本、判断記録、引き継ぎ先。
- Caddieの役割、trigger、許可境界、記録先が既にあるか。

深い本文レビュー、秘密情報、他project、親フォルダの横断scanは行わない。

### 3. read範囲を閉じる

既存承認がなければ、projectに合わせた最小案を出す。標準案は次のとおり。

- project rootのGit状態と履歴。
- projectが採用した入口文書、状態文書、`docs/`。
- それらから明示的にリンクされたproject-localな資料。

標準除外は`.env`、資格情報、秘密情報、無関係な個人情報、他projectとする。追加範囲は別途承認を取る。

### 4. 1つの固定Caddie窓口を接続する

- 既存の論理的なCaddie窓口があれば再利用する。
- runtimeが固定taskや固定チャットを支える場合は、必要性と初期文面を提案し、明示承認後にだけ作成する。
- 推奨表示名は`Caddie｜<project名>｜Ashiba管理`とする。
- 対応していれば固定またはpinする。
- 個別の制作、調査、実装taskにはCaddieを増設しない。重要な状態変化、判断待ち、区切りだけを同じ固定Caddieへ渡す。
- eventを受け取っただけで個別作業へ即時に割り込まず、固定Caddieが `即時対応`、`次の区切り`、`follow-up` を判定する。
- 非緊急の足場ToDoは固定Caddieで保持し、本作業の自然な区切りを待つ。Owner承認済みで、許可範囲と作業ファイルが競合しない場合だけ、固定Caddieの別レーンで扱う。
- 続行により被害が広がるため割り込む場合は、元の目的、作業中のファイル、未完了地点、再開時の最初の一手を残し、対応後に元作業へ戻す。
- timing-driven automationは配置と分け、必要性、頻度、費用を示して別途承認を取る。

固定task、チャット、Skill、人間の手順は交換可能なruntime adapterである。会話履歴をprojectの正本にしない。

### 4.1 共通Skillへの接続を確認する

固定Caddieがあることと、現行Skillを読めることを同一視しない。依頼を渡す前に、次のいずれかを確認する。

- `正本を直接確認済み`: 承認済みread範囲に正本Skillが含まれ、Caddieが本文と期待版の一致を確認した。
- `実行環境から確認済み`: 実行環境がSkill本文を提供し、Caddieが本文と版の対応を確認した。
- `今回の短い作業契約`: 直接読めないため、Butlerが今回の目的、対象、read範囲、必要な手順、禁止事項、返却内容、返却先を依頼内で渡した。共通Skill全体を参照済みとは扱わない。
- `接続不足`: Skill名または版だけ、本文を読めない、短い作業契約も不足、または版不一致。許可範囲外を探索せずButlerへ戻す。

既存Caddieは作り直さない。同じ固定窓口へ`templates/caddie_setup.md`の接続更新文を一度送り、以後の依頼にも接続情報を添える。反映状況は新しい台帳ではなく、既存の非公開対象一覧のCaddie欄とevent受領記録へ浅く残す。全projectへの更新は横断事項として一巡し、重複依頼を出さない。

### 5. project入口を接続する

projectの文化に合う既存入口を使う。READMEを一律に必須化しない。

入口から、少なくとも次へ辿れるようにする。

- Caddieの役割: KTA、状態把握、受け渡し、足場ToDo、follow-up。
- trigger: manual、event-driven、必要なら承認済みtiming-driven。
- 許可境界: read範囲、変更承認、専門判断をしないこと。
- project-localな正本: 現在地、判断、引き継ぎ、次の確認を残す場所。

入口変更が必要なら、対象ファイルと最小差分を提案し、許可後にproject担当側で反映する。

### 6. Butlerの非公開対象一覧へ登録する

深いproject情報を複製せず、次だけを浅く登録する。

- project識別子とlocator。
- 固定Caddieの確認先。
- 導入状態と承認済みread範囲。
- project-localな根拠への導線。
- オーナー付きStewardによる受領確認、プロジェクト内の正本への反映確認、判断待ち、次回確認。
- Git状態。未管理なら`足場未整備: Git管理方針確認`。

公開テンプレートや公開repositoryへ、個人path、task ID、非公開project名を混ぜない。

### 7. Git足場を分岐する

`.git`がない場合も無視しない。入口やdocsからproject実体が確認できるなら、次の状態で残す。

`足場未整備: Git管理方針確認`

Caddieは`git init`、初回commit、remote設定を実行しない。次を順に行う。

1. Git管理を始める具体案をOwnerへ提示する。
2. 承認後、project担当側または作業エージェントへ実行を渡す。
3. Caddieが結果、初回commitの範囲、Git状態、古くなった状態文書をread-onlyで確認する。
4. project-localな正本とButler一覧を反映し、`Git管理済み`、`意図的に非Git管理`、`対象外`、理由付き`保留`のいずれかへ閉じる。

remote設定は別判断とし、自動で行わない。stageは対象ファイルを明示し、`git add .`を使わない。

### 8. eventを受領し、設置を閉じる

配置やGit初期化の実作業後は、固定Caddieへevent-drivenで結果を渡す。Caddieは次を確認する。

- project-localな状態文書が現状と一致するか。
- 重要な判断や変更がcanonical branchから到達できるcommitにあるか。
- オーナー付きStewardによる受領確認と、プロジェクト内の正本への反映確認が閉じたか。
- 残る判断待ちと次回確認が明確か。

3つの設置条件とGit状態を確認してから完了報告する。

## Owner確認の出し方

- 一度に1件だけ尋ねる。
- 「何を決めてほしいか」「Stewardの推奨」「許可後に誰が何をするか」を短く示す。
- 配置の標準手順で判断不要な項目を、Ownerの大量ToDoに戻さない。

例:

`Stewardからのご提案: <project名>のCaddie read範囲は、Git状態、<入口文書>、<状態文書>、docsと、そこから明示リンクされたproject-local資料までにしてよいですか？`

`判断いただきたいこと: <project名>はproject実体がありますがGit未管理です。project担当側でGit管理を開始し、Caddieが結果を確認する方針にしてよいですか？`

## 完了報告

- 固定Caddieの確認先。
- project-localな正本と入口。
- 承認済みread範囲と除外範囲。
- 共通Skillへの接続状態と、Caddie自身が確認できた範囲。
- Butler対象一覧への登録結果。
- Git状態とfollow-up状態。
- 残るOwner判断があれば1件。なければ`なし`。
