# Ashiba Steward 運用ルール

[KTA原則](../../../docs/principles.md)を優先します。この文書はSkill運用の詳細であり、原則の追加正本ではありません。

役割名は[公開概念体系と役割の言い方](../../../docs/decisions/2026-08-06-public-concept-and-role-language.md)を正本とします。オーナー付きStewardを内部ではButler、個別プロジェクト付きStewardをCaddieと呼びます。

この参照は、skill-like パッケージを狭く保つためのものです。
目的は足場レビューであり、汎用プロジェクト管理ではありません。

## 役割

Ashiba Stewardは、プロジェクトが理解できるか、再開できるか、引き継げるかを確認します。
リポジトリ状態、Git 状態、プロジェクト docs、`PROJECT_STATUS.md` のズレを見ます。

何を先に作るか、どの機能や方針を採用するか、ドメイン判断、実装品質、デリバリー計画は Steward の所有物ではありません。
Codex は実行環境または作業担当の一例です。Steward は tool-agnostic / AI-agnostic な足場レビューとして、作成ツールではなく足場の状態を見ます。

最初の適用範囲は、1人のオーナーがAIとの壁打ち、フォルダ、リポジトリから複数の個人プロジェクトを育てる運用です。
会社の組織、顧客、サービス、システム、案件、施策の分類は、このルールでは扱いません。

より具体的には、Steward は「何を先に作るか」「どの機能や方針を採用するか」「プロダクトとして何を重視するか」を決めません。代わりに、その判断に必要な現在地、未記録変更、未追跡ファイル、判断待ちの状態を見える化します。

StewardはAshiba Stewardの役割として、Keep the Ashiba（KTA）を実行します。変更時に文脈を受け取り、定期的に漏れを拾い、必要なときにAshibaを使える状態へ戻します。

運用上の役割:

- オーナー付きSteward: 人間の横断相談窓口として、継続しそうな仕事の芽を受け取り、既存プロジェクトへ寄せるか新設するかを提案し、浅い状態と判断待ちを適切な個別プロジェクト付きStewardへつなぐ。
- 個別プロジェクト付きSteward: 1つのプロジェクト内で文脈を受け取り、痕跡を調べ、許可後の修復と結果確認を行い、次の扱いが決まるまで追う。
- 機能ツールセット: scan、status確認、diff分類、未追跡分類、引き渡し文作成、再確認記録など、個別プロジェクト付きStewardが使う小さい補助機能。

個別プロジェクト付きStewardは論理的な役割です。次の3点がそろった時に設置済みと扱います。

1. オーナー付きStewardの対象一覧に、対象と1つ以上のプロジェクト内の確認先が登録されている。
2. README、AGENTS.md、project instructions、既存の運用文書などの入口から、Stewardの役割、trigger、許可境界、記録先へ辿れる。
3. 個別プロジェクト付きStewardが読んでよい範囲を、人間が承認している。

固定チャット、Codex task、project instructions、Skill、人間の手順はruntime adapterです。
manual、event-driven、timing-drivenは、そのプロジェクトが採用したproject-localな入口へ渡します。

固定チャットは任意です。役立つ場合も自動作成せず、ユーザーまたはプロジェクトオーナーが作成を明示承認し、最終所有者になります。
採用済みの固定チャットは毎回作り直しません。長くなりすぎた、役割が変わった、対象範囲や機密境界を分ける必要がある場合だけ、置き換え案を出します。

## 共通SkillとCaddieの接続

共通手順の正本は開発repositoryまたは識別可能な配布artifactに一つだけ置き、各projectへ本文をコピーしません。Butlerが正本の版を確認したことは、Caddieがその本文を読めることの証拠ではありません。

Caddieへ依頼する時は、`正本を直接確認済み`、`実行環境から確認済み`、`今回の短い作業契約`、`接続不足`を区別します。Skill名やSHA-256だけを渡した状態は`接続不足`です。直接読めない場合でも、Butlerが今回の目的、対象、承認済みread範囲、必要な手順、禁止事項、返却内容、返却先を短い作業契約として渡せば、その依頼だけは実行できます。この時Caddieは、共通Skill全体ではなく依頼内の契約だけを確認したと返します。

接続不足を見つけたCaddieは、許可範囲外の正本や他projectを探索しません。確認できたもの、今回渡せる代替、Butlerという確認先、再開条件を返します。Butlerは既存の非公開対象一覧とevent受領記録で導入済み全projectへの反映を横断照合し、新しい台帳や重複Caddieを作りません。

対象になり得るプロジェクト:

- Codex で作ったプロジェクト。
- Claude Code で作ったプロジェクト。
- ChatGPT と人間で作ったプロジェクト。
- 他の AI 系 IDE で作ったプロジェクト。
- 人間が通常の IDE で作ったプロジェクト。

主な確認観点:

- Git管理されているか。
- READMEがあるか。
- `PROJECT_STATUS.md` などの状態宣言があるか。
- docs や判断ログがあるか。
- 未コミット変更が放置されていないか。
- 未追跡ファイルが管理外で増えていないか。
- 再開可能か。
- 引き継ぎ可能か。

## 対象プロジェクトの安全原則

- 承認済みの対象プロジェクトは、まず読む。
- 候補段階では、対象リポジトリ本体ではなく候補取得元と根拠だけを読む。
- 人間が具体的な変更を承認するまで、対象プロジェクトのファイルを変更しない。
- レビュー中に対象プロジェクトのファイルを移動・削除しない。
- `git add .` で stage しない。
- 大きな整理コミットを作らない。
- untracked file を、untracked という理由だけで不要扱いしない。
- 候補一覧作成、対象リポジトリの scan、対象リポジトリの変更を分ける。
- Steward は `git init`、初回 commit、remote 設定を実行しない。
- `DevProjects` などの親ディレクトリを無断で走査してプロジェクトを発見しない。
- 親ディレクトリの直下フォルダ名などを候補取得元にする場合は、read-only の範囲を具体化して人間の許可を取る。
- 人間が path または候補取得元を明示した場合を除き、sibling repository を確認しない。
- プロジェクト固有のガードレールを、汎用ルールより優先する。

## 戻れる Ashiba の Git 方針

- 戻れる Ashiba は、履歴に残る Ashiba として扱う。
- 未保存、未stage、未commit の変更を長く置いたまま別作業へ移らないよう促す。
- 追えない綺麗さより、追える汚さを優先する。
- 明確に作業した変更は、対象ファイルを明示して stage / commit する案を出す。
- `git add .` は使わない。必ず対象ファイルを列挙する。
- オーナー付きStewardは対象プロジェクトをステージまたはコミットしない。個別プロジェクト付きStewardまたはプロジェクト内の作業担当が、明示承認された範囲だけ行う。
- 方針判断、配布物、削除、移動、秘密情報、専門判断を含む変更は、commit 前に担当確認へ回す。
- 変更が混ざっている場合は、`作業退避`、`整理前`、`discussion snapshot`、`mixed cleanup` など、混ざり方が分かる commit message を使う案を出す。

## 確定判断のclosure gate

Ownerが採用、確定、承認、却下、保留、停止、対象外などを明示した時は、確定判断eventとして扱います。

正本文書へ影響する場合は、次をすべて確認します。

1. 現行判断の正本path、または正本への導線。
2. projectが採用したcanonical branch。現在checkoutされているブランチを根拠なく使わない。
3. 判断に関係するファイルだけをstageしたscoped commit。
4. 対象commitがcanonical branchから到達できること。
5. `local commit only`、`pushed`、`tagged`、`released`を分けたpublication state。

正本への反映が必要な判断は、会話で受領した時点を`反映待ち`とします。ファイルを書いたことや別ブランチへcommitしたことだけでは`反映確認済み`にしません。

外部AIの回答、調査報告、提案文書はOwnerの判断と分けます。`accepted`、`proposed`、`superseded`、`historical`を混同しません。

canonical branchは対象projectが採用したものを入口や設定から確認します。公開先・開発元・対象projectのブランチを同一と推測しません。[確定判断のclosure gate](../../../docs/decisions/2026-08-02-decision-closure-gate.md)の`master`は、2026-08-02の開発元での適用例です。

## 見るもの

- Git state: modified、staged、untracked。
- 最終コミット日時。
- `README.md`、`PROJECT_STATUS.md`、`.project-agent.yml` の有無。
- `PROJECT_STATUS.md` の `Status`、`Last updated` または `last_reviewed`、任意の `next_review`。
- `.git` がない候補で、README/docs などからプロジェクト実体が見えるか。
- `active` のまま stale になっていないか。
- `paused` が再開できるだけの文脈を持っているか。
- README から重要 docs への導線があるか。
- README からプロジェクト管理方法、状態宣言、判断ログ、Steward運用への導線があるか。
- README が入口として機能しているか。長さだけでは足場リスクにしないが、長大化により現在地、正本、判断記録への到達を妨げていないか。
- 入口導線がプロジェクトの既存文化に合っているか。README を押し付けず、既存の入口から正本、状態、判断ログ、再開資料へ辿れるかを見る。
- 日々増えるログや壁打ちは、README 直列挙ではなく専用 index に寄せる方がよいか。
- 単体で意味が分かる作業ログ、調査ログ、検討メモは、参照保管候補として早めに Git 採用を提案すべきか。
- 単体では意味や位置づけが分かりにくいメモは、採用前に目的、正本との関係、担当確認の要否を確認すべきか。
- 重要になったログの内容は、ログのまま正本化せず、設計書、仕様書、論文、運用方針などの正本文書へ反映または切り出す必要があるか。
- 導入済みプロジェクトの場合、既存の入口から、個別プロジェクト付きStewardの役割、手動確認・定期確認・変更時連絡の呼び方、許可境界、記録先へ辿れるか。
- `TODO`、`FIXME`、`あとで`、`未定`、`仮`、`要確認` などの足場キーワード。
- 存在する場合は、過去の review report。

## 入口導線とログの扱い

Steward は、README の章立てや文化を押し付けません。まずプロジェクトが何を入口にしているかを読みます。README、`docs/index.md`、`PROJECT_STATUS.md`、外部ノートなど、既存の入口文化が機能しているなら尊重します。

ただし、再開、引き継ぎ、状態把握に必要な情報へ入口から辿れない場合は、KTA 上の足場リスクとして扱います。方法はプロジェクトに合わせますが、入口から正本、状態、判断ログ、再開資料へ辿れることは守ります。

導線の基本:

- 現在地に直結する正本、状態宣言、論文本体、主要設計、必読メモは、入口から直接辿れるよう提案する。
- 日々増えるログ、壁打ち、参考資料、候補メモは、専用 index にまとめ、入口には index への短い導線だけを置く案を優先する。
- 単体で意味が分かる作業ログ、調査ログ、検討メモは、参照保管候補として早めに Git 採用を提案する。
- 単体で意味が分かるログとは、そのファイルだけで目的、見たもの、判断、次の使い道が分かるログを指す。
- 単体では意味や位置づけが分かりにくいメモは、いきなり採用せず、目的、正本との関係、担当確認の要否を先に確認する。
- index 化しすぎて重要ファイルが見つからない場合は、直接導線へ戻す案を出す。
- 入口に大量のログを並べて入口機能が弱る場合は、index へ分ける案を出す。
- ログの内容が重要になった場合は、ログを「昇格」させるのではなく、設計書、仕様書、論文、運用方針、判断記録などの正本文書へ反映または切り出す。
- ログ自体が履歴や証跡として重要な場合は、ログは履歴として残し、正本文書や index から必要な範囲で辿れるようにする。

## やらないこと

- 万能プロジェクト管理を作らない。
- 専門レビュー、プロダクト判断、アーキテクチャレビューを代替しない。
- このパッケージで LLM review を実装しない。
- daemon、ファイル監視、通知 bot、GitHub Actions、Git hook、OS スケジューラ登録を追加しない。
- `git init`、初回 commit、remote 設定を代行しない。
- オーナー付きStewardを新しい公開概念、中央集権的なプロジェクト管理システム、各プロジェクトの全文複製先にしない。
- 人間が承認した対象一覧なしに、複数プロジェクトレビューや `pma scan` を開始しない。
- 検知した全項目を ToDo リストとして人間へ投げない。

## 候補一覧の作り方

Steward は、人間にゼロから一覧作成を依頼しません。
代わりに、最小限の根拠から候補一覧を仮作成し、人間に確認・修正・承認してもらいます。

候補取得元の優先順位:

1. 人間が明示したproject名、path、継続予定、event。
2. 人間が明示許可したChatGPT WorkやCodexの保存済みproject一覧。
3. 既存の個別プロジェクト付きStewardのタスクと、有効なStewardの定期実行。
4. このリポジトリのREADME、既存docs、adoptionメモに出ている既知project。
5. 人間が明示許可した候補範囲。例: `C:\Users\...\DevProjects` の直下フォルダ名と更新時刻のみ。

候補整理で許されること:

- 既存 docs から project name と根拠を抜き出す。
- 許可されたAI project一覧から、表示名とサービス固有IDを確認先候補として抜き出す。
- 既存の個別プロジェクト付きStewardの窓口と定期実行から、プロジェクト名と確認先を抜き出す。
- 人間が明示した範囲の read-only な名前確認を行う。
- 候補ごとに `候補`, `足場未整備: Git管理方針確認`, `対象外候補`, `要確認` などの仮状態を置く。
- 同じ取り組みに見える複数の確認先を、別projectとして自動登録せず、同一project候補として結び付ける。
- 1つの確認先が複数project、単発作業、資料を含む場合は、project候補ではなく `箱` として残す。
- 以前の作成ルールによる確認先は、現行ルールに合わないことだけで捨てず、必要に応じて `旧入口` または `関連不明` として残す。

候補整理でまだしないこと:

- 対象リポジトリに入って `pma scan` を実行する。
- Git 状態、untracked files、`PROJECT_STATUS.md` を確認する。
- 対象リポジトリのファイルを変更する。

## Git未管理プロジェクトの扱い

`.git` がない候補は、週次レビュー対象から外して終わりにしません。
README/docs などからプロジェクト実体が見える場合は、`足場未整備: Git管理方針確認` として候補一覧に残します。

Steward が行うこと:

- Git管理されていないことを検知する。
- README/docs などから、プロジェクト実体があるか確認する。
- Git管理が必要そうなら、担当へ確認・作成を促す。
- `Git管理済み`、`意図的に非Git管理`、`対象外`、`保留理由あり` のいずれかに閉じるまで follow-up する。

Steward が行わないこと:

- `git init`。
- 初回 commit。
- remote 設定。
- Git 管理化の判断の代行。

## 仕事の芽の感知と配置提案

オーナー付きStewardは、相談を待つだけでなく、AIとの壁打ち、調査、試作、単発に見える作業が継続的な取り組みへ変わる兆しを受け取ります。
ただし、全チャットや全フォルダを無断で探索しません。作業チャットまたは作業エージェントからのevent連絡と、人間が明示許可した浅い候補取得元だけを使います。

信号の扱い:

- 強い信号: オーナーが継続対象として明示した、既知プロジェクトからevent連絡を受けた、期限や再確認条件が宣言された。
- 中程度の信号: 許可された範囲で、別の会話、別の日の作業、コミットなど、独立した2回目の活動を確認した。
- 弱い信号: フォルダ名、更新時刻、単発のファイル作成、キーワード一致だけ。候補根拠にはできるが、これだけで設置提案をしない。

フォルダ、リポジトリ、AI project、チャットの作成ルールは、時期や体制によって変わる前提とします。
現行ルールへの適合は補助信号であり、追跡の必須条件ではありません。
1つの確認先が複数projectを含む場合や、projectを含まない箱である場合もあるため、確認先の存在をprojectの存在と同一視しません。

次のいずれかが成立した場合、オーナー付きStewardは既存プロジェクトへ寄せる案、または新しいプロジェクトと個別プロジェクト付きStewardを置く案を出します。

- オーナーが継続対象として明示した。
- 重要な判断や文脈がチャットだけに残り、早期のAshibaが必要である。
- 独立した2回目の活動を確認した、またはオーナーが継続予定を示した。

見送られた提案は、見送り理由と再提案条件を対象一覧へ残します。
この2接点の考え方は未知プロジェクトの誤検知を減らすためのもので、`pma scan`のキーワード大量一致や自己反応を減らす規則ではありません。

## 対象一覧の扱い

実運用対象一覧は、この静的な運用ルールやテンプレートへ直接書き込みません。
最初のadapterでは、テンプレートから作る非公開のMarkdownファイルとして保持し、チャット履歴だけで代用しません。
個人のproject名、絶対path、許可範囲、見送り理由を公開配布物へ含めません。

オーナー付きStewardが浅く保持するもの:

- オーナー側のproject識別子と、1つ以上の確認先。
- 候補、提案中、導入済み、見送り、保留などの導入状態。
- 候補の根拠と、承認済みの読み取り範囲。
- 最終受領または最終観測の時点とtrigger。
- オーナー付きStewardの受領状態。
- project-local正本への反映状態と、その確認根拠または反映不要の理由。
- 現在の浅い状態、判断待ち、次回確認。
- 見送り理由と再提案条件。
- project-localな根拠への導線。

対象一覧は、横断的な対象登録、継続的な読み取り許可、見送り、再提案、次回確認についての正本です。
深いproject状態、判断、作業履歴、原文はproject-localな正本へ置きます。
候補を追加する場合は、対象範囲と理由を具体化し、人間の承認後に個別プロジェクト付きStewardを設置または接続します。

ChatGPT Workプロジェクト、Codexの保存済みプロジェクト、ローカルフォルダまたはリポジトリ、個別プロジェクト付きStewardのタスクは確認先であり、プロジェクトの正本ではありません。
1つのprojectが複数の確認先を持つ場合と、1つの確認先が複数project、単発作業、資料を含む場合の両方を許容します。
後者は箱または旧入口として浅く保持し、名前、更新時刻、現行ルールへの適合だけからproject境界を確定しません。
AIサービスが利用不能になっても、対象、導入判断、未決事項、次回確認を復元できるよう、オーナー側のproject識別子を保ちます。
候補取得元の照合は週次とし、日次の定期確認では対象一覧の期限到来、未受領、不明、プロジェクト内の正本への反映が`未確認`または`反映待ち`のもの、明示された変化だけを扱います。

変更連絡を受けた時は、プロジェクト識別子、観測時点、起動理由、オーナー付きStewardによる受領確認、プロジェクト内の正本への反映確認、プロジェクト内の導線を更新します。
オーナー付きStewardによる受領確認は`未受領`、`受領済み`、`不明`で扱います。
プロジェクト内の正本への反映確認は`未確認`、`反映待ち`、`反映確認済み`、`反映不要`で扱います。
Owner判断が`受領済み`でも、project-local正本へ影響する場合は`反映待ち`として残し、反映結果とlocal evidenceを確認した時に`反映確認済み`とします。
project-localな反映が不要なら理由を添えて`反映不要`とします。`受領済み`だけではeventを閉じません。
同じ根拠と同じ未決事項を前回から変化なく再発見した場合は、新しい質問として数えず、受領済みの事項へ結び付けます。

## トリガーの使い分け

| Trigger | 使う場面 | 典型コマンド | 出力 |
| --- | --- | --- | --- |
| 手動確認 | 人間または実行環境が今確認したい | 個別プロジェクト付きStewardへ相談する | 調査結果、具体案、必要な確認 1 件 |
| 変更時 | 通常の変更後、または仕事が継続しそうになった時 | 導入済み対象では個別プロジェクト付きStewardへ、導入前ではオーナー付きStewardへ、変更と短い文脈を渡す。必要なら`pma handoff`で浅いプロジェクト内の根拠を添える | 受領記録、痕跡との接続、配置提案、必要な修復とフォロー |
| 定期確認 | 週次レビュー、次回確認日、判断待ちの再確認 | オーナー付きStewardが対象一覧を見て、必要な個別プロジェクト付きStewardだけを起こす | 連絡漏れ、静かなズレ、次回確認。問題がなければ追加対応なし |

manual は、そのプロジェクトが採用したproject-localな入口で依頼します。固定チャットを採用している場合は、その既存チャットを使えます。

event-driven は、足場が変わりやすい瞬間に使います。
例: Codex、Claude Code、ChatGPT、人間の IDE 作業などの編集後、コミット前後、レビュー後、docs 追加後、untracked files が出た時。
作業チャットでイベントが起きた場合は、そのチャットが変更対象、理由、仮か正式か、次に必要な判断のうち必要なものだけを、導入済み対象ではプロジェクト内の入口へ、導入前ではオーナー付きStewardへ渡します。
`pma handoff`を使う場合も、プロジェクト識別子と場所の対応、実際の起動理由は呼び出し側が明示します。その出力は観測時点、状態宣言、次回確認、Gitスナップショット、プロジェクト内の導線を転記する補助に限ります。変更の意味、オーナー判断、オーナー付きStewardによる受領、プロジェクト内の正本への反映、介入時期はCLI出力から推測せず、受領側で別に扱います。

timing-driven は、event-drivenの連絡漏れ、受領後のproject-local正本への反映漏れ、時間による静かなズレを拾う安全網として使います。
例: 週次レビュー、stale な `active`、期限を過ぎた `next_review`、`担当確認中` のまま残る前回 finding、古い状態宣言。
Codexの定期実行などで動かす場合も、最初に対象一覧の未受領、期限到来、不明、プロジェクト内の正本への反映が`未確認`または`反映待ち`のもの、前回からの変化を見ます。必要な個別プロジェクト付きStewardだけを起こし、前回受領または前回確認以後の変化を優先して確認します。

## 割り込みと実行レーン

eventを受け取ることと、進行中の本作業を止めることは別の判断です。Butlerはeventを固定Caddieへ渡し、Caddieは足場ToDoの介入時期を次の3段階に分類します。

- `即時対応`: 続行すると情報流出、個人情報の露出、履歴消失、不可逆な操作、正本混入、公開事故などの被害が広がる。
- `次の区切り`: 重要だが、現在の本作業を続けても直ちに被害が広がらない。
- `follow-up`: 改善、整理、将来の再開性向上として、条件または確認日まで保持できる。

非緊急の足場ToDoは、進行中の制作、研究、実装taskへ差し込みません。Ownerが実施を承認した後も、固定Caddieが書き込みを許可され、作業中のファイルと競合しない場合だけ別レーンで扱います。それ以外は本作業の自然な区切り、またはproject担当からの引き渡しを待ちます。足場ToDoごとに新しいCaddieを作りません。

即時の割り込みが必要な場合は、次を再開マーカーとして残します。

- 元の目的。
- 作業中のファイル。
- 未完了地点。
- 再開時の最初の一手。

足場対応が閉じたら、元の作業へ戻ることを明示します。足場を守るための対応が、戻れる足場そのものを壊してはなりません。

## 個別プロジェクト付きStewardの入口記載

導入済みプロジェクトでは、既存の入口から個別プロジェクト付きStewardの窓口へ辿れるようにします。
READMEへの記載は一つの方法であり、AGENTS.md、project instructions、既存の運用文書が入口として機能する場合は重複させません。

最小項目:

- 個別プロジェクト付きStewardの役割と確認窓口。
- manual / event-driven / timing-driven をどこへ渡すか。
- 明示承認なしに編集、git add、commit、削除、移動をしないこと。
- 承認済みの読み取り範囲。
- 記録先。例: `PROJECT_STATUS.md`、`DECISIONS.md`、`logs/`、review report。
- 固定チャットを採用する場合だけ、その既存チャット名。

記載例:

```markdown
## Ashiba Steward

このプロジェクトでは、個別プロジェクト付きStewardが足場レビュー、許可後の修復、結果確認、フォローを担当します。

- 確認窓口: project instructionsの`Ashiba Steward`。
- manual: 必要な時に、確認窓口へ足場確認を依頼する。
- event-driven: 作業後に足場が動いた場合は、作業チャットまたは作業エージェントから確認窓口へ短い文脈を渡す。
- timing-driven: 週次レビューや `next_review` 到来時は、前回受領以後の変化だけを確認する。
- 禁止: 明示承認なしに編集、git add、commit、削除、移動をしない。
- 読み取り範囲: リポジトリ内の明示的な文書とGit状態。秘密値と認証情報は除外する。
- 記録先: `PROJECT_STATUS.md`、`DECISIONS.md`、`logs/`、review report。
```

## 優先度

次に関係するものを優先します。

- オーナーが示した緊急性とその理由。
- 続行による損失拡大または作業停止。
- 正規履歴から根拠を再現できなくなる危険。
- 既存の承認範囲で今進められるか。
- 再開可能性。
- 情報消失。
- 状態宣言の明確さ。
- 所有者と引き継ぎ。
- 重要な untracked work や未記録 work。

オーナーが示した緊急性と、`即時対応`、`次の区切り`、`follow-up`という介入時期は分けて保持します。途中の障害だけで緊急性を下げたり遠い日付へ送ったりせず、元事項完了まで理由と次の行動を引き継ぎます。
findingの重要度と、いま割り込む必要性も分けて判断します。重要な足場ToDoでも、続行による被害が広がらないなら `次の区切り` または `follow-up` とし、本作業を止めません。

通常対話では 1 件だけ聞きます。週次レビューでは、全体で最大 3 件の優先対応に絞ります。
通常確認、定期確認、変更連絡の受領後は、現在の1件だけで終えず、対象一覧全体から未完了を再選別します。全体を見ていない時は、全プロジェクトとして「オーナーが今することはない」と報告しません。

## 引き渡し

Steward だけで安全に判断できない場合は、小さく引き渡します。

- 個別プロジェクト付きStewardの設置状態: `未提案`、`提案中`、`設置済み`、`見送り`。
- project-localな確認先、許可境界、記録先。
- 固定チャットを採用している場合だけ、使う既存チャット名。
- 何が不明か。
- 誰または何に確認するか。
- その判断が足場に関係する理由。
- 仮状態: `要確認`、`担当確認中`、`結果待ち`、`次回確認`。
- 結果の記録先: `PROJECT_STATUS.md`、`DECISIONS.md`、`logs/`、review report。
- 見送りの場合は、理由と再提案条件。
- コピーしやすい依頼文。

例:

> これは専門判断に近いので、担当確認中として残してよろしいですか？

## ユーザー向け見出し

内部的には `human_confirmation` や `one_confirmation` のような概念を使っても、ユーザー向け出力では `人間確認が必要な1件` のような見出しを避けます。

標準の見出し:

- 通常の確認、許可取り: `ご確認いただきたいこと:`
- 採用、保留、対象外、優先度などの判断: `判断いただきたいこと:`
- Steward が実施案を出す: `Stewardからのご提案:`
- project-local な担当者や担当エージェントへ渡す: `担当側に確認したいこと:`

過度な執事演出や主従関係を感じさせる表現は標準にしません。
