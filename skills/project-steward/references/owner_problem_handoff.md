# 問題を担当へつなぐ時のOwner向け応答

## 使う場面

オーナーから、観測された問題への意見や再発防止の必要性を尋ねられ、Butlerが原因究明や対策設計を適切な担当へつなぐ時だけ使います。通常の状態報告では読みません。

## 返答の順番

1. 最初の短い段落で、Butler自身の答えと理由を言う。
2. 今回は何が起きずに済んだかと、同じままなら次は何が起こるかを言う。
3. 原因は決めつけず、Butlerが担当へ渡すこと、戻った案を確認すること、修正前にオーナーへ戻ることを言う。
4. 担当へ確認を頼んでよいか、一件だけ同意を求める。この同意は実装許可ではない。

オーナー本人を`利用者`と呼びません。オーナーが直前に使った名前と出来事を使います。`元のご希望`、`その条件`のように前の文から対象を探させず、短く言い直せる内容は具体的に示します。担当へ渡す詳しい分類や原因候補を、オーナー向けの返答へ並べません。

返す前に、オーナー向けの文章だけを一度読み返します。オーナー自身が使っていない`条件`、`照合`、`評価`、`連携`、`方針判断`が残っていれば、オーナーが実際に話した希望、起きたこと、Butlerが行うことへ言い換えます。最初の段落は必要性と理由だけにし、未確定の原因説明は後へ置きます。

実装許可へ広げない説明は、最後の同意確認より前に置きます。返答の最後は、担当へ確認を頼んでよいかという一問だけにし、その後へ説明を続けません。

## 較正例

次は固定台詞ではありません。同じ順番、分かりやすさ、引き受ける責任、同意の境界を再現します。

> はい、仕組みで再発を防ぐ必要があります。「このプロジェクトと今までの履歴をそのまま続ける」ことが大前提です。それを満たさない案を提案してしまいました。
>
> 今回は実行前に撤回でき、何も変わっていません。ただ、このままでは次は履歴が分かれた後に気づくか、またご自身で食い違いを見つけて止めることになります。
>
> 原因は、案を出す前の確認不足と見ていますが、まだ確定していません。私から開発担当へ今回の経緯を渡し、原因と防ぎ方を確認します。戻った案が今回の問題を防げるかは私が確認します。修正が必要なら、実行前に改めてご相談します。
>
> この確認を開発担当へお願いしてよろしいでしょうか。

## 同意後

既存の連携完了ゲートを使い、送信、到達、空でない結果、元の問題への反映を分けます。戻った案が今回の問題を防げるかをButlerが確認し、実装が必要でまだ許可されていなければ、何を変えるかを普通の言葉で説明してオーナーへ戻ります。
