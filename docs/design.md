# 設計

Status: working design

この文書は、Ashiba Stewardが[KTA原則](principles.md)をどのように実装するかを定めます。
思想の説明は[コンセプト](concept.md)、全体要件は[要件定義](requirements.md)、現在の実装・検証・運用状態は[PROJECT_STATUS.md](../PROJECT_STATUS.md)を参照します。MVP計画（開発資料：`mvp_plan.md`、本配布では省略）は`pma`部品の過去計画と検証履歴です。

Ashibaは全体概念、Keep the Ashiba（KTA）は方法、Stewardは公開上の役割族です。Ashiba Stewardはこのプロジェクト全体の正式名称です。ソース上の配布名とプロジェクト内の自己識別子は`ashiba-steward`、CLIとPythonのimport名は`pma`です。旧称Project Steward Agentと`project-steward-agent`は、既存のローカルフォルダ、公開リポジトリ、現在インストールされている編集可能パッケージの情報、過去の記録を追うために残っています。
Stewardは二つの配置に共通する役割族です。オーナー付きStewardを内部ではButler、個別プロジェクト付きStewardをCaddieと呼び、機械上の関係は`attached_to: owner | project`で表します。
`attached_to`は配置関係だけを示し、許可や設置済み状態を与えません。Butler / Caddieは別の概念、決定権の階級、単独の公開製品名ではありません。
公開概念体系は[公開概念体系と役割の言い方](decisions/2026-08-06-public-concept-and-role-language.md)、配置と内部呼称の対応は[Stewardの役割族・配置・内部呼称](decisions/2026-08-02-steward-role-placement.md)を正本とします。

## 最初の適用範囲

最初に扱うのは、1人のオーナーがAIとの壁打ち、フォルダ、リポジトリから複数の個人プロジェクトを育てる運用です。
仕事は、明確なプロジェクトとして始まる場合だけでなく、相談チャット、調査、試作、単発に見える作業から継続的な取り組みへ変わる場合があります。

会社の組織、顧客、サービス、システム、案件、施策をどの単位で束ねるかは、この段階では設計しません。
現在の1フォルダまたは1リポジトリをproject-localな単位として扱う方法も、最初のadapterであり、普遍的なプロジェクト定義ではありません。
フォルダ、リポジトリ、AI project、チャットの作成ルールは、時期や体制によって変わる前提とします。
現行ルールへの適合を追跡条件にせず、古い入口や混在した箱からも、継続性を守る必要がある仕事を辿れるようにします。

## 配置モデル

現在の運用は、管理装置と各管理対象内のエージェントに近い配置として扱います。

| 配置 | 内部呼称 | 主な責務 |
| --- | --- | --- |
| オーナー付き相談窓口 | Butler（`attached_to: owner`） | 継続しそうな仕事の芽を受け取り、既存プロジェクトへ寄せるか新設するかを提案し、承認済み対象、判断待ち、次回確認を浅く把握する |
| 個別プロジェクト付き実行役 | Caddie（`attached_to: project`） | 1つのプロジェクトの文脈と痕跡を扱い、調査、確認、許可後の修復、結果確認、フォローを行う |
| 補助機能 | `pma scan`など | Git状態、状態宣言、導線、差分など、機械的に確認できる事実を集める |

### Butler（オーナー付きSteward）

オーナー付きStewardは、人間がプロジェクトごとのStewardを一件ずつ巡回しなくてもよい相談窓口です。
各プロジェクトの詳細を抱えて忙しく動き続ける役ではありません。
人間のそばでいつでも相談を受けられ、必要なときに、どの個別プロジェクト付きStewardまたは担当へ聞けばよいか分かっている状態を保ちます。

行うこと:

- 壁打ちチャット、作業エージェント、人間から、継続しそうな仕事の芽を短い連絡として受け取る。
- 人間が許可した候補取得元または浅い観測範囲について、未知の仕事の芽、既知プロジェクトとの関係、再確認時期を確認する。
- 候補を既存プロジェクトへ寄せるか、新しいプロジェクトと個別プロジェクト付きStewardを置くかを、理由とともに提案する。
- 人間が許可した対象プロジェクトの浅い状態を把握する。
- 変更連絡、相談、定期確認の結果を、該当する個別プロジェクト付きStewardへ渡す。
- 各個別プロジェクト付きStewardから、現在の状態、重要なズレ、判断待ち、次回確認、根拠への導線を受け取る。
- 複数プロジェクトを横断し、人間が今判断する価値のあることを圧縮して提示する。
- 通常確認、定期確認、変更連絡の受領後は、現在処理した1件だけで終えず、対象一覧全体から未完了と今進める価値が高い対応を最大3件へ再選別する。
- 個別プロジェクト付きStewardへ渡した事項が、結果待ちのまま消えていないか確認する。
- 安定しているプロジェクトについては、詳細報告や頻繁な確認を求めず、相談が来たときに動ける状態を保つ。

行わないこと:

- 各プロジェクトの深い文脈を中央へ複製する。
- 対象プロジェクトの専門判断、設計判断、採否を決める。
- 個別プロジェクト付きStewardを飛び越えて、対象ファイルを無断で変更する。
- 承認されていないプロジェクトを探索または管理対象へ追加する。

### 仕事の芽を扱う基準

オーナー付きStewardは、すべてのチャットやフォルダ活動をプロジェクトにしません。次の信号を強さの違う根拠として扱います。

- 強い信号: オーナーが継続対象として明示した、既知プロジェクトからevent連絡を受けた、期限や再確認条件が宣言された。
- 中程度の信号: 許可された範囲で、別の会話、別の日の作業、コミットなど、独立した2回目の活動を確認した。
- 弱い信号: フォルダ名、更新時刻、単発のファイル作成、キーワード一致だけ。候補の存在を示す材料にはできるが、これだけで設置を提案しない。

個別プロジェクト付きStewardの設置提案は、次のいずれかが成立した場合に行います。

- オーナーが継続対象として明示した。
- 重要な判断や文脈がチャットだけに残り、早期のAshibaが必要と判断した。
- 独立した2回目の活動を確認した、またはオーナーが継続予定を示した。

提案を見送った場合は、見送り理由と再提案条件だけを浅く残します。
この基準は未知プロジェクトの誤検知を減らすためのもので、`pma scan`のキーワードノイズ対策には使いません。

### Caddie（個別プロジェクト付きSteward）

個別プロジェクト付きStewardは、そのプロジェクトに最も近いAshiba Stewardの実行場所です。

行うこと:

- 通常の変更時に、変更した人または作業エージェントから短い文脈を受け取る。
- Git、既存文書、チケット、ログなど、許可された痕跡を先に調べる。
- 事実、推測、不明点を分け、重要な曖昧さだけを具体案付きで確認する。
- 人間の指示と許可後、既存の適切な場所へ文脈、状態、導線を反映する。
- 修復結果を確認し、残る不明点と次回確認を記録する。
- 判断待ちや保留を放置せず、人間が次の扱いを決めるまで適切な時点でフォローする。
- 把握済みの複数task、変更のまとまり、依存関係、未完了をプロジェクト内の正本と照合し、1taskの結果だけでproject全体を順調または完了と判断しない。

個別プロジェクト付きStewardは固定チャット、プロジェクト指示、Skill、人間の手順などで実行できます。
固定チャットは文脈の継続に使えますが、プロジェクトの正本にはしません。

### プロジェクトを休止する提案の役割分担

プロジェクトを休止する提案は、プロジェクト内の通常の改善提案と分けます。Caddieがオーナーと直接話している場合も、休止案だけは標準経路を飛ばして提案しません。

1. Caddieが、活動、未完了、具体的な次の作業、外部での継続が不明であることを、プロジェクト内の正本と照合してButlerへ返す。
2. Butlerが、他プロジェクトの緊急性、現在の優先事項、オーナーの管理負担と浅く照合する。
3. Butlerが、停止を欠陥と決めつけず、戻せる休止案、再開できること、次回確認を引き受けること、短い返答方法をオーナーへ提案する。
4. オーナーが休止を選んだ場合、Caddieがプロジェクト内の正本へ反映し、結果をButlerへ返す。
5. Butlerが結果を受領し、横断側の状態と次回確認を更新する。

Caddieは、休止以外のプロジェクト内の具体案をオーナーへ直接提案できます。ここで分けるのは、複数プロジェクトを持つオーナーの管理対象から外すかに関わる休止案だけです。

### 優先順位から次の行動への接続

ButlerまたはCaddieが複数の未完了へ優先順位を付けた時は、順位の提示と実行対象の選択を別の処理にしません。現在の1位が、現在の許可範囲で安全に進められ、必要な入力、先行作業、担当からの結果を待っていないなら、その項目を次の行動にします。

1位を直接実行しない場合は、次のいずれかを実行前に確定します。

- 適切な担当へ依頼し、連携完了ゲートの`依頼到達確認済み`まで確認した。これは元事項の完了ではない。
- 阻害中または意図的に後回しであり、理由、確認先、戻る条件がある。
- 新しい事実によって優先順位を変更し、変更後の順序と理由を示した。オーナーが示した緊急性そのものは弱めない。

2位以下は、1位の扱いを決めただけで自動的に進めません。1位を遅らせず、権限、担当、作業対象、必要な注意が競合しない時だけ並行できます。これにより、一覧全体の再選別が正しくても、直前の話題へ注意が戻って実行順だけが入れ替わることを防ぎます。

### 利用者を助ける一手の確認

ButlerまたはCaddieは、正本到達、対象一覧の再選別、一覧同期、仕組み改善、試験継続を、利用者を助けるための内部作業として扱います。これらが最優先の損失または作業停止を直接取り除く場合を除き、内部作業だけを利用者支援の結果へ広げません。

利用者向けに返す前に、現在の実務上の目的と、それを前へ進める行動、実行する担当、結果を閉じる方法を一組にします。

- 現在の許可範囲で安全に実行できる場合は、Stewardが実行し、結果の実体を確認してから返す。
- 読み取り専用または権限不足の場合は、最も価値のある具体案、実行する担当、必要な許可または確認1件、完了確認の方法を返す。
- 対象一覧全体の再選別は内部処理とし、現在の相談へ答える前に行う。別の未完了を利用者向けに割り込ませるのは、それが現在の判断、安全、期限、本作業を変える場合、または直ちに知らせる必要がある重大な危険の場合だけとし、割り込む理由を先に示す。内部で除外したことや変更しなかったことも通常の返答には出さない。
- 現在の事項が未完了なら、今できる回収または具体的な確認先へつなぐ。観測だけが残る場合は、観測する出来事、確認する結果、確認する担当、結果を戻す条件を定め、理由のない将来観測を閉じ方にしない。
- 現在の事項が完了し、関連する即時対応もない場合は、Stewardが新しい仕事を作らず止まることを正しい結果とする。オーナーが今動く必要がないことを、無関係な提案で埋めない。
- 完了報告では、一覧同期、正本確認、試験成功などの内部結果より先に、利用者の実務上の目的に対して何が成立したかを示す。
- 専門判断、オーナー判断、許可を推測して行動を作らない。

管理された振る舞い試験では、試験対象へ期待回答、疑っている失敗、採点基準を渡しません。独立した評価側が、依頼、耐久的な状態、出力、変更後の実体だけから、利用者負担の軽減、目的の前進、実行主体、閉じ方、現在の相談との関連性を確認します。試験対象自身の`成立した`、`できた`、`完了した`という申告は、合格根拠にしません。

### 個別プロジェクト付きStewardの設置済み条件

個別プロジェクト付きStewardは、次の3点がそろった時に設置済みと扱います。

1. オーナー付きStewardの対象一覧に、対象と1つ以上のプロジェクト内の確認先が登録されている。
2. README、AGENTS.md、project instructions、既存の運用文書など、プロジェクトの入口から、Stewardの役割、許可境界、記録先へ辿れる。
3. 個別プロジェクト付きStewardが読んでよい範囲を、人間が承認している。

固定チャット、Codex task、project instructions、Skill、人間の手順は、この役割を動かすruntime adapterです。
固定チャットの有無だけで、設置済みかどうかを判定しません。

## 情報の流れ

### プロジェクトになる前の仕事

```text
AIとの壁打ち・調査・試作・単発に見える作業
  -> 作業者または作業エージェントが、継続の兆しをオーナー付きStewardへ短く渡す
  -> オーナー付きStewardが、非公開の浅い対象一覧と照合する
  -> 既存プロジェクトへ寄せる案、または新しいプロジェクトと個別プロジェクト付きStewardを置く案を出す
  -> 人間が配置と読み取り範囲を判断する
  -> 承認後に登録し、project-localな入口と記録先へ接続する
```

オーナー付きStewardは、会話の内容を全文保存したり、許可されていないフォルダを読んだりして候補を作りません。
作業チャット側からのevent連絡を主経路とし、許可された浅い観測は漏れを拾う安全網として使います。

### 通常の変更

```text
変更した人・作業エージェント
  -> 個別プロジェクト付きStewardへ短い文脈を渡す
  -> 個別プロジェクト付きStewardが既存の痕跡と照合する
  -> 必要な判断または許可を人間へ求める
  -> 許可後に個別プロジェクト付きStewardが記録・状態・導線を修復する
  -> 結果を確認する
  -> 浅い状態と判断待ちだけをオーナー付きStewardへ返す
```

event-drivenの中心は`pma scan`の実行ではなく、変更と文脈の受け渡しです。
`pma scan`は、残された痕跡との照合や不足候補の検知に使う補助機能です。

許可された方法が失敗した場合や重要な前提が崩れた場合、Stewardは方法を目的へ置き換えず、実務上の目的と変えてはいけない結果条件へ戻ります。現状維持を含む代替案をその条件と照合し、目的、対象範囲、完了条件、正本、project identity、履歴、権限、公開範囲を変える案は、以前の許可の続きではなく新しい判断としてオーナーへ返します。この確認は方法または結果条件が変わる時だけ行い、結果が変わらない通常の小さな作業へ追加手順を課しません。

### 相談で回収した背景を次の担当へ残す

FR-REC-03〜05とFR-REP-01〜03を、Caddieの情報所在・判断理由の相談へ接続します。運用Skillの該当入口からだけ[相談・記録・復元手順](../skills/project-steward/references/caddie_context_recovery.md)を読み、既存の正本と痕跡から助言し、不足分は許可内で確認して元の質問へ戻します。現在の規則の効用と当時の採用理由を分け、記録補完は別に確認できた許可範囲で行います。

本文は既存の判断・変更記録へ後日補足として置き、根拠は既存の保存先または許可された原文保全先へつなぎます。現在地へ全文を複製せず、同じ記録が十分なら追加しません。プロジェクト資料だけで後任が根拠へ戻れること、元の記録・未確認・権限を保つことを検証し、部品の整合、管理された復元、通常の効果を分けます。新しい記憶保管庫、台帳、実行基盤、pma機能は追加しません。

### 緊急対応

緊急時は対処を優先します。
その場で文脈を渡せなかった場合は、落ち着いた後のtiming-driven見回りで、記憶と痕跡が新しいうちに回収します。

### 定期的な見回り

```text
既存の定期実行・リマインダー
  -> オーナー付きStewardが浅い対象一覧の最終受領、次回確認、未決、候補状態を見る
  -> 未受領、期限到来、不明、正本反映待ち、前回からの変化がある対象だけを選ぶ
  -> 必要な場合だけ個別プロジェクト付きStewardを起動する
  -> 個別プロジェクト付きStewardが前回受領・前回確認以後の変化を浅く見る
  -> 連絡のない変更、宣言と実態のズレ、期限到来を拾う
  -> 必要な場合だけ調査・確認・修復へ進む
  -> 結果または「追加対応なし」をオーナー付きStewardへ返す
```

timing-drivenは安全網です。毎回すべてを読み直したり、同じ質問を機械的に繰り返したりしません。

導入済み対象の既存`次回確認`には、連絡がなくても確認する最終期限を日付で置きます。個別事項の「結果が届いたら」などの戻る条件とは別です。条件だけの既存入力は拒否せず、`pma followups`が`review_deadline_missing`として選びます。休止中も対象です。候補・見送りの条件付き確認は維持します。間隔は影響・活動・許可範囲から定め、全対象へ一律の日数を製品で固定しません。

候補は全件保持し、提示する最大3件に入らない期限超過も消しません。Butlerは個別の定期実行結果を先に回収して重複起動を避け、機械候補0件でも未完了と未回収結果を照合します。期限後の限定した再確認で回収不能なら、状況不明の影響、試した回復、次の確認先をオーナーへ報告・相談します。無活動を異常と決めつけず、取得不能を無回答とも断定しません。

センサーは候補を返すだけで、自動送信、予定登録、権限変更はしません。実行経路と最終確認の根拠は既存の確認先・最終受領・根拠欄に置き、別台帳を増やしません。全実行環境が停止中なら自動救済できない限界は残ります。実行担当の手順とモデル選択は[定期確認と実行設定](../skills/project-steward/references/timing_and_model_policy.md)にまとめ、運用ごとの推奨設定を製品定数にしません。

## Butlerの耐久的な対象一覧

オーナー付きStewardは、チャット履歴だけに依存せず、実運用の対象一覧を耐久的な場所へ保持します。
最初のadapterでは、[対象一覧テンプレート](../skills/project-steward/templates/project_list.md)から作る非公開のMarkdownファイルを使います。保存場所はオーナーが実運用面で定め、この公開repositoryには記載せず、チャット履歴だけでも代用しません。
実データはテンプレートと分け、個人のプロジェクト名、絶対path、許可範囲、見送り理由を含み得る非公開の運用記録として、公開配布物へ含めません。

対象一覧が持つ情報は、原則として次に限定します。

- オーナー側のproject識別子と、1つ以上の確認先。
- 候補、提案中、導入済み、見送り、保留などの導入状態。
- 候補の根拠と、承認済みの読み取り範囲。
- 最終受領または最終観測の時点とtrigger。
- オーナー付きStewardの受領状態。
- project-local正本への反映状態と、その確認根拠または反映不要の理由。
- 現在の浅い状態。
- 判断待ちと確認先。
- オーナーが示した緊急性とその理由。これは`即時対応`、`次の区切り`、`follow-up`という介入時期とは別に保つ。
- 未完了事項の許可済みの次の行動と戻る条件。
- 横断事項ごとの`対応済み`、`対象外`、`未確認`と根拠。
- 次回確認の条件または時期。
- 見送り理由と再提案条件。
- 詳細を確認できるproject-localな根拠への導線。

この一覧は、横断的な対象登録、継続的な読み取り許可、見送り、再提案、次回確認についての正本です。
プロジェクトの深い状態、判断、作業履歴、原文はproject-localな正本へ置き、一覧へ複製しません。

ChatGPT Workプロジェクト、Codexの保存済みプロジェクト、ローカルのフォルダまたはリポジトリ、個別プロジェクト付きStewardのタスクは、プロジェクトそのものではなく確認先です。
1つのprojectが複数の確認先を持つ場合は、別projectとして自動登録せず、同じ行へ結び付けます。
逆に、1つの確認先が複数のproject、単発作業、資料を含む箱である場合や、現在はprojectを含まない旧入口である場合もあります。
確認先の名前、作成場所、更新時刻、現行テンプレートへの適合だけから、projectの存在、境界、進行を確定しません。
AIサービス固有のproject IDやtask IDは確認先として保持できますが、オーナー側のproject識別子と導入判断の正本にはしません。

候補取得元の照合は週次で行います。明示許可されたChatGPT/Codexのプロジェクト一覧、既存の個別プロジェクト付きSteward、明示許可された親フォルダ直下の名前と更新時刻を対象一覧と比べます。
projectの内容、Git状態、ファイル本文は候補段階では読みません。
観測した確認先は、必要に応じてproject候補、箱、旧入口、関連不明として区別します。箱や旧入口を無理に1つのprojectへ対応付けず、現行ルールに合わないことだけでも除外しません。
同一projectか不明なもの、自動的に導入状態を決められないものは、通常1件ずつ人間へ確認します。

event連絡を受けた時は、少なくともプロジェクト識別子、観測時点、起動理由、オーナー付きStewardの受領状態、プロジェクト内の導線を更新します。
オーナー付きStewardによる受領確認と、個別プロジェクト付きStewardによる正本への反映確認は別状態として扱います。

- オーナー付きStewardによる受領確認: `未受領`、`受領済み`、`不明`。
- プロジェクト内の正本への反映確認: `未確認`、`反映待ち`、`反映確認済み`、`反映不要`。

Owner判断を受領しても、project-localな正本、状態、導線へ影響する場合は`反映待ち`として残します。
個別プロジェクト付きStewardが反映結果とプロジェクト内の根拠を確認した時に`反映確認済み`とし、プロジェクト内の反映が不要なら理由を添えて`反映不要`とします。
オーナー付きStewardが`受領済み`であることだけではeventを閉じません。
同じ根拠と同じ未決事項を前回から変化なく再発見した場合は、新しい質問として数えず、受領済みの事項へ結び付けます。
オーナーが緊急または優先とした事項は、理由とともに元事項へ結び付けます。途中で実装障害、保存先不明、確認待ちが生じても、それだけを理由に将来日へ送らず、許可済みの次の行動、確認先、戻る条件を保ちます。
横断事項は新しい台帳を作らず、この一覧のevent受領記録で、導入済みの各プロジェクトを`対応済み`、`対象外`、`未確認`へ一度ずつ照合します。

### 未完了事項の識別と個別完了

オーナーが別々に扱うよう示した未完了事項は、同じプロジェクト、同じ根拠、似た症状、同じ変更に関係していても、各事項の目的と完了条件が同じと確認できない限り別々に保持します。新しい台帳や一律の識別番号は増やさず、既存の`event受領記録`で事項ごとに行を分けます。横断事項は`横断事項`欄をその事項の識別に使い、プロジェクト内だけの事項は`浅い要約`、`判断待ち / 確認先`、`次の行動 / 戻る条件`で区別できる短い名前を保ちます。

同じ根拠と同じ未決事項への重複連絡は既存行へ結び付けますが、関連する言葉や対策を含むことだけでは同じ事項とみなしません。開発または担当から結果を受け取った時は、関係する各事項について次を別々に照合します。

- `解決した`: その事項自身の完了条件と結果確認を満たした。該当行だけを閉じる。
- `一部だけ救った`: 結果が一部へ効いたが完了条件は未達。救えていない部分、次の行動、戻る条件を同じ事項に残す。
- `救っていない`: 関係する表現または変更があっても、その事項の完了根拠にならない。状態を引き継ぐ。

一つの結果は複数の事項の根拠として参照できますが、一つの事項の完了を別の事項へ引き継ぎません。`横断対応`の`対応済み`は、そのプロジェクトを横断照合した状態であり、横断事項そのものの完了を意味しません。いずれかを閉じた後は、機械的な候補だけでなく対象一覧の未完了行全体へ戻ります。`pma followups`の候補が0件でも、通常の緊急性で次の行動または将来の戻る条件を持つ未完了行は存在し得るため、全体として未完了なしとは判断しません。

### Butlerのfollow-up選別センサー

`pma followups --list <明示した一覧>`は、上記の耐久的な対象一覧全体から、いま確認が必要な行だけを機械的に選ぶ読み取り専用センサーです。対象一覧を新設・更新せず、対象プロジェクトや確認先も読みません。選別結果には、記録済みの緊急性と浅い理由コードから機械的に並べた最大3プロジェクトの提案と、記録や通知だけで終わらせない完了条件を添えます。この順序はプロジェクトの実状態を読んだ判定ではありません。通知、再実行、個別プロジェクト付きStewardの起動、候補への実際の対処は実行接続部または人間の責務に残します。

選別する信号は次に限定します。

- `対象`表のISO日付による`次回確認`が基準日以前。
- `浅い状態`がセル全体で`unknown`または`不明`。
- 変更連絡の受領記録で、オーナー付きStewardの受領が`未受領`または`不明`。
- プロジェクト内の正本への反映が`未確認`または`反映待ち`。
- `判断待ち / 確認先`がセル全体で`unknown`または`不明`。
- 未受領、不明、未反映、または既知の判断待ちを持つ変更連絡だけ、ISO日付の`次回確認`が基準日以前。
- 未完了の変更連絡に記録された緊急性が`緊急`、`優先`、`不明`。`緊急`または`優先`は次回確認が将来でも選ぶ。
- 未完了の変更連絡で、`次の行動 / 戻る条件`が`なし`または`不明`。
- 横断事項について、導入済みプロジェクトの照合行がない、または横断対応が`未確認`。

`event受領記録`は履歴なので同じプロジェクトの複数行を許容し、各行を独立に評価します。ただしプロジェクト、理由コード、期限が同じ出力は1候補へまとめ、同じ確認を重ねて出しません。受領と正本への反映が閉じ、判断待ちもない過去の変更連絡にある古い`次回確認`は再通知しません。条件文は日付へ変換せず、次の手動確認または変更時の起動理由へ残します。予定した実行環境が停止しても、実行履歴を持たず次の実行日の比較で期限超過を拾います。このため、実行できなかった回数や理由は復元せず、最後に記録された期限を過ぎている事実だけを扱います。

欠測後に動けた時は、実際の基準日で候補を選び、対象の個別プロジェクト付きStewardが現在地を確認します。必要な修復と次回確認をプロジェクト内で閉じ、その浅い結果を受け取ったオーナー付きStewardが対象一覧を更新します。同じ基準日でも期限超過候補が消えたことを再選別で確認して一巡を閉じます。次回確認が未決なら候補を消さず、確認先または戻る条件を残します。実行接続部が再び動かない限り自動復帰はできないため、常時稼働や遅延分の自動実行はこの契約に含めません。

追加列、列順、周囲の散文は許容します。一方、必須の2表、必須列、対象表のプロジェクト一意性、既知の受領・反映・緊急性・横断対応、表の行数整合を確認できない場合は、内容を推測せず部分出力も行いません。空欄、テンプレート値、日付に見える非ISO値も実行不能とします。正常出力は一覧全体を選別したこと、全候補のプロジェクト、日本語の理由、内部理由コード、期限と、記録済みの緊急性と理由コードから作る最大3件の一般的な提案、完了確認を示します。確認先、要約、緊急性の理由、横断事項名、根拠、一覧の非出力列は提案のためにも転載しません。エラーも破損セルの値を引用しません。

候補が0件でも複数でも、選別とMarkdown出力が完了すれば終了コードは`0`です。候補0件は一覧に記録された機械候補がないことだけを表し、全プロジェクトの実状態を確認したことやオーナーが今することがないことを意味しません。非0は入力を安全に解釈できず、要求された選別を完了できなかったことだけを表します。

## Butlerへ返す最小情報

オーナー付きStewardは、各プロジェクトの全文や詳細ログを保持しません。
個別プロジェクト付きStewardから返す情報は、原則として次に限定します。

- project識別子。
- 個別プロジェクト付きStewardまたは担当の確認先。
- 観測時点とtrigger。
- 現在の浅い状態。
- 前回からの重要な変化。
- 文脈の受領済み、欠落候補、不明の区別。
- project-local正本への反映状態とlocal evidence。
- 人間の判断待ちがある場合、その要点と確認先。
- 次回確認の条件または時期。
- 詳細を確認できるproject-localな根拠への導線。

秘密値、不要な原文、プロジェクト固有の詳細は中央へ複製しません。
オーナー付きStewardが詳細を必要とした場合も、自分で恒常的に保持するのではなく、その時点で個別プロジェクト付きStewardまたは担当へ問い合わせます。
プロジェクトの深い状態はproject-localな正本と痕跡から再取得できる形を保ちます。
一方、横断的な対象登録、継続的な読み取り許可、見送り、再提案、次回確認はproject-localな痕跡だけでは復元できないため、対象一覧を耐久的に保持します。

## 正本と通信路

- プロジェクトの深い状態と判断は、そのプロジェクトが採用した正本へ戻す。
- 固定チャットやタスク間メッセージは通信路であり、唯一の保存先にしない。
- オーナー付きStewardは浅い状態マップとフォロー情報だけを持つ。
- `README.md`、`PROJECT_STATUS.md`、`.project-agent.yml`は現在のadapterであり、全プロジェクトへ一律に要求する普遍的なAshiba Steward要件ではない。
- 詳細な履歴は既存のログや判断記録へ置き、現在地の文書へ重複して列挙しない。
- 共通化するのはファイル名や章立てではなく、現在値を答える入口が1つで、現在のフェーズ、状態、ブロッカー、オーナー判断の要否、次の行動、最後に確認した結果へ短く到達できるという契約である。

## 最初に検証する一巡

Ashiba Steward全体の最初の成立は、scan結果の生成では判定しません。
1つの現役プロジェクトで、少なくとも次を一巡させます。

1. event-drivenの変更連絡を受ける、またはtiming-drivenで受け渡し漏れを見つける。
2. 既存の痕跡を先に調べる。
3. 事実、推測、不明点を分ける。
4. 推奨案と必要な判断または許可を示す。
5. オーナー付きStewardが判断の受領を記録し、プロジェクト内の正本への反映が必要かを`未確認`、`反映待ち`、`反映不要`のいずれかに置く。
6. `反映待ち`なら、許可後に個別プロジェクト付きStewardが記録、状態、導線を修復する。
7. `反映待ち`の結果とlocal evidenceを確認して`反映確認済み`へ更新する。`反映不要`の場合は、その理由を確認して状態を保つ。
8. 未決または未反映が残る場合は、再確認条件を残してオーナー付きStewardへ返す。
9. オーナー付きStewardが受領時点、受領状態、反映状態、次回確認を対象一覧へ反映する。

同じ根拠と同じ質問が、変化がないまま次のtiming-driven確認で繰り返されないことも、この一巡の確認対象にします。

## 現行`pma`センサーの境界

現行の`pma`は、ローカル Git プロジェクトの周囲に置く読み取り中心の補助センサーです。
`pma`は現在、Project Memory Anchor（プロジェクトの運用記憶の取付点）と読みます。新しい記憶保管庫を作るのではなく、Git、状態文書、判断記録、対象一覧など、運用記憶がすでに残っている取付点を観測します。歴史的な展開形が正本にないため、当初からの正式名称だったとは扱いません。

- プロジェクトの実態を読む。
- 記録と状態宣言を読む。
- ズレの候補と根拠を作る。
- 個別プロジェクト付きStewardが調査を始める材料へ圧縮する。

commandの役割は、`scan`がいま見るべき取付点を見つけ、`followups`が戻る時期の来たプロジェクトを選び、`handoff`が受け渡しに添える浅い観測を作ることです。`pma`自身はプロジェクト状態の修正、commit、通知、受領、意味の判断、follow-upの完了を行いません。既定は読み取り専用で、明示した`scan --save-report`だけがプロジェクト内へレポートを保存します。

現行実装は1つのローカルリポジトリ、Cheap scan、Markdownレポートに限定されています。
これはAshiba Steward全体の境界ではなく、既存の補助機能として継続利用できる範囲です。

## 現行`pma`センサーの構成

責務を Scanner、Historian、Steward の3つに分けます。

### Scanner

現在の表面から、機械的に確認できる事実を集めます。

- Gitリポジトリとルート。
- working tree、未追跡ファイル、HEAD commit、branch、直近コミット。
- 必須ファイルの有無。
- 状態メタデータと日付。
- 設定された正本とREADME導線。
- 許可された範囲の足場キーワード。

Scanner は重要度や意図を断定しません。

### Historian

時間による変化を扱います。

- 状態ファイルの確認日と `next_review`。
- 直近コミットと状態更新を別々に比較する。
- 過去のレポートと未決finding。
- 判断記録や運用ログ。

コミットが新しいことを理由に、古い状態宣言を新しいものとして扱いません。
活動の鮮度と記録の鮮度は別の証拠です。

現行`pma`部品のHistorianは、直近コミットと状態日付の読み取りまでの部分実装です。
`project.status_file` で指定したproject内の状態ファイルを読み、`next_review` 超過を活動の古さとは別のfindingとして扱います。
設定先がproject外を指す場合は読み取りも存在確認も行わず、欠落や読取不能とは別のfindingとして扱います。
project内でも、機密名または許可されていないテキスト形式なら読みません。

### レポート整形

現行コードで`Steward`と呼んでいた層は、ScannerとHistorianの結果をレポートへ整形します。
これはAshiba Steward全体ではなく、個別プロジェクト付きStewardへ渡すセンサー出力です。

- 事実、解釈、影響、提案を分ける。
- 詳細を読む前の機械的な全体判断として、`continuity`を`ready`、`at_risk`、`unknown`のいずれかと理由1文で示す。
- レポート全体に、実行日時、対象path、HEAD commit、branch、working treeのclean / dirty、観測の一貫性を1つだけ持たせる。
- 安全性と再開可能性から優先順位をつける。
- 通常は一件、重大事項は件数制限を越えて提示する。
- 担当判断が必要なものは、確認先と記録先を添える。

現行`pma`部品はルールベースの提案だけを生成します。
`unknown`はGitまたは現在状態という中核観測ができない場合、`at_risk`はmedium以上のfindingがある場合、`ready`はlowだけまたはfindingがない場合に使います。`ready`はプロジェクト全体の安全を断定せず、「確認できた範囲」の判断として理由へ明記します。項目の一部だけが曖昧または不正な場合は、codeだけで全体を`unknown`にせず`at_risk`として扱います。
このレポートだけでfindingを閉じたとは扱いません。
個別プロジェクト付きStewardが調査、確認、許可後の修復、結果確認、フォローへつないで初めてAshiba Stewardの一巡になります。

## 現行`pma scan`のデータフロー

```text
対象path
  -> Gitルートと安全な走査範囲を確定
  -> 設定と状態ファイルを読む
  -> Git・ファイル・導線・日付の事実を収集
  -> finding候補を生成
  -> severityとpriorityを決定
  -> Markdown / 将来のJSONへ整形
  -> 必要な場合だけプロジェクト内へ保存
```

走査失敗と「Gitリポジトリではない」は区別します。
一部を読めなくても、確認できた事実と確認不能な範囲を分けて報告します。

## 現行adapterで使うプロジェクト内ファイル

ここで挙げるファイルは、現在の試行環境で使うadapterです。
同じ情報へ安全にたどれる既存の正本がある場合は、これらのファイルを新設または必須化しません。

### `README.md`

プロジェクトの身元と入口です。
現在地、正本、状態、判断記録へ短く辿れればよく、管理方法の全文は置きません。

### `PROJECT_STATUS.md`

現在の状態、確認日、次回確認、再開に必要な短い文脈を置きます。
詳細な作業履歴は既存ログへ置き、ここには現在地と導線だけを残します。
現行`pma scan`ではMarkdownを読みますが、メタデータ部分は曖昧な全文検索ではなく、明確な領域またはfront matterとして扱える形へ寄せます。

### `.project-agent.yml`

プロジェクト固有の期待値を置きます。

- project name、status file、source of truth。
- required files、走査対象、除外対象。
- 状態確認の既定値。
- 自動適用されるプロジェクト指示、開始時に必ず読む文書、必要時だけ読む資料、履歴・索引・参考資料の分類。
- 毎回読む情報の通常目標、改善を優先する目安、理由付き例外と再確認条件。
- レポート件数と保存先。

設定は、プロジェクト外の読み取りや書き込みを許可する権限として使いません。
`checks.required_files`はファイルとして存在を確認し、README、状態ファイル、設定ファイル以外の欠落も一般findingにします。
`project.source_of_truth`はproject内のファイルまたはディレクトリとして存在を確認します。README自身を除く存在済み正本について、README本文に相対pathがあるかを安い導線候補として確認します。意味的な正しさ、リンク先の内容、外部URLの有効性はこのCheap scanでは断定しません。

### 判断記録、`logs/`、`reports/`

必要なプロジェクトだけが採用します。
ログは履歴、設計書や仕様書は正本として分け、重要になったログ内容は正本へ反映します。

## 安全な走査

Cheap scanでも、リポジトリ内の全ファイルを無条件に読んではいけません。

既定の設計:

- Markdown、設定、明示されたテキスト形式を許可方式で読む。
- `.gitignore`、既定の機密パターン、設定された除外を適用する。
- `.project-agent.yml`がない場合は既定値を使う。明示的な設定が存在するのに安全に読めない場合は、除外範囲を推測せずkeyword内容走査を止める。
- `.env`、秘密鍵、credential、token store、認証ファイルを既定で除外する。
- symlinkの参照先がプロジェクト外なら読まない。
- keyword findingは補助信号とし、設定ファイル自身への反応、文脈を無視した大量一致、前回から変化していない一致を主要findingにしない。
- keyword findingを使う場合も原文全体を載せず、安全な位置情報と短い説明を使う。
- サイズ、件数、実行時間に上限を置く。

`--save-report` の保存先は、解決後の絶対パスがプロジェクト配下にあることを確認します。

現行の最小実装は安全側に倒し、内部・外部を問わずsymlink自体をkeyword走査から除外します。
Gitが認識するtracked / untrackedのうち`.gitignore`対象外だけを候補にし、許可拡張子、既定の機密名、`checks.exclude_paths`を通過したファイルだけを読みます。
未追跡物は`git status --short --untracked-files=all`でファイル単位に数えます。Gitのignore規則は従来どおり尊重し、無視対象の探索は追加しません。
`checks.exclude_paths`の末尾が`/`の単純なディレクトリ指定は、その配下全体を表す互換入力として扱います。例として`outputs/`は`outputs/**`と同じ範囲を除外します。
各Gitコマンドは30秒で打ち切り、応答停止をGit状態の確認不能として報告します。最初のtimeoutで後続のGit走査を止め、キーワード用のGit一覧取得だけが失敗した場合も未確認とします。タイムアウトを理由に走査範囲を広げません。
Gitリポジトリかどうか自体を確認できなかった場合、リポジトリルートも確定値として表示しません。Git状態またはキーワード用のGit一覧を確認できなかった場合、その観測に依存する件数を`0`や`なし`とは表示せず、`未確認`と表示します。
Gitリポジトリではないと確認できた場合は、Git依存のroot、HEAD、branch、working tree、件数、直近commit、keyword候補を`対象外`と表示します。
明示的な`.project-agent.yml`はsymlinkを追わず、UTF-8の通常ファイルかつ1MB以下の場合だけ読みます。読取不能、解釈不能、辞書形式でない場合も、parser例外や設定原文を出さず`config_unavailable`とし、`continuity: unknown`へ戻します。この場合もGitから独立に確認できた事実と固定のREADME確認は継続しますが、設定に依存する状態ファイル、正本、必須ファイル、未追跡分類、keyword内容走査は未確認とします。`--save-report`も設定された保存先を推測せず拒否します。
専用チェックがある`.project-agent.yml`と状態ファイル、Ashiba Stewardが生成した`footwork_review`はkeyword走査から除外します。1文字keywordは語の一部まで拾わず、区切りが確認できる場合だけ候補にします。
keyword findingはTODO一覧の代替ではなく確認すべきファイルを示すセンサーなので、同じファイルでは設定順で優先される代表候補1件だけを返します。一致原文は保持せず、レポートにはpath、行番号、検知語だけを出します。
候補ファイルは、現在のworking treeで変更・追加されたものと既存不変のものに分けます。既存不変の候補は位置情報を背景として残しますが、毎回の主要findingにはせず、今回変更された候補だけを優先します。
未追跡物は合計をGit状態へ残したうえで、`checks.exclude_paths`に一致する設定上の背景と、それ以外の要確認候補に分けます。背景へ分けたpathも隠さずGit statusの範囲で表示しますが、件数だけを理由に主要findingへしません。
report保存先は解決後のpathがproject内にある場合だけ作成し、同日ファイルが存在する場合は排他的な新規作成で連番保存します。

## 状態と鮮度

目標モデルでは、作業状態、ライフサイクル、継続性を分けます。

```yaml
work_state: active | paused | blocked
lifecycle: experimental | production | maintenance | archived
continuity: ready | at_risk | unknown
```

現行の単一 `Status` は互換入力として扱います。

状態文書は、作業開始・再開時、文脈圧縮後、現在値に関係する変更後に読むライブ入口として扱います。同じ連続作業の候補ごとには全文を再読しません。閉じた履歴、詳細ログ、終了済み判断、個別結果は既存の正本へ分け、状態文書には現在値と導線だけを残します。

従来の4,096文字・128行は、2026-08-23に状態文書1件の肥大化候補を見つけるため導入した内部の試行値で、外部基準、token量、通常作業の品質との対応根拠はありませんでした。代表6プロジェクトで実際に毎回読むと整理されたプロジェクト固有情報は3,231〜12,695文字、97〜183行であり、4,096文字では理由のある整理済み文書の多くも警告対象になります。このため、普遍的な上限としては採用しません。

現行`pma scan`は、次を分けます。

- 自動適用されるプロジェクト指示: プロジェクト内の`AGENTS.md`等のうち、実行環境により毎回適用されると宣言したfile。
- 開始時に必ず読む文書: README、現在地など、プロジェクトが毎回読むと明示したfile。
- 必要な時だけ読む資料: 作業内容に応じて辿る仕様、判断、設計等。固定入力の合計から除外する。
- 履歴・索引・参考資料: 閉じた経緯や詳細。固定入力の合計から除外する。
- システム、全プロジェクト共通指示、Skill、ツール定義: プロジェクト側で直接削減できないため、project管理の合計から除外し、総使用量とは断定しない。

主な観測値は、最初の2分類を重複除去した合計です。文字数は依存を増やさず量を比べる目安、行数は分割や構造を確認する目安です。任意の`tiktoken`が利用できる場合は設定した代表encodingでfileごとのtoken数を実測して合計します。利用できなければ`未確認`とし、文字数から換算しません。このtoken数も実際のCodexデスクトップ入力、cache、クレジット、課金量の計測値とは扱いません。

試行中の通常目標は8,192文字・192行、改善を優先する目安は16,384文字・384行です。通常目標は代表6件のうち安全規則を多く含む1件を除く5件を収め、行数は観測最大の183行を少し上回る位置です。改善優先は観測範囲を明確に超える量だけを先に扱うための保守的な初期値であり、どちらもtokenやクレジットの換算式ではありません。通常目標超過はlowの確認候補、改善優先超過はmediumの改善候補とし、非停止です。

安全、権限、オーナー判断、現在地のため必要な情報は、数字合わせで削りません。超過理由と再確認条件が両方あれば理由付き例外として受理し、条件到来時に再確認します。片方だけなら例外は未完成です。本文、例外理由の原文、安全に読めないpathはfindingへ転載せず、自動分割、自動削除、ルート状態文書の自動作成を行いません。

`.project-agent.yml`がなく実際の状態文書と毎回読む範囲を確認できない場合は、ルートの`PROJECT_STATUS.md`を正本と決めつけず`毎回読む範囲を確認できません`と返します。旧`checks.status_max_chars`と`checks.status_max_lines`を持つ設定は、状態文書単体の互換警告を維持しますが、固定入力全体を確認済みとは扱いません。過去に状態文書単体が閾値内という理由で閉じた記録は失敗へ戻さず、新しい4分類を一度だけ浅く確認して移行します。

OpenAI公式資料から根拠にできるのは、APIのusageが入力token等を別に持つこと、token数を数えるAPIがあること、重複指示や不要な例を減らした簡潔なpromptを代表作業で検証する推奨までです。Codexデスクトップのクレジット換算やcache対象はこの設計から推測しません（2026-08-25確認: [model guidance](https://developers.openai.com/api/docs/guides/latest-model), [Responses usage](https://developers.openai.com/api/reference/cli/resources/responses/methods/create), [input token count](https://developers.openai.com/api/reference/cli/resources/responses/subresources/input_tokens)）。

鮮度判定では、次を独立して見ます。

- `last_reviewed` または状態更新日。
- `next_review` の期限。
- 直近コミット日。
- working treeの変化。

例:

- 状態文書は古いがコミットが新しい: 活動はあるが状態宣言が追いついていない候補。
- `paused` だがコミットが続く: 再開済みか、意図した保守作業かを確認する候補。
- `active` で活動も確認も古い: 継続、休止、保留を確認する候補。

現行実装では `next_review` 超過を独立して判定します。
状態日付は欠落と不正値を分け、ISO日時を互換入力として受け入れます。不正な値そのものはfindingへ転載しません。
単一 `Status` の既知の互換値は `active`、`paused`、`blocked`、`archived` とし、statusの欠落と未知の値を別findingにします。未知値はAshiba Stewardのローカルな語彙に対して未認識なだけなので不正とは断定せず、値そのものをレポートへ転載しません。日付は外部基準で解釈可能性を判定できるため、不正日付として扱います。
同じ状態項目が複数ある場合は、後方の例や過去記録を現在値として黙って採用しません。重複した項目名だけを`ambiguous_status_fields`として示し、値は転載せず、該当項目を使う状態・日付判定を未確認として扱います。
既知値は `status.py` を正本とし、`config.py` の `stale_days` はそのサブセットです。
直近コミットをGit活動、`Last updated`と`last_reviewed`のうち新しい日を状態文書で確認できた最新日として別々に扱い、`active`の無活動、Git活動に追いつかない状態文書、`paused`確認後のGit活動を区別します。working treeに変更がある場合は、その時刻を確定できないため`active`の無活動とは断定しません。後から状態を確認した場合は、それ以前の`paused`中活動を繰り返し通知しません。
`blocked`には固定stale閾値を設けず、`next_review`を再確認の安全網とします。Cheap scanの開発上の区切り後に採用した状態継続期間表示では、手入力の`status_since`を増やさず、一意に読めた現在の`Status:`行をGit履歴で確認し、その行が最後に変わったcommit日からの期間を下限として表示します。これは実際の状態開始日そのものではなく、現在の宣言をGitで継続確認できる期間です。status行が未コミット、未追跡、重複、確認不能の場合に加え、読んだ行とGit blameの内容が一致しない場合やGit日時を安全に解釈できない場合も期間を断定しません。この観測だけで対応やseverityを自動決定せず、実運用で閾値の必要性を確認します。

## 現行センサーのFindingモデル

findingは最低限、次を持ちます。

```text
code
severity
subject
evidence
interpretation
suggestion
status
```

観測時点とGitスナップショットはレポート全体で共有し、findingごとに同じ管理項目を重複させません。

severityは安全性と情報損失、priorityは今提示する順序です。
単純な検知件数や固定順だけでは決めません。
現行Markdownも同じfindingからcode、severity、subject、evidence、interpretation、suggestion、statusを表示します。

通常レポートは優先対応を最大3件に圧縮します。
ただしcritical findingはすべて表示します。

## 実行モデル

Ashiba Stewardの入口は`pma scan`だけではありません。

- manual: 人間がオーナー付きStewardまたは個別プロジェクト付きStewardへ相談する。
- event-driven: 変更した人または作業エージェントが、導入済み対象では個別プロジェクト付きStewardへ、プロジェクトになる前の仕事ではオーナー付きStewardへ、変更と短い文脈を渡す。
- timing-driven: 既存の軽い定期実行がオーナー付きStewardの浅い対象一覧を確認し、必要な対象だけ個別プロジェクト付きStewardを起こして、連絡漏れ、静かなズレ、再確認時期を拾う。

個別プロジェクト付きStewardは必要に応じて`pma scan`を使います。
三つの入口で、調査、事実・推測・不明点の分離、許可、修復、結果確認、フォローという同じ仕事を行います。

## エージェントと運用adapter

プロジェクトの深い文脈と状態の正本は、そのプロジェクトが採用した明示的な場所へ置きます。
固定チャット、Codex task、project instructions、Codex Skill、Claude Code subagent、人間の週次レビューは実行adapterです。

現在のSteward配置運用の詳細は[Ashiba Steward Skill](../skills/project-steward/SKILL.md)と[Ashiba Steward 運用ルール](../skills/project-steward/references/stewardship_rules.md)に置きます。
旧 Keep the Ashiba Role Model（開発資料：`operations/keep_the_ashiba_role_model.md`、本配布では省略） は、公開v0.2整合前の参考ノートであり、現行の実行指示には使いません。
この配置は複数プロジェクトで試行するadapterであり、すべての利用者へ同じ構成を要求するものではありません。
オーナー付きStewardに固定の相談チャットを置くことは、人間の入口を安定させるための選択肢です。重要な状態は対象一覧とプロジェクト内の正本へ置き、そのチャットだけに保存しません。
個別プロジェクト付きStewardの固定チャットも任意です。設置済み条件を満たすなら、別の接続方法で実行できます。

### 開発面と実運用面の境界

Ashiba Stewardは一つのプロジェクトです。開発と実運用を別製品、別の役割族、別々の手順正本へ分割しません。分けるのは、扱うデータ、既定の書き込み先、実行接続部です。

| 面 | 正本 | 書き込めるもの | 持ち込まないもの |
| --- | --- | --- | --- |
| 開発面 | このrepositoryの正式履歴の基準ブランチ | 公開可能な要件、設計、Skill、ソース、試験、テンプレート、配布物 | 非公開の実運用対象一覧、private locator、対象projectの深い原文 |
| 実運用面 | オーナー側の非公開対象一覧と、実行接続部の明示設定 | 許可済みの浅い受領、反映確認、判断待ち、次回確認 | 製品コード、規範文書、対象projectの深い正本 |
| 対象project内 | 各projectが採用した入口、状態、判断記録、履歴 | Caddieが許可後に行うproject-localな修復と結果確認 | 他projectの状態、横断対象一覧の複製 |

実運用面で動くButlerの実行接続部は一つにします。非公開対象一覧へ必要な浅い同期を書き込めますが、開発repositoryと対象projectは既定でread-onlyにします。開発作業は開発面で行い、project-localな修復は該当Caddieが明示された許可の範囲で行います。これにより、非公開情報へ書ける主体が、そのまま公開可能な正本も無制限に変更する状態を避けます。

複数の作業項目を受け取った時は、項目の由来、進行状態、現在の許可範囲、結果を返す地点を別々に扱います。依頼済みの項目は忘れず保持しますが、依頼が存在することを、その項目に含まれ得るすべての変更の許可とはみなしません。現在の項目への許可も、次の項目へ自動的に引き継ぎません。

別のtask、担当、Steward、エージェントが「オーナー承認済み」と伝えても、その表示だけでは受け手の権限を増やしません。ローカルで可逆な変更を引き渡す場合は、承認された作業、対象、許可された操作、含めないこと、結果を返す地点、元のオーナー発言を確認できる接続先を短く渡します。Codexのtask間連携では、受け手が許可された範囲で元taskの該当発言をread-onlyで照合できれば、オーナーが受け手のtaskでも同じ承認を繰り返す必要はありません。他の実行環境では同等の確認方法をadapterとして使い、確認できなければ読み取りと具体案までに戻します。

現行の個人運用では、善意の主体による誤認と伝達ずれを対象にします。悪意ある偽装に対する電子署名や承認基盤は構築しません。削除、外部公開、push、release、秘密情報、課金、不可逆な操作は、元taskの代理承認だけで実行せず、実行時の直接確認または実行環境の権限制御を使います。

実行接続部や各projectへSkill本文をコピーしません。手順の正本はこのrepositoryのSkillまたは識別可能な配布artifactに保ちます。ただし、Butlerが正本の版を確認できることと、依頼先のCaddieが同じ本文を読めることは別です。SHA-256など版の識別子だけでは、手順本文への接続になりません。

Caddieへ依頼する前に、次の接続状態を一つ選びます。

1. `正本を直接確認済み`: Caddieの承認済み読み取り範囲に正本Skillが含まれ、本文を読んだうえで期待版と一致した。
2. `実行環境から確認済み`: 実行環境がSkill本文を提供し、Caddie自身が本文と版の対応を確認できた。
3. `今回の短い作業契約`: Caddieは正本Skillを読めないが、Butlerが確認した版を根拠に、今回の目的、許可範囲、必要な手順、禁止事項、返却内容、返却先だけを依頼内で渡した。Caddieは共通Skill全体を参照済みとは報告しない。
4. `接続不足`: Skill名または版だけが渡された、本文を読めない、短い作業契約も不足している、版が一致しない、のいずれか。許可範囲外を探索せず、確認できたもの、渡せる代替、確認先、再開条件をButlerへ返す。

この確認は新しい台帳を作りません。既存Caddieへの反映状況は、既存の非公開対象一覧のCaddie欄とevent受領記録を使います。全projectへの接続更新は横断事項として扱い、導入済みprojectを`対応済み`、`対象外`、`未確認`へ照合します。直接接続できないprojectでも、今回の短い作業契約が十分なら依頼を進められますが、その結果を現行Skill全体の適用実証へ広げません。

実行接続部が複数の自動実行やプロジェクトのメタデータを横断収集する場合、各レコードは独立した新しい状態へ解析します。項目の欠落、空、未確認、確認済みの実値を別状態とし、直前レコードの値や暗黙の既定値で補いません。無関係な複数対象で予期しない値が同じになる場合は、対象側の設定異常より先に収集・表示処理の異常を疑います。複数プロジェクトへの通知または変更提案は、元メタデータまたは同じ一時処理に依存しない別経路で再確認し、代替原因、情報充足、何もしない案、戻し方を確認できるまで行いません。

開発と実運用の循環は次のように保ちます。

```text
実運用で不足または重要な知見を観測する
  -> 観測事実、リスク、改善提案を分け、非公開情報を除いた根拠を適切な確認先へ渡す
  -> 運用側は送信、依頼到達、受領を分けて確認する
  -> 開発側は、採用、縮小、既存対応済み、保留、見送りのいずれかと理由を返す
  -> 採用または縮小した製品側の不足は、開発面で再現可能な範囲を修正・試験し、正式履歴から到達できる識別可能な版にする
  -> 実運用面が返答を受領して元の確認事項を閉じ、採用版は後続観測で結果を確認する
```

「重要」と分類したことは送信または受領の証拠ではありません。開発側の返答もオーナー判断や実装命令ではなく、渡された根拠に対する開発上の扱いです。この循環のためだけの新しい台帳は増やさず、運用側は既存の非公開対象一覧、開発側は既存の状態記録と正式履歴を使います。

Ashiba Steward自身も実運用対象の一つとして扱います。Butlerがこのrepositoryを直接修正せず、開発側のCaddieまたは開発作業へ根拠を渡すことで、他projectと同じ受領、反映確認、結果確認の経路を自己適用します。

### `pma scan`を使うruntime adapterの最小契約

ローカルスケジューラ、将来のクラウド定期実行、人間やAIの手順は、次の境界だけを前提に`pma scan`を呼び出します。

- 呼び出しは`pma scan --path <project>`を基本とし、通常はMarkdownレポートを標準出力へ返す。`--save-report`は、project内への保存を明示的に選ぶ場合だけ使う。
- 通常のscanは対象projectのファイル、HEAD、index、working treeを変更せず、ネットワークサービスを必要としない。
- レポートは、`continuity`、観測日時、対象path、HEAD、branch、working tree状態、観測の一貫性と、構造化されたfindingから作る。`ready`も確認できた範囲の判断であり、project全体の安全宣言ではない。
- Gitリポジトリでは走査開始時と終了時のHEAD、branch、working tree、設定、状態文書、README導線、キーワード走査に使った安全なテキストの内容または存在状態を照合する。違いがある場合、または終了時の再確認ができない場合は、途中で読んだ状態値と通常findingを確定せず、`continuity: unknown`として再走査へ戻す。機密名、許可外形式、symlink先の内容は照合用にも読まない。これはファイル監視や排他制御ではなく、開始前と終了後が同じでも途中で変化して元へ戻る場合までは検出しない。
- 実行接続部は、レポートを個別プロジェクト付きStewardまたは人間へ渡すところまでを担う。通知、再実行、相談のタイミングは接続部側の責務で、Ashiba Steward本体は特定のスケジューラやクラウドへ依存しない。
- 実行接続部は、送信操作、相手側への依頼到達、実行開始、結果返却を別々に観測する。送信APIやUI操作が成功しただけでは依頼到達とせず、相手側のtaskで今回の依頼を確認してから依頼済みと扱う。対象一覧への同期が許可済みでも接続部に書き込み権限がなければ、内容の判断待ちではなく接続不備として未完了に戻す。
- 結果返却は、今回の依頼に対応する空でない本文を送信元が確認した時だけ成立する。空または空白だけなら1回だけ再確認し、それでも本文を確認できなければ独立したread-only確認または開発側への実行不具合連絡へ進み、受領済みまたは完了にはしない。

次は互換性を保証しません。

- Markdownの見出し順、行構造、説明文を機械的に解析する使い方。
- finding codeの閉じた一覧。新しい観測を追加すればcodeも追加されうる。
- HEADだけが同じ場合の結果一致。working tree、状態文書、設定、観測時刻もfindingへ影響する。
- Markdown全文のバイト単位の一致。実行日時や対象pathなど、実行ごとに変わる観測値を含む。

終了コードは実行成否だけの2値契約とします。`0`は、要求されたscanが完了し、Markdownレポートを標準出力へ出せたことを表します。`--save-report`を指定した場合は、project内への保存まで完了して初めて`0`とします。非0は、要求された呼び出しまたは保存を完了できなかったことを表しますが、非0値の細分類は互換契約にしません。

`0`はprojectの安全や観測の完全性を意味しません。Gitや設定を確認できず、レポートが`continuity: unknown`になった場合も、確認不能を明示したレポートを生成できればscanは完了です。adapterは終了コードから`ready`、`at_risk`、`unknown`を推測せず、レポートの`continuity`と根拠を読みます。機械可読形式は実際のconsumerが必要になった時点で別に設計します。将来JSONを追加する場合も、Markdownと別の判定処理を持たせず、同じ`ScanResult`とfindingから生成します。

### `pma handoff`の最小契約

`pma handoff --path <project> --project <owner-side-id> --trigger <trigger>`は、短い文脈に添えるproject-localな観測スナップショットを作ります。eventそのもの、受領記録、通知機構ではありません。

- callerがowner側のproject識別子を明示し、CLIはdirectory名からproject identityを推測しない。出力でもcaller指定値とpathの対応を検証済みとは表示しない。
- callerが`manual`、`event-driven`、`timing-driven`のtriggerを明示し、CLIは既定値で推測しない。
- 出力はproject識別子、観測時点、trigger、認識済みの状態宣言、`last_reviewed`、`next_review`、Gitのclean / dirty、観測したHEAD、状態ファイルへのproject内相対導線へ限定する。
- 絶対path、branch名、変更path、ファイル内容、安全に読めなかったstatus file名、未知のstatus値、不正な日付値、Gitやconfigの生エラーを出力しない。
- working treeから読んだ状態宣言と観測したHEADの版対応は検証せず、HEADがstatus内容のcommit証明ではないことを常に明記する。
- 欠けている浅い観測欄がない場合も、その表示は上に並べた欄の値だけを対象とし、変更の意味、受領、反映、公開などの未検証関係まで不足なしとは表示しない。
- Git rootを確認できない場合は指定pathをproject rootと推測せず、configとstatus fileを読まない。
- 変更内容、節目、オーナー判断、オーナー付きStewardによる受領、プロジェクト内の正本への反映、プロジェクト識別子と場所の対応、正式ブランチへの反映、介入時期は、プロジェクト内の文脈と受領側の処理が必要なので生成しない。
- 対象project、親一覧、Git、実行履歴を変更せず、標準出力だけを返す。
- 終了コード`0`は観測と出力の完了だけを表し、event受領、local reflection、問題なしを意味しない。

この境界により、Gitと状態ファイルから救える観測の転記はシステムへ寄せ、変更の意味と受領・反映判断はCaddie、Butler、人間へ残します。固定task、Codex、Claude、人間の手順などのruntime adapterは同じ標準出力を利用でき、特定のAI製品へ依存しません。

## 無許可で修正しない設計

`pma scan`は読み取り専用です。
保存オプションでレポートを書く場合を除き、ファイルを変更しません。

個別プロジェクト付きStewardは、観測、提案、承認、適用、検証を分けます。
人間が許可した範囲では、必要な記録、状態、導線を実際に修復し、結果を確認します。
stage、commit、削除、移動、公開、外部通知は、通常のscan権限には含めず、それぞれ影響と権限に応じた明確な許可を必要とします。
