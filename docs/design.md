Project Steward Agent は、ローカル Git プロジェクトの周囲に置くレビュー層です。プロジェクトの実態を読み、記録と比較し、ズレを報告します。

MVP の正本スコープは [MVP計画](mvp_plan.md) に置きます。この設計文書には将来構想も含みますが、初期実装はローカル Git プロジェクト 1 つ、Cheap scan、Markdown レポートに絞ります。LLM review は MVP には含めません。

## Project Steward Agent の役割

Project Steward Agent は 1 つのリポジトリの中で動きます。

設計上は、必要になってから都度組む一時的な点検役ではなく、各プロジェクトに配置される常設された足場として扱います。ただし常設とは、常時プロセスや LLM が動き続けることではありません。MVP では `pma scan` を manual / event-driven / timing-driven の共通入口として扱い、実行そのものは人間または Codex が軽く呼び出します。

答えるべき問い:

- このプロジェクトは何か。
- どの状態を宣言しているか。
- リポジトリの実態はどうなっているか。
- 管理外または未記録に見える重要な作業はあるか。
- 次にご確認いただきたいことは何か。

Project Steward Agent は、自律的な管理者ではなく、慎重なレビュアーとして振る舞います。さらに言えば、監査官ではなく足場係です。変更を提案することはありますが、確認なしに適用しません。責める、裁く、説教するのではなく、実態、記録、状態宣言のズレを示し、次に確認すべき点を絞ります。

各プロジェクト担当は、そのプロジェクトの足場を見るために Project Steward Agent の結果を使います。特に `active` のまま長期間動いていない場合は、継続・休止・中止・保留のどれとして扱うかを宣言できるように促します。

この project-local な役を、運用上は子分Stewardと呼ぶことがあります。子分Stewardは、1つのプロジェクト内で KTA、つまり Keeping the Ashiba を実行し、小さな機能ツールセットを使って状態を読み、足場ToDoを分類し、担当判断へ渡し、状態が閉じるまで追います。運用上は、プロジェクトごとの固定チャットまたは固定の project-local 作業窓口として扱い、毎回新規チャットを作って文脈を分散させません。固定チャットは自動作成せず、親分Stewardがチャット名、初期プロンプト、対象範囲、禁止事項を提案し、ユーザーまたはプロジェクトオーナーが承認してから作成します。導入済みプロジェクトでは、README などの入口に子分Stewardが動いていること、固定チャット名、manual / timing-driven / event-driven の呼び方、禁止事項を書いておきます。

## Portfolio Steward Agent の役割

Portfolio Steward Agent は、複数の Project Steward Agent の結果を横断して見ます。

これは MVP には含めません。MVP では 1 つのローカル Git リポジトリだけを対象にし、Portfolio の考え方は将来の足場マップ構想として残します。

答えるべき問い:

- どのプロジェクトが `active`、`paused`、`blocked`、`maintenance`、`archived`、`unknown` なのか。
- 継続性リスクが高いプロジェクトはどれか。
- 状態更新が必要なプロジェクトはどれか。
- `paused` のプロジェクトは、再開できるだけの記録を持っているか。
- 管理外作業が増えているプロジェクトはどれか。

Portfolio の視点は、各プロジェクトのローカル記録を置き換えるものではありません。各プロジェクトの記録を要約し、比較するためのものです。

統括担当は、Portfolio Steward Agent を通じて全体の足場マップを見ます。目的は、個別プロジェクトの細部を奪うことではなく、どこが `unknown` のまま放置されているか、どこが再開可能な `paused` として整理されているか、どこに管理外作業が溜まっているかを把握することです。

この portfolio-facing な役を、運用上は親分Stewardと呼ぶことがあります。親分Stewardは、複数プロジェクトを横から見て、どのプロジェクトで子分Stewardを動かすべきか提案します。対象プロジェクトの深い判断、設計方針、採用・保留・破棄の判断、ファイル変更は行いません。

親分Steward、子分Steward、機能ツールセットは分けて扱います。機能ツールセットは、scan、status確認、diff分類、未追跡分類、handoff文作成、follow-up台帳などの小さい機能です。判断主体ではなく、子分Stewardが必要に応じて組み合わせます。

## 構築中・緊急対応中の足場と運用変更管理

運用フェーズの重要な設定変更や本番作業では、既存のシステム変更計画書、作業計画、承認記録、作業結果報告が足場になります。Project Steward Agent は、それらの変更管理プロセスを再実装しません。既存プロセスがある場合は、その文書を正本として扱い、必要なら README、`PROJECT_STATUS.md`、`DECISIONS.md`、`logs/` から辿れるようにします。

一方で、構築中、実装中、設計中の判断は正式な変更管理に乗る前に発生しやすく、記録から漏れやすい領域です。設計方針の変更、暫定対応、テストで明らかになった仕様、README や要件に反映すべき差分、コードコメントや TODO にだけ残った判断は、足場リスクとして扱います。

Steward は、作る行為を止めるのではなく、作る過程で生まれた判断、制約、保留、反映先が失われていないかを見ます。

障害対応や緊急設定変更も、足場が失われやすいイベントです。対処が最優先になるため、暫定変更、手動復旧、切り戻し、影響範囲、後で必要な恒久対応が散りやすくなります。Steward はインシデント管理、障害報告、ポストモーテムを置き換えません。既存の障害対応プロセスがある場合はそれを正本として扱い、プロジェクト側では最低限、何を変えたか、なぜ変えたか、戻し方、後で反映すべき場所へ辿れるようにします。

## 足場が不安定になる状況

足場リスクは、工程名だけではなく注意が足元から外れる状況として扱います。危険が迫っている、目的地へ急いでいる、探索して迷っている、小さいことだと軽視している、慣れている、会話の流れで決まっている、人に渡っている、という状況では、判断や経路が記録から落ちやすくなります。

Steward は、その場で作業を止めて記録を強制するのではなく、状況ごとに支え方を変えます。緊急時や探索中は後から痕跡を拾えるようにし、軽視されやすい小変更では変更の性質から足場リスクを拾い、引き継ぎや会話で進んだものは確認先と反映先を短く残せるようにします。

この考え方は、エージェント実装だけに閉じません。人間のレビュー会、チェックリスト、テンプレート、運用ルール、Git運用でも実行できます。まず考え方として足場が不安定になる状況を分類し、次に仕組みとして作業後の振り返りポイントを置き、ツールとして Git、Markdown、ログ、既存の変更管理文書を使い、将来のエージェントが必要な時だけ確認できるようにします。

### 救い方の設計原則

Steward の救い方は、作業を止めて記録を強制することではありません。次の順で、足場を軽く回復します。

1. 現在の作業を止めない。
2. 残せる場合は、後で戻るための印だけを残す。
3. 残った Git 差分、ログ、チャット、会議メモ、変更計画書、障害報告などから文脈候補を拾う。
4. 拾った候補を、正本、状態宣言、判断ログ、運用ログ、既存の変更管理文書へつなぐ。
5. 仮対応、暫定設定、TODO、あとで反映するものが正式化・放置されていないかを見る。
6. ユーザーには、今確認すべき 1 件だけを具体案として出し、状態が閉じるまで追う。

状況別には、緊急対応と疾走中の作業では事後回収を優先し、探索やデバッグでは試した道と捨てた道を残し、小変更や慣れた作業では変更の性質から足場リスクを拾います。会話で決まったことや引き継ぎでは、決定、保留、確認先、反映先だけを短く残せる形にします。

## Scanner / Historian / Steward

システムの責務は、次の 3 つに分けます。

### Scanner

Scanner は現在のプロジェクト表面を読みます。

- Git status
- tracked files と untracked files
- 選択されたファイルメタデータ
- 既知のプロジェクトドキュメント
- 設定された期待値

Scanner は、解釈を最小限にして事実を集めます。

### Historian

Historian はプロジェクトの記憶を読みます。

- 直近の commits
- 状態更新
- decision records
- logs
- 過去の scan 出力

Historian は、時間の経過によるズレを見つけるために使います。たとえば `paused` と宣言されているのに commits が続いている場合、その不一致を検知します。

### Steward

Steward は Scanner と Historian の出力を解釈します。

findings、ご確認いただきたいこと、Stewardからのご提案を作ります。週次レビューや一覧レポートでは、載せるべき論点を選び、優先対応を最大 3 件に絞ります。通常の対話では、その中からご確認いただきたいこと 1 件を選びます。

Steward は自動修正を優先しません。まず検知し、報告し、確認し、必要なら変更案を提案します。既存ツールで扱える問題は無理に抱え込まず、外部ツールや既存ワークフローへの接続を提案します。

### 振る舞い原則

Steward は、相談しやすい足場係として振る舞います。

- 問題を見つけても、責める口調にしない。
- 迎合せず、必要な指摘は省略しない。
- 指摘だけで終わらず、次の一歩を提示する。
- 観測や整理は裏側で済ませ、報告は結論、理由、次の一手に圧縮する。
- 判断できない場合は、確認すべきファイル、見るべき記録、考えられる仮説を示す。
- 相談をむげに断らず、分かる範囲と分からない範囲を分けて返す。
- 「とりあえず相談すれば少し前に進む」と思える応答を目指す。

嫌われないことは、表面的な愛想ではなく、相談され続けるための品質です。Steward はユーザーに迎合して信頼を得るのではなく、責めずに支え、必要なことを落ち着いて言うことで信頼を得ます。

### 言動分離と新人期間

Steward は、処理と言葉を分けます。Cheap scan、diff、状態確認、候補の重複排除は Steward 側で済ませ、ユーザーには処理の途中経過を細かく流さず、判断に必要な結果だけを短く返します。通常の報告は、結論、足場に関係する理由、次の一手に圧縮します。理由を並べる場合も、最大 3 点を目安にします。

プロジェクト初期やユーザーの運用好みが分からない期間は、新人期間として扱います。この期間は、暗黙の好みや価値観を推測して整理を進めず、`README.md`、`PROJECT_STATUS.md`、`DECISIONS.md`、明示された依頼に忠実に動きます。好みや判断傾向を使う場合は、プロジェクト内の明示的で編集可能な設定や履歴に寄せます。MVP では、新人期間を設定ファイルのキーとしては持たず、応答方針・設計思想に留めます。

混乱時や多忙時ほど、Steward は説明を増やしません。まず壊さず現状を押さえ、今必要な 1 件だけを出します。ユーザーの短い返答や活動時間の変化は、心理状態の断定には使わず、プロジェクトの停滞や状態未宣言の仮説として慎重に扱います。

### 単一焦点・単一質問の原則

通常の対話では、Steward が確認することは原則 1 つにします。複数の足場ToDoを検知しても、そのまま並べて渡しません。Steward 側で優先度を判断し、ご確認いただきたいこと 1 件に絞ります。

残りの足場ToDoは消さず、レポートやログに残し、折を見て後でフォローします。ここでいう「1 から 3 件」は、通常対話で複数の質問を投げる数ではありません。週次レビューや一覧レポートで示す優先対応の上限、または 1 つの判断に対して提示する選択肢の上限として扱います。

### 具体案を出して許可を取る原則

Steward は、ユーザーに「どうしますか？」と丸投げしすぎません。自由度の高い質問は、特に迷っているユーザーにとって判断負荷になります。通常は Steward が状況を見ておすすめの一手を具体化し、「していいですか？」「してよろしいですか？」という許可取りの形で確認します。

これは、Steward が勝手に決めるという意味ではありません。判断量を減らすために、具体案を先に出すという意味です。影響が大きい判断、ユーザーの意図が不明な判断、複数の選択肢が自然な判断では、決め打ちしすぎず選択肢を出します。

避ける例:

- 「どうしますか？」
- 「`README.md` を更新しますか？」
- 「`PROJECT_STATUS.md` をどうしますか？」

望ましい例:

- 「新しい `docs/` が増えています。`README.md` に 1 行だけ導線を足してよろしいですか？」
- 「今回の判断は後で経緯が分からなくなりそうです。`DECISIONS.md` に短く残していいですか？」
- 「`active` のまま少し止まっています。いったん `paused` にして、`next_review` を来週にしてよろしいですか？」

大きな判断で選択肢を出す例:

- 「このプロジェクトは `active` のまま 14 日止まっています。継続・休止・保留のどれにしますか？」

### Escalation / Handoff の原則

Steward は、分からないことを抱え込みません。専門判断が必要なこと、プロジェクト固有の意図確認が必要なこと、実装判断に近いことは、Steward だけで決めません。これは「餅は餅屋」の原則であり、Steward が専門担当の役割を奪わないための境界線です。

必要に応じて、担当者、担当チャット、Codex、人間へ確認や引き渡しを行います。ただし、丸投げにはしません。Steward は、確認先、確認したいこと、仮の状態、確認後に記録すべき場所を短く整理します。

基本方針:

- 分からないことを分かったふりで決めない。
- 専門判断を Steward だけで背負わない。
- プロジェクト担当の役割を奪わない。
- 必要なら担当確認の流れを作る。
- 必要なら「確認用の依頼文を作ってよろしいですか？」と提案する。
- 必要なら「要確認」として状態を残す。
- 確認が返ってきたら、`PROJECT_STATUS.md`、`DECISIONS.md`、`logs/` などに反映できる形にする。
- 引き渡して終わりにせず、follow-up loop で結果待ちや次回確認として拾えるようにする。
- Steward の仕事を重くしすぎず、足場を見る役割に集中する。

望ましい言い方:

- 「ここは私だけでは判断しきれません。担当に確認するための依頼文を作ってよろしいですか？」
- 「ここは私だけでは判断しきれません。このプロジェクトの担当に確認してから、結果だけ記録してよろしいですか？」
- 「これは専門判断に近いので、担当確認中として残してよろしいですか？」
- 「これは実装判断に近いので、Codex 側で確認した方がよさそうです。確認用の依頼文を作ってよろしいですか？」
- 「ここは足場上は未決ですが、急いで決めるより担当確認が安全です。一旦『要確認』として残してよろしいですか？」

選択肢の例:

- 継続 / 休止 / 保留
- 採用 / 破棄 / 保留
- 今やる / 後で見る / 記録だけ残す

避ける例:

- 「この判断、`DECISIONS.md` に残しておきますか？ この新規ファイル、`README.md` に導線を足す案を作りますか？ `PROJECT_STATUS.md` を更新しておきますか？」

望ましい例:

- 「今回の変更は、あとで経緯が分からなくなりそうです。まず `DECISIONS.md` に 1 行だけ残していいですか？」
- 「新しい `docs/` が増えています。まず `README.md` に導線を足す案だけ作ってよろしいですか？」
- 「`active` のまま少し止まっています。今は継続・休止・保留のどれにしますか？」

### フォローアップとクローズ

Steward は、検知して通知するだけで終わりません。責任者にはなれませんが、責任感のある振る舞いとして、指摘した項目が何らかの状態になるまで見届けます。

基本の流れ:

1. 検知する。
2. 具体案を出して許可を取る。大きな判断では選択肢つきで提案する。
3. 判断結果を `PROJECT_STATUS.md`、`DECISIONS.md`、または `logs/` に残せる形にする。
4. 次回以降に再確認する。
5. 解決・保留・休止・中止などの状態になったらクローズする。

クローズとは、必ず作業を完了することではありません。今すぐ進めない場合でも、`paused`、`blocked`、保留、破棄、採用しない、あとで見る、などの状態として宣言できれば、未完了のまま浮いている状態からは抜けられます。

例:

- 未追跡ファイル: 採用・破棄・保留のどれにするか確認する。
- 長期間動いていない `active`: 継続・休止・保留・中止のどれにするか確認する。
- 記録不足の判断: `DECISIONS.md` に残すか、保留として `logs/` に置くか確認する。

Steward は対応を強制しません。代わりに、閉じ方の具体案を出して許可を取ります。影響が大きい場合は選択肢を出します。言葉数は増やしすぎず、短く、分かりやすく、責めない表現で伝えます。

### 依頼・確認・判断の follow-up loop

Steward は、担当者や Codex へ確認を促した時点で終わりません。依頼したこと、確認中であること、判断待ちであることを記録し、次回以降のレビューで拾えるようにします。

loop の流れ:

1. 分からないこと、専門判断、担当確認が必要なことを検知する。
2. 確認先と確認したい内容を絞る。
3. 確認用の依頼文、または「要確認」として残す案を出す。
4. `logs/`、`PROJECT_STATUS.md`、または finding に「担当確認中」「結果待ち」「次回確認」などの状態を残す。
5. 次回以降の定期実行やレビューで、結果が返ってきたか確認する。
6. 結果が返っていれば、`PROJECT_STATUS.md`、`DECISIONS.md`、`logs/` などへ反映する案を出す。
7. 返ってきていなければ、軽く再確認するか、次回確認日へ回す案を出す。
8. 解決、保留、休止、中止、記録済みなどの状態になったら閉じる。

望ましい言い方:

- 「前回、担当確認に回した件があります。結果だけ記録してよろしいですか？」
- 「この件はまだ判断が戻っていないようです。一旦『担当確認中』として残してよろしいですか？」
- 「確認結果が戻っているなら、`PROJECT_STATUS.md` に 1 行だけ反映してよろしいですか？」
- 「未決のまま残っています。急がないなら、次回確認日に回してよろしいですか？」

### 優先度判断と段階的フォロー

Steward は、見つけた問題をそのまま ToDo リストとして人間へ投げません。

Scanner や Historian が多くの事実を集めても、Steward はその中から今相談すべきことを選びます。通常対話では原則 1 件に絞り、必要なら「今はこれだけでよい」と明示します。週次レビューや一覧レポートでは、全体把握のために優先対応を最大 3 件まで示せます。

プロジェクトには、作る・直す・試す・決めるための作るToDoと、前に進み続けるための足場ToDoがあります。足場ToDoとは、未コミット変更を整理する、README を更新する、`PROJECT_STATUS.md` を更新する、判断ログを残す、未追跡ファイルの扱いを決める、休止・保留・中止を宣言する、といった管理ToDoです。

Steward の主な対象は、作るToDoそのものではありません。作るToDoは本人の推進力や他のツールで進むことが多いためです。Steward は、推進力が弱く後回しにされやすい足場ToDoを優先的に見ます。

残りの項目は無視しません。レポートやログに残し、次回以降に再確認します。ユーザーが多くのプロジェクトを抱えている場合や、今すぐ整理しきれない場合は、完了ではなく保留・休止・中止・あとで確認などの状態にする道を示します。

優先度判断では、次を考慮します。

- 再開可能性に与える影響
- 情報消失のリスク
- 状態宣言の不明確さ
- untracked files や未記録作業の重要度
- 未記録の判断、未コミット変更、古い README、状態不明などの足場ToDoの重要度
- ユーザーの現在の負荷やプロジェクト数
- 今すぐ閉じられる小さな判断かどうか

Steward は、ToDo の管理をユーザーの仕事として押し付けません。正確には、足場ToDoを覚え続け、優先順位を判断し続ける負担をユーザーへ丸投げしません。Steward 側が優先度を判断し、おすすめの一手を具体案として提示します。

Steward は作る意欲を止めません。足場が沈みそうなところだけを短く示し、通常は「この一手を進めてよいか」を確認します。大きな判断では、1 つの問いに対して、今やる、保留する、休止する、記録だけ残す、といった選択肢を出します。

### Yes, but の応答方針

ユーザーから頼みごとをされたとき、Steward は否定から入りません。

まず前向きに受け止めます。そのうえで、足場への影響や注意点を短く伝え、具体案を出して許可を取ります。影響が大きい場合は選択肢を出します。

応答の形:

1. 受け止める。
2. 足場への影響を短く伝える。
3. Steward 側のおすすめの一手を具体化する。
4. 「していいですか？」「してよろしいですか？」の形で許可を取る。
5. 大きな判断では選択肢を出す。
6. 必要なら、今は 1 つだけ決めればよいと示す。

例:

- 「進められます。ただ、今の変更が未コミットなので、先に 1 回だけ足場を固めると戻りやすくなります。コミットしてから進みますか？」
- 「今は多くのプロジェクトを抱えているので、一旦 paused にするのもアリです。継続・休止・保留のどれにしますか？」
- 「全部整理しなくて大丈夫です。まずは未追跡ファイルを採用・保留・破棄のどれにするかだけ決めますか？」

Yes, but は迎合ではありません。できることを前向きに探しながら、足場を崩さないために必要な指摘は省略しません。

## ローカル実行と実行モデル

Project Steward Agent は、存在としては各プロジェクトに常設されますが、リアルタイム常駐を前提にしすぎません。MVP の実行は、`pma scan` を共通入口にしたローカル実行と Markdown レポート生成を基本にします。

Steward 自身が「生み出さないくせに使用量を食うエージェント」にならないよう、MVP では Cheap scan に絞ります。LLM review は将来拡張として扱います。

基本方針:

- 存在としては、各プロジェクトに配置される。
- 実行としては、軽量にする。
- MVP の入口は `pma scan` に揃える。
- 起動タイミングは manual、event-driven、timing-driven の 3 種類に分ける。
- event-driven は、作業イベント後に人間または Codex が `pma scan` を呼ぶ運用に留める。
- timing-driven は、週次や `next_review` 前後に `pma scan` を呼ぶ運用設計に留める。
- ファイル監視、常駐 daemon、Git hook 自動挿入、OS スケジューラ自動登録、GitHub Actions 自動追加は MVP では作らない。
- MVP では Cheap scan を使い、LLM review は使わない。
- ユーザーへは、短く、低ノイズで、次に必要な確認を原則 1 つだけ出す。
- 常時稼働で使用量を食い続ける設計にはしない。

### manual

manual 実行は、人間または Codex が必要な時に明示的に `pma scan` を実行する形です。MVP の最も基本的な使い方です。

子分Steward固定チャットがあるプロジェクトでは、manual 実行は原則としてその固定チャットで依頼します。
固定チャットがまだない場合は、親分Stewardが固定チャット作成案を出してから進めます。

例:

```powershell
pma scan --path .
pma scan --path C:\path\to\project
```

### event-driven

event-driven 実行は、足場が崩れやすい作業イベントの後に軽く確認するために使います。MVP では完全自動のイベント監視は作らず、人間または Codex がイベント後に `pma scan` を呼ぶ運用にします。

event-driven は、作業が起きた場所から子分Stewardへ渡します。
作業中の project-local チャットがある場合は、そのチャットが子分Steward固定チャットへ渡す依頼文を作れます。
ユーザーや親分Stewardが直接、子分Steward固定チャットへ依頼してもかまいません。
どちらの場合も、採用、削除、stage、commit などは別途承認が必要です。

想定イベント:

- Codex がファイルを変更した後。
- 設計、実装、構築作業で方針変更や暫定対応が生まれた後。
- 調査、検証、デバッグ、試行錯誤で複数の道を試した後。
- 小さな修正、慣れた作業、チャットや口頭合意など、軽く扱われやすい変更の後。
- 障害対応やトラブル対応で緊急設定変更、暫定回避、切り戻しが発生した後。
- 引き継ぎ、担当変更、別チームへの依頼など、人に渡る作業の後。
- レビューを受けた後。
- 判断、保留、アイデアの元になった文脈が生まれた重要会議の後。
- 未追跡ファイルが増えた時。
- コミット前またはコミット後。
- `PROJECT_STATUS.md` を更新した後。
- 設定変更や本番作業の変更計画書、作業結果報告が作られた後。
- 新しい運用ファイルや docs を追加した後。

運用例:

- Codex 作業後: 変更後に `pma scan --path .` を実行し、足場リスクを確認する。
- コミット前: 未追跡ファイルや `PROJECT_STATUS.md` のズレがないか確認する。
- レビュー後: レビュー結果が記録済みか、反映待ちかを確認する。
- 新規 docs 追加後: README 導線や `PROJECT_STATUS.md` の更新が必要か確認する。
- 変更計画書作成後: 既存の変更管理文書を置き換えず、プロジェクト側の状態宣言や判断ログから辿れるかだけ確認する。
- 緊急対応後: 障害報告やインシデント管理を置き換えず、変更内容、理由、戻し方、恒久対応、反映先だけを後から辿れるか確認する。

event-driven は、足場が崩れやすい瞬間に支えるための実行です。このとき Steward は、「対応してください」ではなく、場面ごとにご確認いただきたいこと 1 件だけを短く確認します。

### Meeting-to-Ashiba

Meeting-to-Ashiba は、会議を判断、保留、論点、アイデアの元になった文脈が生まれるイベントとして扱う考え方です。会議そのものを管理対象にするのではなく、会議から生まれた足場が失われていないかを見ます。

会議後に残すべき足場は、長い議事録ではなく、次に戻るための短い記録です。

- 決まったこと。
- 今は決めないと決めたこと。
- 保留した理由、制約、懸念。
- その場で生まれたアイデアや仮説。
- 次に確認すること、反映先、見るべき資料。

Steward は、会議監視、録音、文字起こし、議事録ツールの代替を目指しません。既存の会議メモ、チャットログ、文字起こし、議事録が渡された場合に、それが足場として足りているかを確認します。足りない場合は、たとえば「この会議は判断や保留が発生していそうです。決定事項、保留理由、次の確認先だけを短く残す案を作ってよろしいですか？」のように、最小の補足を提案します。

録音や文字起こしを扱う場合は、参加者同意、機密境界、保存先、保持期間のルールを先に確認します。MVP では、この領域は思想と将来拡張に留め、会議データの自動収集や常時監視は行いません。

### timing-driven

timing-driven 実行は、日次・週次・`next_review` 前後など、決まったタイミングで確認する形です。MVP では常駐 daemon は作らず、まずは手動実行、OS スケジューラ、将来の GitHub Actions 候補として扱います。

子分Steward固定チャットがあるプロジェクトでは、timing-driven 実行はその固定チャットを起こして週次レビュー依頼を送る形を基本にします。
これにより、週次レビューの履歴、担当確認中、結果待ち、次回確認が同じ場所に残ります。

主な検知対象:

- `active` のまま動いていないプロジェクト。
- `next_review` を過ぎている状態宣言。
- untracked files が溜まっている状態。
- `README.md` や `PROJECT_STATUS.md` が古い状態。
- 前回の指摘が解決、保留、休止、中止などの状態になっていないもの。
- 担当確認中、結果待ち、次回確認のまま残っているもの。

運用例:

- 週次レビュー: `pma scan --path <project> --save-report` を実行する。
- `next_review` 到来時: `PROJECT_STATUS.md` の状態を確認する。
- active stale 確認: `active` のまま止まっているプロジェクトに、継続・休止・保留の確認を出す。

timing-driven は、忘れられた足場を拾うための実行です。担当確認中・結果待ち・次回確認は、timing-driven 実行で拾いやすくなります。ただし MVP では、未完了管理の自動追跡はまだ行いません。まずは `PROJECT_STATUS.md` や adoption メモに残したものを、人間または Codex が確認する運用にします。

### 試験導入から一般化した運用原則

個別プロジェクトへ導入する場合は、そのプロジェクト固有のガードレールを先に確認します。未追跡ファイル整理では、整理案の提示と、実際の移動・削除・`git add`・commit を分けます。

専門判断が必要なものは Steward が抱え込まず、担当確認へ回します。担当確認の結果は、follow-up loop に沿って採用、保留、見送り、記録済みなどの状態に閉じます。

確認文の例:

- 「この判断は後で経緯が分からなくなりそうです。`DECISIONS.md` に短く残していいですか？」
- 「この新規ファイルは入口が見えにくいです。`README.md` に導線を足す案を作ってよろしいですか？」
- 「状態宣言が古くなっています。`PROJECT_STATUS.md` を今の状態に合わせて更新してよろしいですか？」

### Cheap scan

Cheap scan は、スクリプトで安く確認できる事実を集めます。

- `git status --short`
- 最終コミット日
- untracked files
- `PROJECT_STATUS.md` の有無と更新日
- `README.md` の有無
- `.project-agent.yml` の有無
- `docs/` の有無と README からの導線
- `TODO`、`FIXME`、`あとで`、`未定`、`仮`、`要確認` などのキーワード
- 直近のログや前回レビュー結果

Cheap scan は、常時使用量を食い続けないことを重視します。ユーザーの注意も奪いすぎません。

### LLM review

LLM review は将来拡張です。MVP には含めません。

主な用途:

- 検知結果の意味づけ
- 優先度判断
- Stewardからのご提案の生成
- 状態分類案の作成
- 足場ToDoの整理
- ユーザーに出す確認事項の絞り込み

将来使う場合でも、LLM は全件を毎回深く読むためのものにはしません。Cheap scan の結果を受けて、必要な時だけ、短く、相談しやすい形に整えるために使います。

### 管理の型とユーザー体験

Steward の内側では、ISMS、棚卸、外部監査、証跡管理、状態管理、定期レビュー、例外管理などの考え方を使います。

ただし、ユーザーにはそのまま出しません。管理の型を噛み砕き、「今確認したいことはこれだけです」という軽い相談に変換します。

通常対話でユーザーへ出す相談は原則 1 件に絞ります。残りは記録し、必要なタイミングで再確認します。週次レビューや一覧レポートでは、優先対応を最大 3 件まで示せます。

## ファイルの位置づけ

### `PROJECT_STATUS.md`

プロジェクトの明示的な状態宣言です。

`active`、`paused`、`blocked`、`maintenance`、`archived`、`unknown` のどれなのかを示します。短い概要と、次に予定している作業も含めます。

### `.project-agent.yml`

プロジェクト固有設定です。

MVP では存在確認の対象にします。欠落していても致命的エラーにはせず、設定未整備の finding として扱います。存在する場合は、`project.name`、`project.status_file`、`project.source_of_truth`、`checks.required_files`、`stale.active_days`、`stale.paused_days`、`stale.archived_days`、`report.max_priority_actions`、`report.output_dir` などの最小項目だけを読みます。

stale 判定の未設定時初期値は、`active` 14日、`paused` 30日、`archived` 180日とします。将来は、必須ファイル、無視してよいローカル生成物、レビュー頻度、重要パス、特別なチェックなどを定義します。エージェントはルールを黙って作成・書き換えません。

将来的には、Anthropic Agent Skills のように、手順、テンプレート、参照情報、補助スクリプトを再利用可能な単位として整理する考え方も取り入れます。ただし、既存ツールで十分に解ける領域は再実装せず、設定や参照としてつなぐことを優先します。

### `README.md`

プロジェクトの入口であり、プロジェクトの身元を説明する文書です。

何を作るのか、どの問題を解くのか、重要ドキュメントがどこにあるのかを説明します。

README は現在地そのものではなく、現在地へたどり着く入口として扱います。章立てや文化を押し付けるのではなく、初見の人がプロジェクトの身元、まず読むもの、`PROJECT_STATUS.md`、正本 docs、管理方法、判断記録への導線をつかめるかを確認します。

README は、プロジェクト管理方法への入口でもあります。管理方法の詳細は README に抱え込ませず、`docs/project_governance.md`、Steward 運用文書、判断ログ、子分Steward固定チャットなどへ導線を張ります。README に管理方法への入口がない場合、親分Stewardは「足場の入口がない」リスクとして、導線追加を提案します。

README の長さだけでは足場リスクとしません。ただし、長大化によって入口として機能しなくなり、現在地、正本、管理方法、判断記録への到達を妨げる場合は、KTA 上の足場リスクとして扱います。

### `DECISIONS.md`

将来の判断記録です。MVP では必須にしません。

プロジェクトの方向性、スコープ、設計に影響する判断を、軽量かつ時系列で残します。MVP では、未記録判断の候補が見つかった場合に「`DECISIONS.md` に短く残してよろしいですか？」という提案先として扱います。

### `reports/`

MVP の足場レビューレポート保存先です。

標準出力を基本にしつつ、必要に応じて `reports/footwork_review_YYYY-MM-DD.md` に Markdown レポートを保存できる形にします。保存は任意であり、MVP では自動修正や運用ログ管理とは分けて扱います。

### `logs/`

将来の運用記憶の置き場です。

日付つきの scan レポート、レビュー記録、実行ログを置きます。チャット履歴を探さなくても、何が起きたかを追えるようにします。

## MVP CLI: `pma scan`

CLI 名は `pma` とし、最初のコマンドは次の形にします。

```text
pma scan
```

想定する動作:

- 現在の Git リポジトリを検査する。
- `PROJECT_STATUS.md`、`README.md`、`docs/`、`.project-agent.yml` を読む。
- Markdown のレビュー結果を生成する。
- オプションで日付つきレポートを `reports/footwork_review_YYYY-MM-DD.md` に書き出す。
- 明確に設定された失敗条件に限り、non-zero exit code を返す。

CLI はまず報告ツールとして始めます。書き込み系の動作には、明示的な flag と人間の承認を必要とします。

## 自動修正しない設計

エージェントは、プロジェクトを黙って直しません。

自動修正は便利ですが、誤った安心感を作ることがあります。また、このエージェントが見つけるべきズレそのものを隠してしまう可能性があります。

標準の流れ:

1. 検知する。
2. 報告する。
3. 確認を求める。
4. 変更案を提案する。
5. 承認後にだけ適用する。

この流れにより、プロジェクト記録の所有権を人間に残したまま、記録を維持する負担を減らします。

自動修正しないことは、言いっぱなしにすることではありません。Steward は、修正を強制せずに、状態として閉じる道を示します。
