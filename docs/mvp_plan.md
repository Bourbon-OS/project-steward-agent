# MVP計画

**公開状態:** v0.2（docs-only）

この文書は、[コンセプト](concept.md)と[要件](requirements.md)を、最初にどの範囲で確かめるかを定めます。

公開 v0.2 はドキュメントのみです。実行可能なエージェントやコードは含みません。この計画は、公開済みの実装状況を示すものではなく、PSA の最初の MVP が何を検証できればよいかを示します。

## MVPで確かめること

最初の MVP は、1つのローカル Git プロジェクトを対象にします。プロジェクトの規模を概念上の対象から外すためではなく、PSA の中核となる一連の振る舞いを、小さく安全に検証するためです。

検証するのは、次の一巡です。

1. 変更の連絡を受ける、または見回りで文脈の漏れや状態のズレを見つける。
2. 許可された範囲の既存の痕跡を先に調べる。
3. 確認できた事実、そこからの推測、まだ分からないことを分ける。
4. 影響と、推奨する次の一手を具体化する。
5. 必要な判断または許可を人間へ求める。
6. 許可後に、必要な記録、状態、導線を実際に修復する。
7. 修復結果を確認し、何を行ったかを報告する。
8. 判断待ちや保留が残る場合は、再確認の条件または時期を残し、人間が次の扱いを決めるまでフォローする。

読み取りと報告だけでは、最初の MVP の完了とはしません。許可後の修復と結果確認、必要なフォローまでを少なくとも一度検証して、MVP の一巡が成立したと判断します。

## 段階的に検証する

実装順序は二段階に分けます。ただし、二つを別の製品や別の概念にはしません。

### 1. 安全に観測し、整理する

- 対象プロジェクトの境界を守る。
- Git、既存文書、チケット、ログなど、許可された痕跡を読む。
- 機密情報、秘密値、対象外のプロジェクトを既定で読まない。
- 事実、推測、不明点を分ける。
- 宣言された状態や意図と、実際の変更痕跡のズレを候補として示す。
- すべてを並べず、安全な次の選択に影響するものを優先する。
- 判断材料、推奨案、必要な許可を小さく具体的に示す。

この段階では、許可なく対象を書き換えません。

### 2. 許可された手入れを実行し、閉じる

- 人間が許可した範囲を明確にする。
- 新しい専用文書を一律に作らず、既存の正本や適切な記録先を使う。
- 必要な文脈、状態、導線を修復する。
- 既存の変更を無言で上書きまたは破棄しない。
- 変更結果を確認し、実行内容と残る不明点を報告する。
- 判断待ちや保留には、確認先と再確認の条件または時期を残す。
- 適切な時点で戻り、続行、明示的な保留、停止、やらない、対象外など、人間が次の扱いを決めるまでフォローする。

コード、プロジェクト成果物、稼働中サービスを変更することは、最初の MVP の許可後実行には含めません。

## 三つの起動方法

PSA の中核処理を三種類に分けるのではなく、同じ Steward の仕事を、必要なタイミングで始めます。

### manual

人間が、引き継ぎ、再開、変更、停止などについて確認したいときに明示的に始めます。

### event-driven

通常の変更では、変更した人やエージェントが、その場で短い文脈をPSAへ渡します。PSAは残された痕跡を先に調べ、重要な曖昧さだけを確認します。

障害対応などの緊急時は、まず必要な対処を優先します。その場で渡せなかった文脈は、落ち着いた後の timing-driven の見回りで回収します。

### timing-driven

定期的な見回りと、判断待ち・保留の再確認に使います。

最初の MVP でも、人間が思い出したときだけ動くことを完成形にはしません。ただし、PSA 独自の常駐処理やスケジューラは作りません。既存の定期実行、リマインダー、エージェントの自動実行など、利用できる軽い仕組みにつなぎ、少なくとも一つのプロジェクトで次を検証します。

- 連絡がなかった変更を、記憶と痕跡が新しいうちに拾える。
- 判断待ちや保留の再確認時期を覚えていられる。
- 適切な時点でPSAが戻り、結果を記録へ反映できる。
- 同じ確認を機械的に繰り返さず、重要度、期限、依存関係、状況変化に応じて間隔を調整できる。

具体的な実行手段と標準的な間隔は、利用環境と試験結果を見て決めます。

## 検証する場面

[要件の受け入れ場面](requirements.md#受け入れ場面)を使います。最初の MVP では、少なくとも次を実地に確認します。

- 通常の変更で、短い文脈を既存の痕跡へつなげられる。
- 緊急対応を妨げず、後から必要な文脈を回収できる。
- 宣言された状態や意図と、実態の静かなズレを示せる。
- 長期稼働中または休止中の仕事で、次を安全に選ぶ材料を整えられる。
- 担当者がいない古い仕事で、分からないことを作らずに可能な範囲を復元できる。
- 許可後に記録や導線を修復し、結果を確認できる。
- 小さなプロジェクトへ重い専用運用を持ち込まない。
- 判断待ちを放置せず、適切な時点で再確認し、人間が次の扱いを決めるまで追える。

## MVPの評価

文書数、検出件数、警告数では評価しません。

次を確認します。

- PSAがなければ失われた可能性のある文脈を回収できたか。
- 再開、引き継ぎ、変更、停止などの判断が安全になったか。
- 事実、推測、不明点を分けられたか。
- 人間へ渡した判断は小さく、根拠と推奨案があったか。
- 許可後の処理と結果確認まで行えたか。
- 判断待ちや保留を放置せず、適切にフォローできたか。
- 人間への確認回数、タイミング、記録負担は妥当だったか。
- 既存の方法を生かし、不要な専用文書や重複記録を増やさなかったか。

役に立たない検出、記録、見回りは、追加するのではなく縮小または撤去します。

## MVPで作らないもの

- PSA 独自の常駐処理、ファイル監視、スケジューラ、通知基盤
- 無許可の修正、stage、commit、削除、移動、公開
- コード、プロジェクト成果物、稼働中サービスの自動変更
- 状態名と状態遷移の完全な体系
- 必須の専用ファイル、判断記録、テンプレート
- Issue 管理、プロジェクト管理、変更管理、インシデント対応、監査の代替
- チャット、メール、会議、Git ホスティングサービスとの本格的な連携
- 複数プロジェクトを横断する相談窓口の実装
- 複数プロジェクトの深い情報を一か所へ集める仕組み

## この公開版で固定しないこと

- コマンド、設定、保存形式、内部構成
- 見回りとフォローの標準的な間隔
- 状態名と状態遷移
- 外部サービスと接続する範囲
- 複数プロジェクトを横断する相談窓口の具体的な形
- より広い修復をPSAへ許可する条件

これらは、MVPを具体化する段階、または最初の一巡を実地に試して人間の負担と有効性を確認した後に決めます。
