# コンセプト

Ashibaは、プロジェクトの成果物ではなく、その周囲にある、再開と引き継ぎのための足がかりを扱う全体概念です。

ここでいう Ashiba は、作業を再開できる、他者へ引き継げる、判断の理由を説明できる、変更前後へ戻れる状態を支える最小限の足場です。
Keep the Ashiba（KTA）は、その状態を重い管理制度にせず維持する考え方と実践です。

公開上の役割族はStewardです。KTAには、オーナー付きStewardと個別プロジェクト付きStewardの二つの配置があります。内部ではそれぞれをButler、Caddieと呼び、機械上は`attached_to: owner | project`で表します。

Ashiba Stewardはこのプロジェクト全体の正式名称です。ソース上の配布名とプロジェクト内の自己識別子は`ashiba-steward`、CLIとPythonのimport名は`pma`です。旧称Project Steward Agentと`project-steward-agent`は、既存のローカルフォルダ、公開リポジトリ、現在インストールされている編集可能パッケージの情報、過去の記録を追うために残っています。詳細は[正式名称と識別子移行の方針](decisions/2026-08-16-public-name-direction.md)を参照します。

具体的な規範は [KTA原則](principles.md) を正本とします。

## 解決したい問題

プロジェクトでは、成果物より先に運用記憶が失われることがあります。

- 実態と README、設計書、状態メモがずれている。
- 重要な判断が担当者の記憶やチャットだけに残る。
- 仮対応が、仮だったことを忘れられたまま前提になる。
- 未コミット変更や未追跡ファイルの意味が分からなくなる。
- `active` のまま止まり、休止、保留、忘却のどれか分からない。
- 再開時に、どこまで進んだかを復元するところから始まる。

Ashiba Stewardが防ぎたいのは、規則違反ではなく、この再開不能と文脈喪失です。

## 足場が失われやすい時

足場は、次のように注意が成果や対処へ向いている時に失われます。

- 構築、実装、リリース前など、急いで前へ進む時。
- 障害対応や暫定回避など、まず止血が必要な時。
- 調査、検証、デバッグで複数の道を試す時。
- 小変更や慣れた作業を、記録するほどではないと感じる時。
- 会議やチャットの流れで、前提や保留が決まる時。
- 引き継ぎ、担当変更、別チームへの依頼で人に渡す時。

Steward は、こうした作業を記録のために止めません。
対応後に Git、ログ、会議メモ、変更計画書などの既存の痕跡から、後で戻るための文脈を薄く回収します。

## 休止と忘却を分ける

`paused` は正常な状態です。
休止理由、再開条件、次回確認が分かれば、止まっていても再開できます。

危険なのは、状態を説明できないことです。
Ashiba Stewardは活動量を採点するのではなく、継続、休止、保留、中止のどれとして扱うかを宣言できるよう支えます。

## 正本と痕跡

Ashiba Stewardは、プロジェクトが採用している入口と正本を尊重します。

- `README.md`: プロジェクトの身元と、現在地・正本への入口。
- `PROJECT_STATUS.md`: 現在の状態と次回確認。
- `docs/`: 設計、要件、運用などの正本。
- 判断記録: 後で迷う重要な判断と理由。
- `logs/` や review report: 履歴と確認結果。
- 既存の変更計画書、障害報告、会議メモ: すでに機能している場合の正本または証拠。

README にすべてを書き込む必要はありません。
重要な資料へ迷わず辿れる短い地図であれば十分です。

## Steward の役割

Steward は、監査官、万能管理者、プロジェクト担当者ではありません。

行うこと:

- 実態、記録、状態宣言を観測する。
- ズレを事実と解釈に分けて示す。
- 今扱うべき小さな一手を具体化する。
- 必要な判断を担当へ渡す。
- 記録、保留、次回確認などの状態まで見届ける。

行わないこと:

- プロダクトや設計の採用判断を奪う。
- 全件を人間の ToDo として投げる。
- 無確認で修正、削除、移動、公開、stage、commit する。
- 既存のプロジェクト管理、監査、変更管理を再実装する。

## エージェントに限らない

KTA は、人間のレビュー、チェックリスト、Git運用、テンプレートでも実行できます。
CLI は機械的な事実を集め、AI は文脈の解釈と対話を助けますが、どちらも目的そのものではありません。

価値があるのは、ツールを置くことではなく、未来の自分や次の担当者が安全に戻れることです。

## 価値の判定

Ashiba Stewardの価値は、次の問いで検証します。

> 中断後のプロジェクトを、事情を知らない人または新しいエージェントが、より早く、誤解なく再開できるか。

この差を実運用で確認できない場合、Ashiba Stewardは文書、チェック、役割を縮小します。
