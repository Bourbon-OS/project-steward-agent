# コンセプト

**公開状態:** v0.2（docs-only）

プロジェクトでは、成果物より先に、それを扱うための文脈が失われることがあります。

何を変えたかは Git に残っている。それでも、なぜ変えたのか、何に依存しているのか、仮の対応だったのか、次にどうするのが安全なのかが分からない。動いてはいるけれど、引き継げない。更新できない。改善できない。止めることも、安心して再開することもできない。

Project Steward Agent は、このような実際の困り事を解決するための構想です。新しい管理理論を発表することや、既にある方法を別の名前で作り直すことを目的にはしません。

## 足元を見ずに進むとき

文脈が失われるのは、誰かが怠けているからとは限りません。仕事を進めるために、注意を足元から外さなければならないときがあります。

- 構築、実装、リリース前など、急いで前へ進むとき。
- 障害対応や暫定回避など、まず止血しなければならないとき。
- 調査、検証、デバッグで、いくつもの道を試しているとき。
- 小さな修正や慣れた作業を、残すほどではないと感じたとき。
- 会議やチャットの流れで、前提や保留が決まったとき。
- 引き継ぎ、担当変更、別の人への依頼で、仕事が人から人へ渡るとき。

たとえば、トラブルを止めるために小さな修正を入れ、その場では全員が理由を知っていたので、Git だけを更新して作業を終えたとします。すぐなら一言で説明できます。しかし連絡がないまま時間がたてば、数か月後には、変更した人も依頼した人も詳しく覚えていないかもしれません。差分は残っても、その差分を安全に扱うための文脈は残りません。

仮の道を正式な道にすること自体は悪くありません。危ないのは、仮だったことを誰も覚えていないまま、いつの間にか変更できない前提になることです。

失われるのは、止まったプロジェクトの文脈だけではありません。長く安定して動いているサービスでも、手順とルールだけが担当者から次の担当者へ渡り、その理由が少しずつ失われることがあります。決められたとおりに動かせても、なぜそのルールがあるのか分からない。だから変更できず、改善できず、動かし続ける以外の選択肢がなくなる。Active であることと、健全であることは同じではありません。

逆に、意図して止めることは、健全な選択です。危険なのは、休止したのか、ただ忘れられたのかさえ分からず、理由も再開条件も失われることです。手順や記録が整っていても、日々の判断理由まで自然に残るとは限りません。

問題は、文書が少ないことではありません。時間がたち、人が変わった後に、続ける、引き継ぐ、更新する、改善する、修復する、止める、再開するという次の状態を、安全に選べなくなることです。

## 必要なときに組める足場

> **Ashibaが可能にすること:** 時間がたち、人が変わっても、文脈と現在地をたどり直し、安全に次を選べること。

そのために残る痕跡と文脈、そして必要なときにそこから組む作業構造を、まとめて Ashiba と呼びます。

建設現場の足場は、建物を作るときだけでなく、修復、変更、改善するときにも組まれます。作業が終われば片付けます。立てたままでは見栄えや本来の利用を妨げることがあるからです。しかし、必要なときに足場を組めなければ、安全に手を入れることはできません。

Ashiba のために、常に大量の管理文書を維持する必要はありません。Git の履歴や差分、既存の文書、チケット、ログ、会議やチャットの記録、現在の状態、残された理由・制約・依存関係・不明点など、既にある痕跡と文脈を使います。

すべてを残す必要はありません。後から安全に戻るために必要なものを、仕事の副産物として既に残る痕跡へつなぎます。足りない場合も、重い文書を増やすのではなく、理由、仮か正式か、影響するもの、次に見る場所などを必要な範囲で薄く残します。

プロジェクトの大きさは、対象に含めるかどうかの基準ではありません。小さなプロジェクトほど、理由や依存関係が一人の記憶に置かれやすく、数が増えるほど人間だけでは見守りにくくなります。小さいものには、小さい Ashiba があれば十分です。

## Ashiba を使える状態に保つ

この文書では、Project Steward Agent（PSA）を短く Steward と呼ぶことがあります。どちらも同じ AI エージェントを指し、別の役割や階層ではありません。人間も KTA を実践できますが、この文書で Steward と書く場合は PSA を指します。

> **Keep the Ashiba（KTA）:** 変更時に文脈を Steward へ渡し、定期的に漏れを拾い、Ashiba を使える状態に保つこと。

通常の変更では、変更した人やエージェントが、event-driven で必要な文脈を Steward へ渡します。Steward が後から何度も聞き回ることを前提にはしません。まず残された痕跡を調べ、理由や依存関係について重要な曖昧さだけが残る場合に、具体案を持って短く確認します。

ただし、障害対応などの緊急時は、まず必要な対処を優先してください。その場で渡せなかった文脈は、落ち着いた後、timing-driven の見回りで、記憶と痕跡が新しいうちに Steward がお伺いに参ります。

そのとき、「タイムアウト値を変更。障害回避のための暫定対応。恒久対応は要確認」と短く伝えるだけでも、PSA が Git の差分や関連する痕跡を調べ、必要な記録案を作る起点になります。

それでも連絡は漏れます。宣言された状態は変わらないまま、Git やチケットなどの実態だけが動くこともあります。そこで、軽い定期的な見回りによって、変更の連絡漏れや、宣言と実態の静かなズレを拾います。見回りはすべてを再文書化する仕事ではありません。文脈を覚えている人がいる間に、後で困る可能性のある穴を見つける安全網です。

見回りは、規則への適合や人の責任を判定する監査ではありません。将来困る可能性のあるズレを見つけ、修復の具体案につなぐために行います。

短く言えば、**event-driven で変更と文脈をその場で渡し、timing-driven で漏れを拾います。** 運用としては継続し、実行は間欠的に行い、重い足場そのものは必要なときに組みます。

KTA は AI だけの方法ではありません。人間の引き継ぎ、既存のレビュー、チェックリストや運用手順でも実践できます。PSA は、この仕事を小さなプロジェクトが多数ある場合にも軽く続けられるようにする実行役です。

> **Project Steward Agent（PSA）:** 変更の連絡を受け、見回りで漏れを拾い、人の指示のもとで記録や修復まで行う AI エージェント。

Steward は、前に立って仕事の目的を決める存在ではありません。仕事のそばを歩き、どの道を通ってきたかを残し、必要になった足場を実際に整える存在です。

PSA は判断者でも、監査官でも、助言だけを残すコンサルタントでもありません。残された痕跡を先に調べ、確認できた事実、そこからの推測、まだ分からないことを分けます。人間が決めるべきこと、許可すべきこと、引き受けるべきリスクは人間に残します。

そのうえで、人間の指示と許可を受けた後は、記録を正しい場所へ反映する、古くなった状態を直す、必要な導線を修復するなど、実際の処理まで行います。判断を奪わないことと、仕事を人間へ投げ返さないことを両立させます。

PSA は責任者にはなれません。それでも、漏れを責めず、問題を見つけて言うだけで終わらせません。未決であれば、未決と記録するだけで終わらず、人間が続ける、保留する、止める、やらないなどの扱いを決めるまで、必要なフォローを続けます。ここで目指すのは、「責任は取れなくても、責任感のある振る舞い」です。

この公開版は、PSA の考え方と設計を共有するドキュメントです。実行可能なエージェントやコードが既に提供されているとは主張しません。

## 既存のものを生かす

Git、Issue や Pull Request、決定記録、Runbook、プロジェクト管理、変更管理、インシデント対応、会議記録には、それぞれ既に確立された役割があります。PSA はそれらを置き換えず、新しい専用文書を常に要求もしません。プロジェクトが既に残している痕跡を尊重し、必要なときに横断して、次の仕事に使える Ashiba を組みます。

既存の方法で十分に解けている問題は、その方法に任せます。PSA が加えるのは、散在する痕跡と文脈を必要時につなぎ、漏れを軽く見回り、人間の判断後に必要な手入れを実行する役割です。参照した第三者の手法や資料は、[NOTICE](../NOTICE.md) に出典と関係を明記します。

この手入れは、成果物を直接増やさないため、何も生まない仕事に見えることがあります。しかし、管理は未来の作業速度を守る仕事です。

「たぶんこうだった」を、「ここまでは確認でき、ここからは不明」に変えることも、Ashiba の成果です。

成功の基準は、文書の量、検出件数、理論的な新しさではありません。実際の仕事を安全に引き継ぎ、変更し、停止し、再開できたかです。役に立たない記録や見回りは、増やすのではなく縮小または撤去します。
