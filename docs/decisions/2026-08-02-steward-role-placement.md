# Stewardの役割族・配置・内部呼称

- Status: accepted
- Date: 2026-08-02
- Decision owner: Owner
- Applies to: 現行の複数プロジェクト運用
- Does not decide: 公開プロジェクトの恒久名称、公開上の正式な配置名、商標上の使用可能性
- Later decision: 2026-08-16の[正式名称と識別子移行の方針](2026-08-16-public-name-direction.md)で、プロジェクト全体の正式名称を`Ashiba Steward`とした。物理識別子の変更と外部公開は未実施。

## Context

Project Steward Agent（PSA）は、専門判断や最終決定を人間から奪わず、プロジェクトの文脈、痕跡、判断待ち、正本への反映を追う役割です。

現行運用には二つの配置があります。

- Ownerのそばで、Ownerが許可した複数プロジェクトの浅い状態と問い合わせ先を把握する配置。
- 一つのプロジェクトに付き、深い文脈、調査、許可後の修復、結果確認を担う配置。

二つは別の公開概念や別の役割族ではありません。また、二つを対称な形容詞で表そうとすると、対象との関係を正しく表せませんでした。

## Decision

### 1. 共通の役割族

二つの配置は、どちらも **Steward** です。

Stewardは、先回りして観測・整理しても、設計判断、採用判断、専門判断、プロダクト優先順位を人間から奪いません。許可された範囲で必要な相手へ問い合わせ、判断と反映が未決のまま消えないように追います。

### 2. 配置関係

配置は、可視範囲を表す`global` / `local`ではなく、Stewardが誰または何に付いているかという関係で表します。

```yaml
steward:
  attached_to: owner
```

```yaml
steward:
  attached_to: project
```

| Relation | 現行の内部呼称 | 配置と責務 |
|---|---|---|
| `attached_to: owner` | **Butler** | Ownerのそばで、承認済みプロジェクトの浅い地図と問い合わせ先を持ち、必要な確認を適切な担当へ渡し、結果がOwnerへ届いて正本へ反映されるまで見届ける |
| `attached_to: project` | **Caddie** | 一つのプロジェクトに付き、痕跡を調べ、事実・推測・不明を分け、許可後の修復、結果確認、フォローを行う |

Butlerは各プロジェクトから共有されるサービスではありません。Ownerに付き、Ownerが許可した家の範囲を預かります。料理、掃除、庭、仕事の担当がButlerの主人なのではなく、ButlerがOwnerのために問い合わせ、調整する専門担当です。

Caddieはproject-localに配置されたStewardです。一つのプロジェクトには深く関わりますが、そのプロジェクトの担当者やOwnerに代わって専門判断を決めません。

### 3. Agent

**Agentは人間側の階級名にしません。** Stewardを実現するruntimeの一形態として扱います。

StewardはAIだけに限定されません。固定タスク、Skill、CLI、人間の手順などでもKTAを実行できます。

### 4. 人間側の役職

現行scopeには、Ownerと別人の`Project Lead`を新設しません。最初に扱うのは、1人のOwnerが複数の個人プロジェクトを育てる運用です。

将来、別人がプロジェクトを担当する場合は、その時点の実態に応じてPM、PO、担当者などの既存職位を接続します。

### 5. 公開ブランドとの分離

`Butler`と`Caddie`は、現行チームが二つの配置を呼び分ける内部呼称です。単独の公開製品名、organization名、package名にはしません。

公開文書で内部呼称に触れる場合は、「我々はこの配置をButler / Caddieと呼んでいる」という説明に留められます。公開上の正式な配置名は別の判断として扱います。

`Steward`単独も主公開ブランドにしません。`Project Steward Agent`は2026-08-03のpilot固定評価までは維持しますが、恒久名称として確定したことを意味しません。

## Permission boundary

`attached_to`は配置関係だけを表します。許可や設置済み状態を自動的に与えません。

`attached_to: project`のCaddieは、次の3点がそろった時に設置済みと扱います。

1. Butler側の対象一覧に、対象と1つ以上のproject-localな確認先が登録されている。
2. projectの入口から、Stewardの役割、許可境界、記録先へ辿れる。
3. Caddieが読んでよい範囲を、Ownerまたは権限を持つ人間が承認している。

Butlerが扱えるのも、Ownerが承認した候補取得元と対象プロジェクトだけです。`attached_to: owner`は、未承認のプロジェクトを探索または管理できる権限ではありません。

## Consequences

- 利用者が日常的に覚える内部呼称は、Steward、Butler、Caddieです。
- `attached_to`は設定・実装上の関係表現であり、新しい公開概念ではありません。
- A/Bを一列の階級として扱わず、Owner判断を中心に、ButlerとCaddieの受け渡し経路を保ちます。
- 移行前の役割名は新規文書で使いません。
- `project-local`は配置の説明語として引き続き使えます。
- 現行文書と運用手順は現在の役割名へ揃えます。明示的な過去資料やログは履歴として書き換えません。

## Rejected alternatives

| Alternative | Reason |
|---|---|
| `cross-project / project-local` | 前者は横断閲覧・連絡の範囲だけを示し、Ownerのそばで全体の受け渡しを預かる責任を表しにくい |
| `portfolio / local` | project portfolio managementの選別・優先順位・資源配分を連想させ、現行の非決定権境界と説明上の緊張がある。語の領域も揃わない |
| `house / local` | 家の比喩と技術的scopeが混在する |
| `global / local` | 未承認対象まで含むように見え、浅い情報だけを持つことや非決定権を表さない |
| `shared / local` | 各projectがButlerを共有するという、OwnerとButlerの関係を逆に読ませる |
| Aだけを`Steward`と呼ぶ | BがSteward役割族から外れ、PSAがAだけを指すように見える |
| `Project Lead`を先に置く | 現行scopeに別の占有者がおらず、説明のためだけの人間役職になる |

## 2026-09-11補足：Caddieの責任と記録の継続

- 背景：「1プロジェクトに1つの論理的な固定窓口」が、特定のAIや固定チャットを使い続ける要求とも読める懸念が、配置方法の検討中にオーナーから示された。環境非依存の既存要件に立ち戻り、継続させる対象を明確にした。
- 判断：オーナーの正本追記の依頼を受け、プロジェクト担当、Caddieの担い手、AI・ツール・実行環境が変わっても、足場管理の責任と記録を引き継ぐことを[要件3.3](../requirements.md#33-caddie個別プロジェクト付きstewardの内部呼称)へ補足した。単に同じ窓口を残すのではなく、後任が現在地・判断理由・未完了・次の行動・後日の確認を回収できることを求める。
- 境界：同じ人、AI、チャット、常駐プロセスの維持は求めず、引き継ぎを許可範囲の拡大としない。固定タスク、フォルダ、AGENTS.md、Skillの具体的な配置は未決であり、配置・移植性・実運用効果の検証完了を意味しない。
- 履歴：要件の2項目はmasterから到達する `a555caa6943916c7ce84f6f4c579e2e4f0b79f5f` に保存。先のコミットには変更理由が十分に残っていなかったため、オーナーの確認と補足保存の承認を受け、この判断記録を追加した。元のコミットと過去の判断本文は書き換えない。
