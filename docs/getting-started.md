# 最小の導入

## 1. 対象と責任を決める

Butlerはオーナーの複数プロジェクトを浅く見て、優先順位、未回収結果、次の確認を扱います。Caddieは一つのプロジェクトの背景、正本、複数の作業、未完了を追います。プロジェクト担当が本作業を進め、Stewardは判断理由や戻り先を見失わないよう補います。

一つの論理的な窓口を継続利用し、同じ役割を重複配置しません。固定チャットは配置方法の一例であり必須ではありません。

## 2. 配布一式への接続を作る

この配布フォルダは一つの読み取り可能な場所に置き、各担当が同じSkillと参照先へ辿れるようにします。個別プロジェクトへ手順全文をコピーしないでください。

AI環境へのSkill登録は、その環境の導入方法に従います。4つのSkillフォルダだけを別々の場所へコピーすると、隣のSkillや`docs/`への相対参照が切れる場合があります。最初は配布一式の配置を保ったまま入口を指定し、本文と参照先を実際に読めることを確認してください。この配布物はAI環境への自動インストールは行いません。

直接読めないCaddieには、正本の版を確認したButlerが今回に限った短い作業契約を渡せます。版だけを渡した場合や契約が不足する場合は、接続不足として戻します。

## 3. 許可範囲を設定する

- Butler：許可された非公開対象一覧へ浅く同期する。対象プロジェクトと製品開発リポジトリは既定で読み取り専用。
- Caddie：そのプロジェクト内の許可された入口・状態・判断記録を読む。修復は承認された対象と操作に限る。
- 送信、修正、commit、公開の許可は別です。配置や手順の参照がこれらの許可を自動付与するわけではありません。

[Butlerの初期ひな形](../skills/project-steward/templates/butler/AGENTS.md)、[Caddie配置ひな形](../skills/project-steward/templates/caddie_setup.md)、[対象一覧ひな形](../skills/project-steward/templates/project_list.md)を、自分の環境の入口に合わせて使います。ひな形を置くだけでは導入済みになりません。対象一覧とプロジェクト側の入口、読み取り範囲が接続したことを確認します。

## 4. 起動と回収をつなぐ

| きっかけ | 最小の動き |
| --- | --- |
| 手動確認 | 利用者または担当が、既存のStewardへ確認を依頼する |
| 変更の連絡 | 変更した担当が、対象・理由・仮か正式か・未決事項を必要な分だけ渡す |
| 定期確認 | 実際の定期実行を設定した主体が、許可範囲で確認し、結果を既存の窓口へ返す |

定期確認では、いつ、誰が、どこを、何のために確認し、どこへ結果を返すかを決めます。日付の保存、送信、結果受領、正本反映は別です。実際の起動・結果回収を確認するまでは稼働済みとしません。

## 5. CLIを補助として使う

まず[サンプルプロジェクト](../examples/sample-project/README.md)だけを観測し、その後、許可された実対象へ適用します。サンプルの一覧は架空のもので、実運用対象一覧ではありません。

毎回読む文書と実際の状態文書パスは、[設定例](../examples/sample-project/.project-agent.yml)のように宣言します。開始時に自動で適用される指示、常に読む文書、必要時だけ読む資料を区別し、実環境での適用範囲と合っているか確認してください。

CLIの観測結果をそのままOwner判断や作業許可にしません。危険、重要な未完了、回答待ちを確認し、必要な一件を分かる言葉で返して、許可後の行動と結果の回収を追います。

`.project-agent.yml`がない場合、`scan`はルートの状態文書を実体と決めつけず、状態文書の内容と毎回読む範囲を未確認として扱います。一方、`handoff`は安全な既定位置の`PROJECT_STATUS.md`を読み、読み取れた宣言値を引き渡します。この値を正本確認済みと扱わず、対象projectの入口と照合してください。設定が存在しても安全に読めない場合は、どちらも設定依存の状態観測を行いません。

`scan`の`ready`は、観測できた機械的なfindingからの限定判定です。設定なしの観測不足など、低重要度のfindingだけで`ready`になる経路があり、全ての状態・理由・未完了が確認できたことは意味しません。実対象への導入では、設定を置き、状態文書・正本・毎回読む範囲が実際の入口と一致することを確認します。CLIのREADME必須チェックも既定の観測項目であり、Stewardが既存の入口文化を置き換える要求ではありません。

## 理由を残し、次の担当が戻る短い例

次は旧v0.2の暫定対応の例を使った架空の一巡です。実運用の効果を確認した事例ではありません。

1. 担当が「障害回避のためタイムアウトを延長した。暫定対応で、恒久対応は未決」とCaddieへ連絡します。
2. Caddieは許可された差分と既存の判断記録を先に読み、理由の所在、暫定であること、残る未決を分けます。記録不足なら、既存の判断記録への短い追記と入口の導線だけを提案します。
3. Ownerがその記録の編集を許可したら、当時の記録を保全した後日の補足として理由と根拠をつなぎます。未決の恒久対応には、例えば「次の負荷試験の結果が出たら再検討」という戻る条件を残します。日付だけで自動実行されたことにはしません。
4. 次の担当はプロジェクトの入口から補足と根拠へ辿り、変更の理由、暫定であること、未決、再検討条件を回収します。元のチャットを読み直さずに戻れるかを確認し、記録補完と恒久対応の完了は分けます。

実行時は[Caddieの背景確認](../skills/check-caddie-context/SKILL.md)から[相談・記録・復元](../skills/project-steward/references/caddie_context_recovery.md)へ進みます。必要な理由を既存記録へつなぎ、新しい専用台帳は必須にしません。コードの変更やGit保存には、それぞれ別の操作許可が必要です。

## 6. Work Mapの別配布

Work Mapは、仕事の目的・現在地・判断理由を、仕事が生まれた時から保つための足場です。Stewardは既存のGitや文書でも予防・検知・復元を行い、Work Mapはその目的を支える選択肢です。

[Work Map個人利用・開発スターター v0.1.0](https://github.com/Bourbon-OS/workmap-personal-starter/releases/tag/v0.1.0)は別配布です。初期化、Work登録、Map／Thread表示、保存要求の再確認、バックアップ、隔離復旧候補の確認を提供します。[公開READMEと導入説明](https://github.com/Bourbon-OS/workmap-personal-starter)を参照してください。

対象はPython 3.11以上、同一Windows host、同期対象外のローカルSQLiteです。GUI、全ての日常操作の簡単な入口、複数PC共有、自動マージは含みません。会社での実起動・実業務効果、Stewardとの常用接続は未確認です。このv0.3からWork Mapを操作する手順や統合機能は提供しません。採用するprojectでは、そのprojectの正規入口・操作手順・許可を別に確認します。

両配布に`src/pma`があるため、同じPython環境へ混ぜず、別々の展開先と環境で、それぞれの入口を実行してください。ソース実行では、その呼出しに使う一方の`src`だけを指定します。別配布v0.1.0とSteward v0.3は別の版で、v0.4での統合や時期は約束していません。
