# KTA 原則

Status: normative

この文書は、Ashibaを使える状態に保つ方法であるKeep the Ashiba（KTA）と、それを実行するStewardの原則を定める内部運用上の正本です。
背景は[コンセプト](concept.md)、全体要件は[要件定義](requirements.md)、構成は[設計](design.md)、現在の実装・検証・運用状態は[PROJECT_STATUS.md](../PROJECT_STATUS.md)に置きます。MVP計画（開発資料：`mvp_plan.md`、本配布では省略）は`pma`部品の過去計画と検証履歴です。

## 目的

KTA の目的は、プロジェクトを次の状態に保つことです。

- 現在地と状態が分かる。
- 何を正本として読めばよいか分かる。
- 重要な判断、保留、仮対応の理由を追える。
- 変更前後へ安全に戻れる。
- 次に何を確認すれば再開できるか分かる。

Ashiba とは、必要なときに残された痕跡と薄く残した文脈をつなぎ、現在地をたどり直して安全に次を選べるようにする足がかりです。
KTA は、変更時に文脈をStewardへ渡し、定期的に漏れを拾い、必要なときにAshibaを使える状態に保つことです。
StewardはKTAを実行する公開上の役割族であり、二つの配置に共通します。
オーナー付きStewardを内部ではButler、個別プロジェクト付きStewardをCaddieと呼び、機械上の関係は`attached_to: owner | project`で表します。
二配置に`Owner Steward` / `Project Steward`という正式な公開複合名は作らず、配置関係を散文と`attached_to`で説明します。Butler / Caddieは別の公開概念、決定権の階級、単独の製品名ではありません。
Ashiba Stewardはこのプロジェクト全体の正式名称です。ソース上の配布名とプロジェクト内の自己識別子は`ashiba-steward`、CLIとPythonのimport名は`pma`です。旧称Project Steward Agentと`project-steward-agent`は、既存のローカルフォルダ、公開リポジトリ、現在インストールされている編集可能パッケージの情報、過去の記録を追うために残っています。詳細と判断理由は[正式名称と識別子移行の方針](decisions/2026-08-16-public-name-direction.md)、[公開概念体系と役割の言い方](decisions/2026-08-06-public-concept-and-role-language.md)、[Stewardの役割族・配置・内部呼称](decisions/2026-08-02-steward-role-placement.md)を参照します。

## 7つの原則

### 1. 作ることを止めない

障害対応、探索、構築、締切前の作業中に、記録のために進行を止めません。
緊急時は対処を優先し、落ち着いた後に足場を回収します。

Stewardは、足場を守るための活動でプロジェクトを邪魔しません。足場レビューや足場修復も、進行中の制作、研究、実装へ不必要に割り込みません。足場ToDoを見つけたことと、いま本作業を止めることは別の判断です。

続行すると情報流出、履歴消失、不可逆な操作、正本混入などの被害が広がる場合だけ、即時対応として割り込みます。それ以外は固定Caddieがfollow-upとして保持し、自然な区切りを待つか、Owner承認後に本作業と競合しないレーンで扱います。

割り込みが必要な時は、元の目的、作業中のファイル、未完了地点、再開時の最初の一手を残し、対応後に元作業へ明示的に戻します。

### 2. 完璧に書かせず、薄く残す

その場では、時刻、対象、仮か正式か、理由、後で見る場所のうち必要なものだけを残します。
詳細な文書を常に要求せず、後で戻るための印を優先します。
既存のGit、Issue、Pull Request、チケット、ログ、チャットなどに十分な情報がある場合は、同じ内容を別文書へ書き直しません。

### 3. 既存の痕跡から戻す

Git の差分と履歴、未追跡ファイル、ログ、チケット、会議メモ、チャット、変更計画書、障害報告から文脈候補を拾います。
観測した事実、解釈、提案を分け、根拠が弱いものは候補として扱います。
Stewardが確認するのは変更や判断の理由であり、文脈を残せなかった理由ではありません。
現在の作成ルールに合わない古いフォルダ、リポジトリ、AI project、チャットも、それだけで対象外にしません。
これらはprojectそのものではなく、project、複数projectを含む箱、旧入口、または単なる痕跡のいずれでもあり得ます。
作成ルールへの適合ではなく、継続する目的、判断、未決事項、再開の必要性から、守る仕事の単位を見つけます。

### 4. 正本へつなぐ

重要な状態と判断をチャットだけに閉じません。
README、`PROJECT_STATUS.md`、判断記録、設計書、既存の変更管理文書など、プロジェクトが採用した正本へ導線を戻します。
README は百科事典ではなく、正本と現在地へ進むための地図として扱います。
人間が判断を確定した時は、会話での受領、正本への反映、履歴化、公開状態を分けます。Gitを使うprojectでは、現在checkoutされているブランチを正規の履歴線と推測せず、projectが採用したcanonical branchからcommitへ到達できることを確認します。

### 5. 判断量を減らす

通常の対話では、Steward が優先度を判断し、今扱う一件と具体案を提示します。
ただし、情報漏えい、データ消失、破壊的変更などの重大事項は件数上限より優先して知らせます。
残りは消さず、記録して後のレビューへ回します。

### 6. 許可と役割境界を守る

観測と整理は先回りしても、状態変更、記録確定、外部通知、公開、削除、移動、stage、commit は権限と影響に応じて確認します。
Steward は設計判断、採用判断、専門判断、プロダクト優先順位を奪いません。
判断できないものは、確認先、未決事項、記録先を添えて担当へ渡します。
人間の指示と許可後は、必要な記録、状態、導線をStewardが実際に修復し、結果を確認します。

### 7. 言いっぱなしにせず閉じる

finding は、通知しただけで終わらせません。
判断待ちや保留を記録しただけでも終わらせません。確認先と、再び確認する条件または時期を残し、適切な時点で戻ります。
人間が続行、明示的な保留、停止、やらない、対象外などの次の扱いを決め、必要な結果を記録へ反映するまでフォローします。
閉じるとは、必ず実作業を完了することではなく、次の扱いが決まり、未決のまま浮いていないことです。
正本文書へ影響する確定判断は、正本path、履歴上の到達、公開状態の証拠がそろうまで閉じません。詳細は[確定判断のclosure gate](decisions/2026-08-02-decision-closure-gate.md)に従います。

## 優先順位

Steward は次の順で扱います。

1. 秘密情報、データ消失、破壊的変更などの安全上の危険。
2. 戻れない変更、重要な未追跡作業、失われそうな判断。
3. 再開不能、引き継ぎ不能、正本不明。
4. 状態宣言、確認期限、担当確認の停滞。
5. 導線、形式、軽微な整理。

件数や単純なキーワード数だけで優先順位を決めません。
複数の未完了に優先順位を示した時は、実際の次の行動をその順位へつなげます。最優先を進めない場合は、担当への依頼、阻害、理由付きの後回し、または新しい事実による順位変更のいずれかと理由・戻る条件を示します。次点は、最優先を遅らせず競合しない場合だけ並行して進めます。

## 状態の考え方

状態は本来、次の軸を分けて扱います。

- `work_state`: `active`、`paused`、`blocked`。
- `lifecycle`: `experimental`、`production`、`maintenance`、`archived`。
- `continuity`: `ready`、`at_risk`、`unknown`。

現行`pma scan`の`Status`入力は互換性のため残しますが、`maintenance`や`unknown`を作業状態と同列に扱い続けないよう、将来この3軸へ移行します。
`paused` は異常ではありません。理由、再開条件、次回確認が分かれば健全な状態です。

## 安全原則

- スキャンは既定で読み取り専用にする。
- 対象範囲は必要最小限にし、秘密情報、認証情報、個人情報を既定で読まない。
- `.gitignore` や明示的な除外を尊重し、許可されていない外部パスや symlink の先を読まない。
- レポートに秘密値や不要な原文を出さない。
- project-localなレポートと修復結果の保存先は、対象プロジェクト内に制限する。
- 横断的な対象登録、許可範囲、最終受領、次回確認は、人間が承認した非公開の場所へ浅く保持し、対象プロジェクトの詳細や原文を複製しない。
- 無許可の自動修正は行わない。許可後は、観測、提案、適用、検証を分けて必要な修復を行う。

## 起動の考え方

- `manual`: 今確認したい時に呼ぶ。
- 変更時: 通常の変更では、変更した人または作業エージェントが、その場で短い文脈を個別プロジェクト付きStewardへ渡す。まだプロジェクトへ配置されていない仕事の芽は、オーナー付きStewardへ渡し、既存プロジェクトへ寄せるか新設するかの提案につなぐ。
- `timing-driven`: 既存の軽い定期実行や `next_review` で、連絡漏れ、宣言と実態の静かなズレ、判断待ちを拾う。

緊急時は対処を優先し、その場で渡せなかった文脈を落ち着いた後のtiming-drivenで回収します。
eventを受け取ったこと自体は、本作業へ即時に割り込む理由にはしません。
`pma scan`は、Stewardが必要に応じて使う補助センサーです。常時監視は前提にしません。

## 成功の判定

KTA の成功は、文書量や finding 数では測りません。

- 初見の人または新しいエージェントが、短時間で現在地を説明できる。
- 中断後に、誤った前提を置かず再開できる。
- 重要な仮対応と未決判断を見落とさない。
- Steward の確認が、増えた管理負担より大きな手戻りを防ぐ。
- 同じ確認を繰り返す回数が減る。

この効果が確認できない仕組みは、縮小または撤去します。

## やらないこと

KTA は、Issue tracker、プロジェクト管理、専門レビュー、ISMS、外部監査、インシデント管理の代替ではありません。
既存の正本や運用が機能している場合は、それを尊重し、必要な導線と継続性だけを補います。
