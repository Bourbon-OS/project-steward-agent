この文書は、Project Steward Agent の初期 MVP 要件を定義します。最初のバージョンでは、自動修正ではなく、ローカル Git プロジェクトの検知と Markdown 報告に集中します。MVP のスコープ判断は [MVP計画](mvp_plan.md) を優先します。

## MVP 要件

MVP は、1 つのローカル Git プロジェクトをスキャンし、プロジェクトの足場状態を簡潔に報告できる必要があります。

最低限の機能:

- `pma scan` をローカルで必要時に実行できる。
- リポジトリルートを特定し、Git リポジトリであることを確認する。
- `git status --short` で modified、staged、untracked を読む。
- 直近のコミット日時を読む。
- `README.md`、`PROJECT_STATUS.md`、`.project-agent.yml` の存在を確認する。
- `PROJECT_STATUS.md` から `status`、`Last updated` または `last_reviewed`、任意の `next_review` を確認する。
- `last_reviewed` / `next_review` は MVP では推奨項目とし、欠落しても警告に留める。
- 宣言された状態とリポジトリ活動の明らかな不一致を検知する。
- `active` のまま長期間活動がない場合、継続・休止・中止・保留の宣言を促す相談候補にする。
- 重要そうだが tracked ではないファイル、または管理外に見えるファイルを検知する。
- `TODO`、`FIXME`、`あとで`、`未定`、`仮`、`要確認` などのキーワードを検知する。
- README から `docs/` 配下への導線があるかを、安い文字列チェックで確認する。
- README からプロジェクト管理方法、状態宣言、判断ログ、Steward運用への導線があるかを確認する。
- 中核ドキュメントの欠落を検知する。
- severity、evidence、ご確認いただきたいこと、次の提案を含む findings を報告する。
- 週次レビューや一覧レポートの優先対応は最大 3 件に制限する。
- 通常対話では、人間に聞く確認事項を原則 1 つに絞る。
- 複数の足場ToDoを検知しても、Steward 側で優先度を判断し、ご確認いただきたいこと 1 件を選ぶ。
- 通常は、Steward が具体案を出し、「していいですか？」「してよろしいですか？」の形で許可を取る。
- ユーザーに「どうしますか？」と丸投げしすぎない。
- 1 つの問いに対して、必要なら最大 3 つの選択肢を提示する。
- 影響が大きい判断、ユーザーの意図が不明な判断、複数の選択肢が自然な判断では、決め打ちしすぎず選択肢を出す。
- 分からないこと、専門判断が必要なこと、プロジェクト固有の意図確認が必要なことは断定せず、確認先、確認方法、仮置き状態を提示する。
- 必要なら担当者、担当チャット、Codex、人間へ確認や引き渡しを行うための依頼文を提案する。
- 通常時は軽量スキャンで済ませる。
- Stewardからのご提案は、MVP ではルールベースで生成できる範囲から始める。
- LLM review は MVP には含めず、将来拡張として扱う。

## 起動タイミングと実行モデル

MVP は、`pma scan` を manual / event-driven / timing-driven の共通入口として扱います。常時 daemon や GitHub Actions 前提の実行にはしません。event-driven と timing-driven は、自動化基盤ではなく、まず人間または Codex が `pma scan` を呼ぶ運用モデルとして定義します。

### manual

manual 実行は、人間または Codex が必要な時に明示的に実行できる必要があります。

例:

- `pma scan --path .`
- `pma scan --path <project>`

### event-driven

event-driven 実行は、足場が崩れやすい作業イベントの後に軽く支えるために使います。MVP では完全自動イベント監視を作らず、人間または Codex がイベント後に `pma scan` を呼ぶ運用にします。

想定イベント:

- Codex がファイルを変更した後。
- 設計、実装、構築作業で方針変更や暫定対応が生まれた後。
- 調査、検証、デバッグ、試行錯誤で複数の道を試した後。
- 小さな修正、慣れた作業、チャットや口頭合意など、軽く扱われやすい変更の後。
- 障害対応やトラブル対応で緊急設定変更、暫定回避、切り戻しが発生した後。
- 引き継ぎ、担当変更、別チームへの依頼など、人に渡る作業の後。
- レビューを受けた後。
- 未追跡ファイルが増えた時。
- コミット前またはコミット後。
- `PROJECT_STATUS.md` を更新した後。
- 設定変更や本番作業の変更計画書、作業結果報告が作られた後。
- 新しい運用ファイルや docs を追加した後。

運用例:

- Codex 作業後は、変更後に `pma scan --path .` を実行し、足場リスクを確認する。
- コミット前は、未追跡ファイルや `PROJECT_STATUS.md` のズレがないか確認する。
- レビュー後は、レビュー結果が記録済みか、反映待ちかを確認する。
- 新規 docs 追加後は、README 導線や `PROJECT_STATUS.md` の更新が必要か確認する。
- 変更計画書や作業結果報告がある場合は、それを置き換えず、プロジェクト側の状態宣言や判断ログから辿れるか確認する。
- 障害報告やインシデント管理がある場合は、それを置き換えず、緊急変更の内容、理由、戻し方、恒久対応、反映先へ辿れるか確認する。

event-driven 実行で出す確認は、短く、低ノイズにします。通常対話では、複数の確認をまとめて投げず、ご確認いただきたいこと 1 件に絞ります。たとえば「新しい `docs/` が増えています。まず `README.md` に導線を足す案だけ作ってよろしいですか？」のような Stewardからのご提案にします。

### timing-driven

timing-driven 実行は、日次・週次・`next_review` 前後など、決まったタイミングで忘れられた足場を拾うために使います。MVP では常駐 daemon は作らず、手動実行または OS スケジューラ / 将来の GitHub Actions 候補として扱います。

例:

- 週次レビューで `pma scan --path <project> --save-report` を実行する。
- `next_review` 到来時に `PROJECT_STATUS.md` の状態を確認する。
- `active` のまま止まっているプロジェクトに、継続・休止・保留の確認を出す。

timing-driven 実行では、たとえば次を検知します。

- `active` のまま動いていない。
- `next_review` を過ぎている。
- untracked files が溜まっている。
- `README.md` や `PROJECT_STATUS.md` が古い。
- 以前の finding が未判断のまま残っている。
- 前回の依頼、担当確認、判断待ちが、解決・保留・休止・中止・記録済みなどの状態に閉じていない。

担当確認中・結果待ち・次回確認は timing-driven 実行で拾いやすくします。ただし MVP では、未完了管理の自動追跡はまだ行いません。まずは `PROJECT_STATUS.md` や adoption メモに残したものを、人間または Codex が確認する運用にします。

### Ashibaを救う基本要件

Steward は、足場が不安定になる状況を次の考え方で支える必要があります。

- 作業中の進行、障害対応、探索、構築を記録のために止めない。
- その場で残せる場合は、時刻、対象、仮か正式か、後で見る場所などの最小項目に留める。
- Git 差分、コミット、未追跡ファイル、ログ、チケット、チャット、会議メモ、変更計画書、障害報告など、既存の痕跡から文脈候補を拾える設計にする。
- 拾った候補は、README、`PROJECT_STATUS.md`、`DECISIONS.md`、`logs/`、既存の変更管理文書など、後で戻れる場所へつなぐ。
- 仮対応、暫定設定、TODO、あとで反映するものが、仮だったことを忘れられたまま正式な前提になっていないかを確認できる。
- ユーザーへは足場ToDoを一括で投げず、今確認すべき 1 件と具体案に圧縮する。
- 指摘した足場ToDoは、記録済み、保留、要確認、次回確認、不要などの状態になるまで見届ける。

状況別には、危ないときや急ぐときは事後回収を優先し、迷っているときは試した道と捨てた道を残し、軽く見ているときや慣れているときは変更の性質から拾い、流れで決まったときや人に渡るときは決定、保留、確認先、反映先を短く残せる必要があります。

### 会議由来の足場

会議は、判断、保留、論点、アイデアの元になった文脈が生まれるイベントとして扱います。ただし MVP では、会議監視、録音、文字起こし、議事録自動生成は行いません。

将来拡張では、既存の会議メモ、議事録、チャットログ、文字起こしが渡された場合に、次を足場として確認できるようにします。

- 決まったこと。
- 今は決めないと決めたこと。
- 保留理由、制約、懸念。
- その場で生まれたアイデアや仮説。
- 次に確認すること、反映先、見るべき資料。

Steward は「議事録を作れ」と迫るのではなく、足場として必要な最小項目だけを短く残す提案を出します。録音や文字起こしを扱う場合は、参加者同意、機密境界、保存先、保持期間のルールを先に確認します。

### 実行モデルでやらないこと

MVP では次を作りません。

- 常駐 daemon。
- ファイル監視。
- 自動 Git hook 挿入。
- GitHub Actions 自動追加。
- OS スケジューラ自動登録。
- 通知 bot。
- 会議監視、録音、文字起こし、議事録自動生成。
- システム変更計画書、承認ワークフロー、作業結果報告の代替。
- インシデント管理、障害報告、ポストモーテムの代替。
- 複数プロジェクト横断の Portfolio 実行。

## 共通チェック項目

多くの Git プロジェクトに共通して適用するチェック項目です。

- Git リポジトリが存在し、状態を確認できる。
- working tree の状態が読み取れる。
- `README.md` が存在し、プロジェクトの目的を説明している。
- `PROJECT_STATUS.md` が存在し、現在の状態を宣言している。
- `.project-agent.yml` の有無を確認できる。
- `PROJECT_STATUS.md` の `status`、`Last updated` または `last_reviewed`、任意の `next_review` を確認できる。
- 継続的な設計・運用メモが必要なプロジェクトでは `docs/` が存在する。
- 重要なファイルが tracked であるか、意図的に ignored になっている。
- untracked files が一時ファイル、無害なファイル、または説明済みのファイルとして扱える。
- 直近の活動と宣言された状態が矛盾していない。
- 長期間動いていない `active` プロジェクトが、`paused`、`blocked`、`archived`、または継続予定として説明されている。
- `TODO`、`FIXME`、`あとで`、`未定`、`仮`、`要確認` などの足場キーワードを検知できる。
- README から `docs/` 配下への導線があるかを安く確認できる。
- 判断が蓄積し始めた場合、`DECISIONS.md` などの決定記録を提案できる。ただし MVP では必須にしない。
- 繰り返しレビューや実行記録が必要になった場合、`logs/` などの運用ログを提案できる。ただし MVP では必須にしない。
- 既存の変更計画書、作業計画、作業結果報告がある場合、それを正本として扱い、プロジェクト側の入口や判断ログから辿れるかを確認できる。
- 構築中、実装中、設計中に生まれた方針変更、暫定対応、仕様の明確化、反映待ちの差分を足場ToDoとして扱える。
- 障害対応や緊急設定変更で生まれた暫定変更、切り戻し、恒久対応、反映待ちの差分を足場ToDoとして扱える。
- 危ないとき、急ぐとき、迷っているとき、軽く見ているとき、慣れているとき、流れで決まるとき、人に渡るときに生まれた未記録の判断や経路を足場リスクとして扱える。
- 仮の道が正式化すること自体は否定せず、仮だったことが忘れられたまま前提になる状態を検知対象にできる。

## プロジェクト固有チェック項目

プロジェクト固有の期待値は、エージェント本体へハードコードせず、プロジェクト側で宣言できるようにします。MVP では `.project-agent.yml` の存在を確認し、存在する場合だけ最小項目を読みます。

MVP で読む最小項目:

- `project.name`
- `project.status_file`
- `project.source_of_truth`
- `checks.required_files`
- `stale.active_days`
- `stale.paused_days`
- `stale.archived_days`
- `report.max_priority_actions`
- `report.output_dir`

stale 判定の未設定時初期値は、`active` 14日、`paused` 30日、`archived` 180日とします。

将来の `.project-agent.yml` では、たとえば次のような項目を定義します。

- 必須ドキュメント
- 重要ディレクトリ
- tracked にすべきでない生成物
- 変更時に必ず確認したいファイル
- 期待するブランチ名やコミット運用
- プロジェクト固有の状態ルール
- 既知の一時ファイルやローカル専用ファイル
- `active` や `paused` のレビュー頻度

エージェントは、プロジェクト固有の期待値が欠けている場合や破られている場合に報告します。ただし、ルールを黙って作成・書き換えません。MVP では `.project-agent.yml` の欠落を致命的エラーにせず、設定未整備の finding として扱います。

## 状態種別

各プロジェクトは、原則として 1 つの状態を宣言します。

- `active`: 作業が進行中、または近いうちに進む予定がある。
- `paused`: 作業は意図的に止めており、記録された文脈から再開できる。
- `blocked`: 名前の付いた依存、判断、外部条件が解消されるまで進められない。
- `maintenance`: 積極的な開発中ではないが、修正、更新、定期確認の対象である。
- `archived`: 意図的に終了または参照用に保存している。
- `unknown`: 状態を判定できない。状態宣言がない、古い、または矛盾している。

`paused` は正常な状態です。危険なのは `unknown` です。

状態を変更すべきか迷う場合、エージェントは断定せず、継続・休止・中止・保留のどれとして扱うかを人間に確認します。

## 出力レポート要件

通常レポートは、読み終えてすぐ行動できる長さにします。

MVP では、レポートを標準出力に表示します。必要に応じて、`reports/footwork_review_YYYY-MM-DD.md` に保存できる形にします。

必須セクション:

- 全体の状態判断
- 根拠の要約
- findings
- 最大 3 件の優先対応
- 人間に確認したい質問。通常対話に持ち出す場合は原則 1 つ。
- 任意の提案

通常レポートは説教調にしません。監査官のように違反を裁くのではなく、足場係として「どこを確認すれば再開しやすくなるか」を示します。

各 finding には次を含めます。

- severity
- 対象ファイルまたは対象領域
- 観測された evidence
- なぜ重要か
- 人間が判断すべきこと、または次に取る行動

レポートでは、事実と解釈を分けます。たとえば「file X が untracked である」は事実であり、「これは未記録作業かもしれない」は解釈です。

## フォローアップ要件

Steward は、問題を見つけて通知するだけで終わらないようにします。

- 各 finding には、少なくとも 1 つの次の一歩を含める。
- 対応を強制せず、通常は具体案を出して許可を取る。
- 大きな判断では選択肢を提示する。
- 選択肢は、複数の質問ではなく 1 つの判断に対する選択肢として提示する。
- 未完了の項目は、解決・保留・休止・中止などの状態にできるようにする。
- 判断結果を `PROJECT_STATUS.md`、`DECISIONS.md`、または `logs/` に残す提案を出せるようにする。
- 一度指摘した項目は、次回以降のレポートで再確認できるようにする。
- クローズ済み、保留中、休止中、未判断を区別する。
- フォローアップの言葉は短く、分かりやすく、責めないものにする。
- 処理と報告を分け、スキャン中の細かな観測をそのまま流さない。
- 大きめの依頼では、必要に応じて細分化とクローズ条件を短く示す。

## 確認・引き渡し要件

Steward は、分からないことを分かったふりで決めません。専門判断やプロジェクト固有の意図確認が必要な場合は、担当者、担当チャット、Codex、人間への確認や引き渡しを提案します。Steward は専門担当ではなく、足場を見る役割に集中します。

- 確認先、確認したいこと、確認理由を短く示す。
- 必要なら「確認用の依頼文を作ってよろしいですか？」と提案する。
- 未決のまま放置せず、必要なら「要確認」として仮置きする。
- 「要確認」には、何が未決か、誰に確認するか、確認後にどこへ記録するかを含める。
- 確認結果は、`PROJECT_STATUS.md`、`DECISIONS.md`、`logs/` などへ反映できる形にする。
- Steward は担当者の役割を奪わず、足場を見る役割に集中する。
- 担当へ渡す場合も、依頼文、仮置き状態、次回確認の置き場所を残す。

確認や引き渡しを出した後の要件:

- 「依頼しました」「確認してください」で終わらせない。
- 依頼、確認、判断待ちの状態を記録する。
- 次回以降のレビューで、結果が返ってきたかを確認する。
- 結果が返っていれば、正本ドキュメントやログへ反映する案を出す。
- 返ってきていなければ、軽く再確認するか、次回確認日に回す案を出す。
- 未決のまま放置せず、担当確認中、結果待ち、次回確認、保留、記録済みなどの状態にする。

望ましい確認文:

- 「ここは私だけでは判断しきれません。このプロジェクトの担当に確認してから、結果だけ記録してよろしいですか？」
- 「ここは私だけでは判断しきれません。担当に確認するための依頼文を作ってよろしいですか？」
- 「これは専門判断に近いので、担当確認中として残してよろしいですか？」
- 「これは実装判断に近いので、Codex 側で確認した方がよさそうです。確認用の依頼文を作ってよろしいですか？」
- 「ここは足場上は未決ですが、急いで決めるより担当確認が安全です。一旦『要確認』として残してよろしいですか？」
- 「前回、担当確認に回した件があります。結果だけ記録してよろしいですか？」
- 「この件はまだ判断が戻っていないようです。一旦『担当確認中』として残してよろしいですか？」
- 「確認結果が戻っているなら、`PROJECT_STATUS.md` に 1 行だけ反映してよろしいですか？」
- 「未決のまま残っています。急がないなら、次回確認日に回してよろしいですか？」

望ましいトーン:

- 「新しい `docs/` が増えています。`README.md` に 1 行だけ導線を足してよろしいですか？」
- 「今回の判断は後で経緯が分からなくなりそうです。`DECISIONS.md` に短く残していいですか？」
- 「`active` のまま少し止まっています。いったん `paused` にして、`next_review` を来週にしてよろしいですか？」
- 「このプロジェクトは `active` のまま 14 日止まっています。継続・休止・保留のどれにしますか？」

避けるトーン:

- 「どうしますか？」
- 「`README.md` を更新しますか？」
- 「`PROJECT_STATUS.md` をどうしますか？」
- 「期限です。対応してください。」
- 「未対応です。すぐ修正してください。」
- 「状態管理ができていません。」

## 段階的提示と相談要件

Steward は、ToDo の管理をユーザーへ丸投げしません。

- 検知した問題をすべて同列に並べない。
- 通常対話で提示する次の管理作業は原則 1 件に絞る。
- 週次レビューや一覧レポートでは、優先対応を最大 3 件まで示せる。
- 3 つまで出してよいのは、複数の質問ではなく、1 つの判断に対する選択肢の場合である。
- 必要なら「今はこれだけでよい」と明示する。
- 残りの項目は記録し、折を見てフォローする。
- 指摘を人間への ToDo 投げにせず、Steward 側で優先度を判断する。
- 判断を増やさず、判断を軽くする。
- 通常は Steward 側がおすすめの一手を具体化し、許可を取る。
- 「しておきますか？」よりも、「していいですか？」「してよろしいですか？」を基本にする。
- ユーザーの意図が不明な場合や影響が大きい場合は、勝手に決め打ちしすぎない。
- 足場ToDoを覚え続け、優先順位を判断し続ける負担をユーザーへ丸投げしない。
- 作るToDoは推進力があるものとして扱い、Steward は主に推進力が弱い足場ToDoを拾う。
- 足場ToDoが作るToDoの継続を妨げそうなときだけ、短く相談する。
- ユーザーの状況、作業量、抱えているプロジェクト数を考慮する。
- 進める、止める、保留する、休止する、破棄するなどの選択肢を出す。
- 全部整理しなくてよい場合は、まず 1 つだけ決める形にする。
- プロジェクト初期や好みが不明な間は、暗黙の価値観を推測して勝手に整理しない。
- ユーザーの短い返答や活動時間の変化から、心理状態を断定しない。

ユーザーから頼みごとをされたときは、否定から入らないことを原則にします。

- 「できません」から始めず、まず前向きに受け止める。
- 「先にこれをやってください」と命令形にせず、足場への影響を短く伝える。
- 注意点を述べるだけでなく、進め方の具体案を出して許可を取る。
- 影響が大きい場合は選択肢を出す。
- 迎合せず、必要な指摘は短く伝える。
- 相談の入口を閉じず、次に決めることを小さくする。

## 非機能要件

- Local-first: MVP はホストサービスを必須にせず、ローカルリポジトリだけで動く。
- Read-oriented by default: スキャンはデフォルトでファイルを変更しない。
- Local invocation first: MVP は必要時にローカルで実行できることを優先する。
- Shared scan entrypoint: `pma scan` を manual / event-driven / timing-driven の共通入口として扱う。
- Human-triggered events first: event-driven は、作業後に人間または Codex が呼ぶ運用から始める。
- Situation-aware footwork: 工程名だけでなく、危険、急ぎ、探索、軽視、慣れ、会話、人への引き渡しという状況を足場リスクとして扱う。
- Recover before demanding: 足場が崩れやすい状況では、まず痕跡から回収し、ユーザーには最小確認だけを出す。
- Scheduled operation before automation: timing-driven は、週次や `next_review` 前後に呼ぶ運用設計から始める。
- Cheap scan first: `git status`、最終コミット日、untracked files、`PROJECT_STATUS.md`、`README.md` など、スクリプトで確認できる事実を先に見る。
- No MVP LLM review: MVP では LLM review を行わず、必要になれば将来拡張として意味づけ、優先度判断、Stewardからのご提案生成、分類案作成に限定して検討する。
- Low usage: 常時使用量を食い続けない。
- Low noise: ユーザーの注意を奪いすぎず、通常対話で聞くことは原則 1 つにする。
- Action-report separation: 裏側で観測と整理を行い、表側では結論、理由、次の一手に圧縮して返す。
- Permission-based proposal: 通常は具体案を出し、「していいですか？」「してよろしいですか？」の形で許可を取る。
- Reduce decision load: 自由度の高い質問を避け、ユーザーの判断量を増やさない。
- Low friction: 管理の煩わしさをユーザーに出しすぎない。煩わしいと感じるなら設計を見直す。
- Explainable: 各 finding は根拠を示す。
- Conservative: 根拠が弱いときは断定を避ける。
- Small reports: 通常出力は網羅性よりも行動しやすさを優先する。
- Non-preaching: レポートは責任追及ではなく、確認と提案を中心にする。
- Approachable: 「困ったらまず相談してみよう」と思える応答を目指す。
- Non-compliant-flattery: 相談しやすさを、迎合や無条件の肯定と混同しない。
- Supportive correction: 必要な指摘は行うが、責めず、次の一歩と一緒に示す。
- Useful uncertainty: 分からない場合でも、確認すべき場所、見るべきファイル、考えられる仮説を出す。
- Escalate instead of pretending: 分からないこと、専門判断、プロジェクト固有の意図確認は抱え込まず、確認先と確認方法を示す。
- Handoff with context: 担当者、担当チャット、Codex、人間へ引き渡す場合は、確認事項、理由、仮置き状態、記録先を添える。
- Handoff follow-up: 引き渡した依頼、確認、判断待ちは、次回以降に結果を確認し、記録済み、保留、次回確認などの状態に閉じる。
- Trust through support: 嫌われないことを相談継続の品質として扱う。ただし、迎合ではなく、責めずに支えることで信頼されることを目指す。
- Follow-through: 指摘した項目を言いっぱなしにせず、解決・保留・休止・中止などの状態になるまで追跡できるようにする。
- Responsible behavior without ownership: AI は最終責任を取れないが、責任感のある振る舞いとして、次の一歩と閉じ方を示す。
- No ToDo dumping: ToDo の管理をユーザーへ押し付けず、Steward が優先度を判断して相談する。
- Footwork ToDo awareness: 記録、状態宣言、未完了のクローズ、休止明示、会議由来の判断・保留・アイデアの元になった文脈の記録を足場ToDoとして扱う。
- Footwork-first detection: 作るToDoそのものではなく、後回しにされやすい足場ToDoを優先して検知する。
- Do not block making: 作る意欲を止めず、足場が沈みそうな箇所だけを短く相談する。
- Priority ownership: 足場ToDoの記憶と優先順位づけをユーザーへ丸投げしない。
- Single-focus dialogue: 通常対話では、ご確認いただきたいこと 1 件に絞る。
- Report cap: 週次レビューや一覧レポートでは、優先対応を最大 3 件に絞る。
- Choice cap: 1 つの判断に対して、必要なら最大 3 つの選択肢を出す。
- Concrete recommendation: Steward 側がおすすめの一手を具体化してから確認する。
- Progressive disclosure: 残りは記録して段階的に扱う。
- Explicit preference memory: 好みや運用ルールを使う場合は、暗黙に推測し続けず、プロジェクト内の明示的で編集可能な情報に寄せる。
- No private-state inference: ユーザーの心理状態を断定せず、活動のズレはプロジェクト状態の仮説として扱う。
- Yes-but response: 否定から入らず、前向きに受け止めたうえで足場への影響と具体案を示し、必要なら選択肢を出す。
- Internalized management patterns: ISMS、棚卸、外部監査、証跡管理、状態管理、定期レビュー、例外管理などの型は内側で使い、ユーザーには必要な確認だけを短く提示する。
- Digest, do not dump: 管理ルールを読ませるのではなく、噛み砕いて「この内容を短く記録してよろしいですか？」の形で相談する。
- Extensible: scanner を大きく書き換えずに、プロジェクト固有チェックを追加できる。
- Tool-friendly: 将来は人間向け Markdown と機械可読形式の両方を出せるようにする。

## やらないこと

MVP では次を行いません。

- ISMS、セキュリティ監査、コンプライアンスレビューの代替
- GitHub Actions 前提の運用
- GitHub Issue や PR への自動通知
- Portfolio Steward Agent
- Backstage 相当のポータル
- プロジェクト内の全 ToDo 管理
- プロダクト優先順位の決定
- ドキュメントの自動書き換え
- 自動的な stage、commit、delete、move
- 自動 close / archive
- `DECISIONS.md` の必須化
- コード品質の詳細評価
- CI 全体の実行や依存関係更新ワークフローの代替
- 依存更新 bot、Renovate 相当の更新エンジン、脆弱性 alert bot
- OpenSSF Scorecard 相当のセキュリティスコアリング
- LLM review
- 常駐 daemon
- ファイル監視
- 自動 Git hook 挿入
- OS スケジューラ自動登録
- 通知 bot 化
- 執事キャラクター化
- issue tracker、プロジェクト管理ツール、アーキテクチャ審査会の代替
- 既存ツールで解ける問題の再実装
