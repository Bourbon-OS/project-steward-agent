# Ashiba Steward 要件定義

- 文書状態: 規範となる基準線
- 対象: Ashiba Steward全体
- 最終確認日: 2026-08-16
- 網羅性: Ashibaリスクとの抜け漏れ確認待ち

この文書は、Ashiba Steward全体が満たすべき機能要件、Stewardの振る舞い、非機能要件、受け入れ条件を定めます。
特定のCLI、AI、固定チャット、scheduler、クラウド、開発上の区切りを、Ashiba Steward全体の完成条件にしません。
現時点の正本となる基準線ですが、既存のリスクと検討候補との抜け漏れ確認は未完了です。正本化を、要件の完全性または実装完了の証拠にしません。

規範は[KTA原則](principles.md)、背景と価値仮説は[コンセプト](concept.md)、役割と構成は[設計](design.md)、現在の実装・検証・運用状態は[PROJECT_STATUS.md](../PROJECT_STATUS.md)を正本とします。
MVP計画（開発資料：`mvp_plan.md`、本配布では省略）は`pma`センサーを中心にした過去の実装計画と検証履歴であり、Ashiba Steward全体の要件や完成状態を定めません。

## 1. 目的

Ashiba Stewardは、異なる人間やエージェントが同じプロジェクトを並行・交代・中断しながら扱っても、Ashibaを見失わず、安全に再開・引き継ぎできる状態を支えます。

Ashiba Stewardが実現する価値は次です。

- 現在地、状態、正本、重要な判断、仮対応、未決事項、次の一手を追える。
- 短い中断、長期休止、タスク・チャット・担当エージェント・実行環境の交代後に、誤った前提を置かず再開できる。
- 足場が失われかけた時は早く気づき、既存の痕跡から文脈を復元し、必要な修復へ導ける。
- 許可後の修復を、正本反映、履歴、受領、結果確認、次の扱いまで閉じられる。
- 足場を守る負担を、そこで防げる手戻りや文脈喪失より小さく保つ。

ツールを置くこと、レポートを出すこと、finding数を増やすことは目的ではありません。
プロダクトとしての効果は、事情を知らない人または新しいエージェントが、通常運用の中でより早く、誤解なく、安全に戻れるかで判定します。

## 2. 最初の適用範囲

- 1人のオーナーが、AIとの壁打ち、フォルダ、Gitリポジトリ、複数のAIプロジェクトやタスクを使って、複数の個人プロジェクトを育てる運用を対象にする。
- Codex、ChatGPT、Claude Code、他のAI環境、人間のIDE作業を区別せず、Ashibaが必要な仕事を扱う。
- Gitプロジェクトを主対象にするが、Git未管理の候補、複数projectを含む箱、旧入口、単なる痕跡を、名前だけでprojectと同一視したり無視したりしない。
- 会社組織、顧客、サービス、案件、施策の分類とportfolio管理は、この段階の対象外とする。

## 3. 役割と責任境界

### 3.1 オーナー

- プロダクト、創作、研究、設計、採否、優先順位などの専門判断と最終判断を持つ。
- 対象、読み取り範囲、変更、外部通知、公開など、必要な権限を与える。

### 3.2 Butler（オーナー付きStewardの内部呼称）

- オーナーが承認したプロジェクトと候補取得元の浅い地図、確認先、導入状態、受領、判断待ち、次回確認を扱う。
- プロジェクトの深い状態を中央へ複製せず、必要な確認を該当Caddieまたは担当へ渡す。
- オーナー付きStewardによる受領確認と、プロジェクト内の正本への反映確認を分け、オーナーへ結果が戻るまで追う。
- 通常確認、定期確認、変更連絡の受領後は、現在の1件だけでなく対象一覧全体から未完了と今進める価値が高い対応を再選別する。
- Caddieから、活動、未完了、具体的な次の作業、外部での継続が不明であることを受け取り、他プロジェクトとオーナーの管理負担を浅く照合して、プロジェクトを休止する案をオーナーへ提案する。

### 3.3 Caddie（個別プロジェクト付きStewardの内部呼称）

- 1つのprojectに付き、承認済み範囲の痕跡を調べ、事実・推測・不明を分ける。
- 文脈復元、具体案、許可後の修復、結果確認、後日の確認を担当する。
- 1projectにつき1つの論理的な固定窓口とし、個別taskごとに重複配置しない。
- プロジェクト担当、Caddieの担い手、利用するAI・ツール・実行環境が変わっても、足場管理の責任と記録を引き継ぐ。後任が、現在地、判断とその理由、未完了事項、次の行動、後日の確認を回収し、続きから担当できるようにする。
- 固定するのはプロジェクトごとの責任の所在と継続性であり、同じ人、AI、チャット、常駐プロセスを使い続けることではない。引き継ぎによって許可範囲を自動的に広げない。
- 受け取った1taskだけでproject全体を判断せず、把握済みの複数task、変更のまとまり、依存関係、未完了をプロジェクト内の正本と照合する。
- 活動、未完了、具体的な次の作業の有無を確認してButlerへ返す。プロジェクト内の通常の提案はオーナーへ直接行えるが、プロジェクトを休止する案はCaddieから直接提案せず、Butlerが横断状況と照合してオーナーへ提案する。

### 3.4 補助機能と実行環境との接続部

- `pma scan`、`pma followups`、`pma handoff`などはStewardが使う補助機能であり、Ashiba Steward全体ではない。
- 固定タスク、固定チャット、Skill、CLI、定期実行、クラウド、人間の手順は交換可能な接続部とする。
- いずれかの部品、接続部、テスト群が完成しても、Ashiba Steward全体の完成を意味しない。

### 3.5 開発面と実運用面

- Ashiba Stewardを別々の製品へ分割せず、開発面、実運用面、対象プロジェクト内を、正本と書き込み権限の異なる三つの面として扱う。
- 開発面は、公開可能な要件、設計、Skill、ソース、試験、配布物を扱い、正式履歴の基準ブランチを正本とする。非公開の実運用対象一覧、private locator、対象プロジェクトの深い原文を保持しない。
- 実運用面は、オーナーが許可した非公開の浅い対象一覧と実行接続部を扱う。製品コード、規範文書、対象プロジェクトの深い正本を直接変更しない。
- 各対象プロジェクト内は、そのプロジェクトの現在地、判断、作業履歴、許可後の修復結果の正本を持つ。Butlerへ深い内容を複製しない。
- 実運用で成立した不足は、private locatorや不要な原文を除いた再確認可能な根拠として開発面へ戻す。開発面で確認・修正・試験した結果は、識別可能な版として実運用面へ渡し、同じ事象または後続観測で結果を確認する。
- 実行接続部へ運用手順本文を複製せず、基準ブランチまたは配布済みartifactのSkillを正本にする。Butlerが版を確認したことと、Caddieが同じ本文を読めることを分け、受け手が確認できない版を最新版と推測しない。

## 4. 機能要件

### 4.1 予防

#### FR-PRE-01 projectの足場を接続する

- Butler側の登録、プロジェクト内の入口、承認済みの読み取り範囲がそろった時だけ、Caddieを設置済みとする。
- 入口から、現在地、正本、判断記録、Caddieの役割、起動理由、許可境界、記録先へ辿れるようにする。
- Caddieを使う依頼では、共通Skillを承認済み範囲から直接確認できる、実行環境から本文と版を確認できる、または今回に必要な短い作業契約を依頼内で受け取る、のいずれかを実行前に確認する。版の識別子だけを渡した状態は接続済みとしない。
- 既存の入口文化と正本を優先し、READMEや新しい管理ファイルを一律に追加しない。
- プロジェクト、フォルダ、リポジトリ、AI上のプロジェクト、タスク、チャット、箱、旧入口、痕跡を同一視しない。

#### FR-PRE-02 文脈を薄く残す

- 変更連絡時には、時点、対象、変更または節目、仮か正式か、理由、根拠、次に必要な判断のうち、後で戻るために必要な最小情報だけを残せる。
- Git、Issue、Pull Request、ticket、log、chatなどに十分な痕跡がある場合は、内容を別の管理文書へ重複転記せず、導線でつなぐ。
- 緊急時や集中作業中に詳細記録を強制せず、落ち着いた後に回収できる再開の目印または後日の確認予定を残す。
- プロジェクトごとに、現在のフェーズ、状態、ブロッカー、オーナー判断の要否、次の行動、最後に確認した結果へ短く到達できる、現在値を答える入口を1つ持つ。全仕様や全履歴を1ファイルへ集約する意味ではない。
- 閉じた履歴、詳細ログ、終了済み判断、個別結果を現在地へ蓄積せず、既存の履歴または正本へ導線でつなぐ。README、要件、計画、報告書へ同じライブ値を複製しない。

#### FR-PRE-03 状態と再開条件を持つ

- work state、lifecycle、continuityを混同しない。
- `paused`、`blocked`、判断待ち、保留には、理由、再開条件、確認先、次回確認のうち必要なものを持たせる。
- 状態がどれくらい続いているかは、確認できる証拠から下限または不明として扱い、根拠なく開始日を推測しない。

#### FR-PRE-04 確定判断を正本へつなぐ

- オーナーが採用、却下、保留、停止、対象外などを確定した時は、完了確認を必要とする変更連絡として扱う。
- 会話での受領、プロジェクト内の正本への反映、履歴化、正式履歴の基準ブランチからの到達、公開状態を別々に扱う。
- 外部AIの意見、提案、調査結果をオーナーの確定判断へ昇格しない。

#### FR-PRE-05 本作業へ不要に割り込まない

- 検出事項または変更連絡の受領と、本作業を止める判断を分ける。
- 介入時期を`即時対応`、`次の区切り`、`後日の確認`に分類する。
- 続行により情報流出、履歴消失、不可逆操作、正本混入、公開事故などの被害が広がる場合だけ即時対応する。
- 即時に割り込む場合は、元の目的、作業中の対象、未完了地点、再開時の最初の一手を残す。

#### FR-PRE-06 連絡漏れを安全網で拾えるようにする

- 手動、変更時、定期確認の入口を持つ。
- 変更時の連絡を主経路、定期確認を連絡漏れと静かなズレを拾う安全網とする。
- 定期実行の仕組みやPCが止まっていた期間を成功扱いせず、次に実行できた時に期限超過と未受領を拾える。
- 実行頻度と実行基盤は交換可能な接続部の設定とし、Ashiba Steward本体へ固定しない。
- 見守る導入済み対象には、連絡がなくても実態を確認する期限と確認先を持つ。休止中も見守りを終了したとは扱わず、影響と活動に合う間隔を定める。
- 期限超過後、限定した再確認でも実態や結果を回収できなければ、Butlerは確認不能の影響と回復案をオーナーへ報告・相談する。確認せず期限だけを先送りしない。
- 実行するモデル・推論量は、作業の難しさと利用可能な能力・費用に応じて選び、製品へ名前を固定しない。設定変更と品質・費用の効果確認を分ける。

### 4.2 検知

#### FR-DET-01 project境界とidentityの不明を検知する

- projectとlocatorの対応を確認できない場合は、検証済みと表示しない。
- 1つのlocatorが複数projectを含む可能性、複数locatorが同一projectを指す可能性を保持する。
- 対象外、非Git、権限不足、読取不能、未確認を区別する。

#### FR-DET-02 現在の機械的状態を検知する

- Git、作業ツリー、ステージ済み変更、未追跡ファイル、HEAD、ブランチ、直近コミットを、確認できる範囲で観測する。
- 必須ファイル、状態宣言、正本、入口導線、判断記録候補の有無を観測する。
- 機密対象、project外、symlink先、読取不能な対象を推測せず、観測不能として扱う。

#### FR-DET-03 状態と実態のズレを検知する

- 状態確認の鮮度とGit活動の鮮度を別々に評価する。
- `active`だが活動・確認がない、`paused`後も活動がある、`next_review`を過ぎた、状態値が欠落・未知・重複・不正などを区別する。
- 未コミットまたは未追跡の作業を、意味が不明なまま不要または問題と断定しない。

#### FR-DET-04 受領・反映・履歴・公開のズレを検知する

- オーナー付きStewardが受領済みでも、プロジェクト内の正本への反映が未確認または反映待ちなら閉じない。
- 判断記録が正式履歴ではないブランチに滞留している、コミットへの到達が不明、公開状態が不明などを区別する。
- ファイル保存、ステージ、コミット、正式履歴への到達、共有先への送信、タグ付け、公開を同じ完了状態として扱わない。

#### FR-DET-05 古い観測と観測中の変化を検知する

- 観測時点、対象、根拠の版、Git状態を持ち、現在状態との対応を確認できるようにする。
- 同じHEADだけを理由に、working tree、状態文書、設定、観測時刻も同じとみなさない。
- 観測中の変更により内容と履歴照合がずれた可能性がある場合は、断定せず再確認または不明へ戻す。
- 複数レコードを読む収集処理はレコードごとに新しい状態で解析し、欠落した項目へ直前レコードの値または暗黙の既定値を持ち越さない。欠落、空、未確認、確認済みの実値を区別する。
- 無関係な複数プロジェクトで予期しない値が不自然に一致した場合は、設定異常と断定せず、まず収集処理または表示処理の異常候補として扱う。

#### FR-DET-06 静かな放置と重複確認を検知する

- 未受領、不明、反映待ち、期限到来、再確認条件の成立を拾う。
- 前回と同じ根拠、同じ未決事項、同じ質問に変化がなければ、新しいfindingや質問として重複させない。
- 定期実行の欠測、停止、読取不能を「問題なし」としない。
- オーナーが示した緊急性と理由を未完了事項へ結び付け、障害または将来の確認日があっても元事項の完了まで選別対象から失わない。
- 横断対応では、導入済みの各プロジェクトを`対応済み`、`対象外`、`未確認`のいずれかへ根拠付きで照合し、照合行の欠落も拾う。

### 4.3 文脈復元

#### FR-REC-01 既存の痕跡から文脈候補を回収する

- 承認済み範囲のGit履歴、差分、未追跡物、状態文書、設計、判断記録、ログ、チケット、レビュー、引き渡し、チャットなどから必要最小限の痕跡を読む。
- projectの現在の作成ルールに合わない古い入口も、それだけで捨てない。
- 深い全文を中央へ複製せず、プロジェクト内の根拠への導線を保つ。

#### FR-REC-02 再開に必要な現在地を再構成する

復元結果は、確認できる範囲で次を説明できるようにする。

- projectの目的と対象。
- 現在の状態と、状態を確認した時点。
- 何を正本として読むか。
- 直近の重要な変更と、その根拠。
- 確定判断、仮対応、保留、未決事項。
- 作業中断点、再開条件、次の小さな一手。
- まだ確認できないことと、その確認先。

#### FR-REC-03 事実・推測・不明を分ける

- 観測した事実、そこからの解釈、提案、未確認を明示的に分ける。
- 痕跡に明記がないことを「存在しない」と断言しない。
- 相反する痕跡がある場合は、根拠なく一方を正しい現在値として選ばず、時点、版、正本性、確認先を示す。
- 失われた情報を創作して穴埋めしない。

#### FR-REC-04 実行環境や担当が変わっても復元できる

- 特定のチャット履歴、AIサービス固有の識別子、エージェントの記憶、ローカルにしかないGit履歴だけを唯一の復元経路にしない。
- 新しい人またはエージェントが、projectの入口と許可された痕跡から同じ現在地へ到達できるようにする。
- 復元に不足がある場合は、オーナーへ全履歴の再説明を求めず、最も重要な確認1件と具体案に圧縮する。

#### FR-REC-05 復元結果を再利用可能な足場へ戻す

- 復元した重要な現在値をchat回答だけに閉じず、既存の正本、状態、判断記録、履歴、入口へつなぐ修復案を作る。
- 復元結果そのものを新しい正本へ自動昇格せず、オーナーまたは担当の確認と許可を経る。

### 4.4 修復

#### FR-REP-01 最小の修復案を作る

- 何を、なぜ、どこへ、どの範囲で直すか、影響と確認方法を具体化する。
- 既存の正本、入口、Git、運用を再利用し、新しい管理物や重い制度を先に増やさない。
- 複数の問題を一括整理せず、現在の再開可能性に効く最小差分を優先する。

#### FR-REP-02 許可境界を守って適用する

- 読み取りと状態変更を分け、編集、ステージ、コミット、移動、削除、公開、外部通知などは権限と影響に応じた許可後に行う。
- 許可された対象ファイルと処理だけを変更し、既存の未追跡物、別作業、無関係な差分を含めない。
- 別のSteward、担当、エージェントが「オーナー承認済み」と伝えた事実だけでは、受け手の変更権限を増やさない。依頼元の表示は連携の手掛かりとし、許可の根拠とは分ける。
- ローカルで可逆な編集、試験、対象を限定したコミットは、受け手が確認できる元のオーナー発言または事前に承認された範囲と、対象、許可された操作、除外範囲、結果を返す地点が一致する場合、別タスクで同じ承認を求めず実行できる。元の承認を確認できない場合は、読み取りと具体案までに戻す。
- `git add .`を使わず、対象を明示する。
- Git初期化、初回commit、remote設定、専門判断など、Stewardの権限外の作業は担当へ渡す。

#### FR-REP-03 正本・履歴・導線・状態を修復する

- 必要に応じて、現在地、状態、判断、仮対応、再開条件、入口導線、受領・反映状態を正しい記録先へ反映する。
- Gitを使う場合は、関係する変更だけに限定したコミットとし、正式履歴の基準ブランチからの到達を確認できる形にする。
- 正式履歴ではないブランチ上の回復では、別作業を混入させず、元のブランチを破壊的に書き換えない。

#### FR-REP-04 専門判断を奪わない

- プロダクト、創作、研究、設計、採否、優先順位などをStewardが決めない。
- 判断が必要な場合は、確認先、確認事項、Stewardの推奨、許可後の担当と記録先を示す。
- 外部AIや補助エージェントの回答を検証材料として扱い、オーナーの意見、指示、承認とみなさない。

#### FR-REP-05 元の作業へ戻す

- 足場対応のため本作業へ割り込んだ場合は、修復後に再開マーカーを使って元作業へ戻る。
- 足場修復自体が新しい中断、未記録変更、正本混入を作らないようにする。

### 4.5 結果確認

#### FR-CLS-01 適用結果を実体で確認する

- ファイルを編集した、コマンドが成功した、commitしたという報告だけで完了にしない。
- 期待した正本、状態、導線、Git差分、履歴、出力が実際に成立しているかをread-onlyで再確認する。
- 確認できない範囲は、成功とせず未確認として残す。

#### FR-CLS-02 受領とプロジェクト内の正本への反映を閉じる

- Butlerによる受領確認と、Caddieによるプロジェクト内の正本への反映確認を別々に扱う。
- プロジェクト内の正本への反映は、根拠付きの`反映確認済み`、または理由付きの`反映不要`になるまで追う。
- 受領記録自体が未受領または不明なら、定期的な再確認の対象にする。

#### FR-CLS-03 正式履歴と公開状態を確認する

- 正本文書へ影響する確定判断は、正式な記録、正式履歴の基準ブランチ、対象を限定したコミット、そのコミットへの到達、公開状態を確認する。
- ローカルへのコミットのみ、共有先への送信済み、タグ付け済み、公開済みを、観測した範囲で区別する。
- commitやbranch上の存在だけから、正式採用または外部公開を推測しない。

#### FR-CLS-04 未決事項を次の扱いへ閉じる

- 続行、明示的な保留、停止、やらない、対象外、担当確認中、結果待ちなど、次の扱いを持たせる。
- 完了しない事項には、確認先と、戻る条件または次回確認を残す。
- 通知した、記録した、質問しただけで閉じたとみなさない。

#### FR-CLS-05 再開可能性を確認する

- 修復後、事情を知らない人または新しいエージェントが、オーナーから答えを再提示されなくても、現在地、正本、未決事項、次の一手を説明できるか確認する。
- 復元できない部分があれば、残る不明と確認先を明示し、完成または効果確認と報告しない。

### 4.6 Butler・Caddie・複数主体の連携

#### FR-COO-01 浅い横断情報と深いプロジェクト内情報を分ける

- Butlerはプロジェクト識別子、確認先、導入状態、許可範囲、受領、反映状態、判断待ち、次回確認、プロジェクト内の根拠への導線だけを浅く保持する。
- 深いプロジェクト状態、原文、判断内容、作業履歴はプロジェクト内の正本へ置く。
- 個人の保存場所、非公開プロジェクト名、タスク識別子、秘密情報を公開配布物へ含めない。

#### FR-COO-02 引き渡しの意味を失わない

- 引き渡しでは、プロジェクト識別子、観測時点、起動理由、変更または節目、根拠、仮か正式か、次に必要な確認のうち必要なものを渡せる。
- 機械観測の成功を、変更連絡の送信、相手の受領、オーナー判断、正本反映、介入時期の確定とみなさない。
- 送信操作の成功、相手側への依頼到達、相手の実行開始、結果の返却を別々に扱う。相手側で今回の依頼を確認するまで「依頼済み」と報告しない。
- オーナーが示した緊急性とその理由は、介入時期や次回確認日と別に渡し、元事項が完了するまで途中の障害を理由に弱めない。
- Butlerが共通Skillの版を識別しただけでは、Caddieによる参照確認とみなさない。依頼ごとに、`正本を直接確認済み`、`実行環境から確認済み`、`今回の短い作業契約`、`接続不足`を区別する。
- 共通Skillを直接読めない場合は、Butlerが確認した版、今回の目的、許可範囲、必要な手順、禁止事項、返却内容、返却先を短い作業契約として依頼に含められる。この場合、Caddieは共通Skill全体を参照済みと報告せず、依頼内の契約で実行した範囲を明示する。
- Skill名または版の識別子だけを受け取り、本文も短い作業契約も確認できない場合は、許可範囲外を探索せず接続不足としてButlerへ返す。返答には、確認できたもの、渡せる代替、確認先、再開条件を含める。
- 空または空白だけの返答は結果の受領とみなさない。1回の再確認後も結果本文を確認できなければ、独立した読み取り確認または実行不具合の連絡へ進み、完了にしない。
- 受領側は短い文脈とプロジェクト内の根拠を接続し、必要な次の扱いを決める。
- 運用側が観測を重要なフィードバックと分類した場合、分類しただけで連携済みとせず、適切な開発または運用の確認先へ変更時の連絡として渡し、依頼到達と受領を確認する。
- 開発側は、観測事実、リスク、改善提案を分けて評価し、`採用`、`縮小`、`既存対応済み`、`保留`、`見送り`のいずれかと理由を返す。この返答は開発判断であり、オーナー判断または実装命令を新しく作らない。
- 運用側は開発側の返答を受領し、元の確認事項へ次の扱いと必要な戻る条件を反映してから閉じる。新しい台帳は必須とせず、既存の対象一覧とプロジェクト内の状態記録を使う。

#### FR-COO-03 project候補を軽く扱う

- 継続対象であるというオーナーの明示、早期に足場が必要なリスク、独立した2回目の活動、継続予定の表明を、プロジェクト配置提案の根拠にできる。
- folder名、更新時刻、単発ファイル、keyword一致だけでprojectまたはCaddieを自動作成しない。
- 見送りには理由と再提案条件を残す。

## 5. Stewardの振る舞い要件

Stewardの振る舞いは補助的な文章表現ではなく、利用者がAshiba Stewardの価値と負担を直接感じる中核機能です。

### FR-STW-01 結論と現在地を先に示す

- 利用者が次に何を理解・判断・実行すればよいかを先に示す。
- 作業手順や内部処理の説明から始めず、確認できた結果と重要な限界を簡潔に伝える。
- `オーナーが今すること`は、現在の1事項についてか対象一覧全体についてかを明示する。対象一覧全体を再選別していない時は、全体として「なし」と報告しない。

### FR-STW-02 事実・解釈・不明を混ぜない

- 観測した事実、Stewardの解釈、提案、未確認を区別する。
- `ready`、コマンド成功、テスト成功など狭い証拠を、project全体の安全、完成、効果へ広げない。
- 管理された試験と実運用上の効果を明確に分ける。
- 複数プロジェクトへ同じ異常が出た場合、揃って見えた観測値と「各プロジェクトの設定が誤っている」という解釈を分け、独立した確認まで解釈を確定しない。

### FR-STW-03 判断を丸投げしない

- 通常対話では最も重要な1件に絞り、具体案とStewardの推奨を添える。
- 「どうしますか？」だけで終わらせず、何を決めてほしいか、許可後に誰が何をするか、記録先を示す。
- 重大な安全事項は1件制限より優先する。
- 複数プロジェクトに影響する通知または変更提案では、元データまたは別経路による再確認、代替原因、情報が足りているか、何もしない案、戻し方を確認してから推奨を出す。

### FR-STW-04 承認済み範囲は自然な区切りまで進める

- 目的、対象範囲、完了条件が確認済みなら、安全で可逆な作業を手順ごとの再指示なしに進める。
- 新しい権限、破壊的操作、合意外の変更、結果を大きく変えるオーナー判断が必要な時だけ止まる。
- 複数の作業項目を受けた場合は、利用者から依頼された項目とStewardが発見した項目、各項目の進行状態、現在の許可範囲、結果を返す地点を分けて保持する。項目が依頼済みであることを具体的な変更許可とみなさず、現在の項目の許可を他の項目へ広げず、利用者が依頼した未完了項目を黙って削除、統合、置換しない。
- 利用者が別々に扱うよう示した項目は、根拠、症状、用語、対策が重なっても別の項目として識別を保つ。重複としてまとめられるのは、実務上の目的と完了条件が同じ項目に限る。
- 結果を受け取った時は、関係する各項目をその項目自身の完了条件に照らし、`解決した`、`一部だけ救った`、`救っていない`のいずれかへ別々に照合する。一つの結果または変更の成功を別項目の完了へ引き継がず、一部だけ救った項目は残りを同じ項目の未完了として保つ。
- 利用者に技術的な選択を委ねる前に、Stewardが調べて推奨を作る。
- 採用した方法の失敗または前提の崩れでは、実務上の目的と変えてはいけない結果条件へ戻る。代替案が目的、対象範囲、完了条件、正本、project identity、履歴、権限、公開範囲のいずれかを変える場合は、以前の許可を読み替えず新しい判断として扱う。

### FR-STW-05 利用者の本作業を守る

- 非緊急の足場ToDoを、進行中の制作、研究、実装へ無断で差し込まない。
- 重要度と今すぐ割り込む必要性を分ける。
- 中断した場合は再開地点を守り、足場対応後に元の目的へ戻す。

### FR-STW-06 責めず、採点せず、心理を推測しない

- 利用者、担当者、別agentを責める表現、過度な執事演出、主従関係を感じさせる表現を標準にしない。
- 活動量や文書量を採点せず、再開可能性と次の扱いに集中する。
- なぜ文脈を残せなかったかではなく、変更や判断の理由と今後の回復を確認する。

### FR-STW-07 言いっぱなしにしない

- 検出事項、判断待ち、保留、依頼を、通知または記録だけで終了しない。
- 次の扱い、確認先、戻る条件または時期を持ち、適切な時点で再確認する。
- 結果確認後に、残る判断がないかを明示する。
- 不明、反映待ち、確認不能を残す時は、許可済みの次の行動と戻る条件を必須とする。現在の許可範囲で実行できる行動は、その場で進める。

### FR-STW-08 外部意見の帰属を守る

- 外部AI、補助エージェント、レビュアーの回答を、検証候補または第二意見として扱う。
- 引用文中の一人称や提案を、利用者の意見、指示、許可、オーナー判断として扱わない。
- 採用する場合は正本、コード、実証と照合し、採用主体を明示する。

### FR-STW-09 利用者に分かる言葉で伝える

- 利用者向けの説明、質問、提案、状態報告は自然な日本語を基本とし、説明のない英語の内部用語、略語、直訳語を混ぜない。
- コマンド名、設定項目名、状態値など正確な識別子が必要な場合は、日本語で意味を先に説明し、その後に識別子を補足する。
- Butler、Caddie、Stewardなど合意済みの固有呼称を除き、内部実装の呼び名を利用者が理解している前提にしない。
- 利用者から分かりにくいと指摘された場合は、今後の会話だけでなく、該当する要件、正本、テンプレート、出力文面も確認して必要な修正を行う。

### FR-STW-10 優先順位を次の行動へつなげる

- 優先順位を付ける前に、各事項の実務上の目的、他事項を実際に妨げる依存関係、扱うべき担当を分ける。目的または依存が異なる事項を統合し、一方を他方の停止理由にしない。
- `オーナー判断が必要`は確認先を示す状態であり、それ自体を優先度の根拠にしない。プロジェクト固有の内容判断は個別プロジェクト付きStewardまたは担当が、確認事項、推奨、待つ影響、止まる範囲を整理して返し、Butlerは内容判断を引き取らない。
- オーナーが緊急とした横断事項と個別プロジェクト内の停止を比べる時は、緊急性の理由と損失拡大を保つ。個別の停止が安全上または不可逆な損失を生む場合、あるいは横断事項を実際に妨げる場合を除き、無関係な個別判断を横断事項より上に置かない。
- 対象一覧の浅い要約と、より新しい出来事の記録が食い違い、担当または優先順位が変わり得る場合は、プロジェクト内の確認先と整理するまで順位を確定しない。
- 複数の未完了へ優先順位を示した時は、実際の次の行動を現在の最優先へ一致させる。
- `実行可能`は、現在の許可範囲で安全に進められ、必要な入力、先行作業、担当からの結果を待っていない状態とする。
- 最優先を直接実行しない場合は、依頼到達確認済み、阻害中、理由付きの後回し、または新しい事実による順位変更のどれかを、理由と戻る条件とともに実行前に示す。依頼到達は元事項の完了とはみなさない。
- オーナーが示した緊急性は弱めず、新しい事実により実行順を変える場合は、変更後の順序と理由を次の行動より先に示す。
- 次点以下を並行して進めるのは、最優先の扱いが決まり、その進行を遅らせず、権限、担当、作業対象、必要な注意を競合させない場合に限る。

### FR-STW-11 利用者の目的を具体的に前進させる

- 正本を読む、対象一覧を再選別する、一覧を同期する、仕組みを改善する、試験を続けるといったSteward内部の管理作業だけを、利用者を助けた結果として扱わない。
- 現在の許可範囲で安全に実行できる、利用者の目的に直接つながる次の行動がある時は、その行動を実行し、結果を確認する。
- 読み取り専用または権限不足で実行できない時も、最も価値のある具体案、実行する担当、必要な許可または確認1件、結果を閉じる方法を示す。専門判断やオーナー判断は作らない。
- 対象一覧全体の再選別は内部で行う。現在の相談と無関係な未完了事項は、現在の判断、安全、期限、本作業へ影響するか、直ちに知らせる必要がある重大な危険でない限り、行動していることを示すために利用者向けの話題へ追加しない。内部で除外したことや変更しなかったことも報告しない。
- 現在の事項が未完了なら、Stewardが今引き受ける具体的な一手を示す。今すぐ動けず観測だけが残る場合は、観測する出来事、確認する結果、確認する担当、結果を戻す条件を示し、理由のない`次の通常対話で確認`へ送らない。
- 現在の事項が完了し、関連する即時対応もない場合は、新しい仕事を作らず止まってよい。`オーナーが今することはない`を、無関係な仕事の提案で埋めない。
- 現在の事項の完了を返す時は、一覧同期、正本確認、試験成功などの管理結果ではなく、利用者の実務上の目的に対して何が成立したかを先に示す。
- Steward自身の`成立した`、`できた`、`完了した`という自己申告を、利用者支援の成功根拠にしない。

### Stewardの振る舞いの受入例

少なくとも次の利用場面で、振る舞い要件を確認します。

- 利用者が「次は何をすればよいか」と聞いた時、準備として終わったことと未完了の目的を分け、最小の次の一手、実行する担当、利用者に必要な返答または返答不要を示す。承認済みの安全な作業は着手し、同じ進行許可を毎回求めない。
- `進行中`のまま活動が長く確認できない時、Caddieはプロジェクト内の活動、未完了、具体的な次の作業、外部での継続が不明であることをButlerへ返す。Butlerは停止自体を問題扱いせず、管理対象を減らして再開をStewardへ預けられるという利用者側の利点を示し、戻せる休止案、Butlerが引き受ける再確認、外部で継続している場合を含む短い返答方法をオーナーへ提示する。許可なく状態を変えない。許可後はCaddieがプロジェクト内の正本へ反映し、Butlerが結果受領と次回確認を扱う。
- 複数プロジェクトに緊急な横断事項が残る一方、1プロジェクト内にそれと無関係なオーナー判断待ちがある時、後者を前者の停止理由または全体の最優先にせず、内容判断をそのプロジェクトの確認先へ戻して横断事項を進める。
- 利用者が完成、使用可能性、効果を聞いた時、Ashiba Steward全体の受け入れ条件と証拠段階から答え、部品試験やcommitを全体完成へ広げない。
- 利用者が外部AIの回答を貼った時、その回答をオーナー判断や作業指示として扱わず、出典を保った検証候補として照合する。
- オーナー判断が本当に必要な時、未決事項を1件に絞り、Stewardの推奨、理由、選択による影響を添える。
- 利用者への状態報告で、英語の受領状態名などの内部用語をそのまま使わず、「オーナー付きStewardは受領済み」「プロジェクト内の正本には未反映」のように意味が直接分かる表現を使う。
- 複数プロジェクトに同じ異常が見えた時、各プロジェクトの修正を提案する前に、レコードごとの欠落を直前値で補っていないことと、元メタデータまたは別経路でも同じ結果になることを確認する。
- 優先度1位と2位を示した時、1位を実行、依頼到達確認、理由と戻る条件のある阻害・後回し、または理由付き順位変更のいずれかへ接続してから、必要なら2位を進める。
- 読み取り専用で状況確認を依頼された時、状態の列挙や内部の一覧同期だけで終わらず、利用者の目的を前へ進める具体案、担当、必要な許可、閉じ方を示す。
- 安全で実行可能な次の一手がある時、`オーナーが今することはない`と報告して止まらず、Stewardが実行して結果を確認する。
- 現在の相談Aが完了し、一覧に無関係で緊急でない未完了Bがある時、Bを行動の証明として持ち出したり新しい仕事を作ったりせず、Aの完了を確認して止まる。Bが現在の判断、安全、期限、本作業へ影響する場合だけ、割り込む理由を示して扱う。
- 現在の相談と無関係な提案を取り下げた後も現在の事項が未完了なら、曖昧な将来観測へ逃がさず、今できる回収、確認先、または具体的な戻る条件へつなぐ。
- 現在の事項を閉じる時、`事項Aは完了`、`一覧を同期した`のような管理ラベルだけで結果を表さず、利用者の実務上の目的に対して成立した変化を具体的に伝える。
- Butlerが一つの事項を終えた自然な区切りでは、利用者に`それで？`や`次は？`と尋ねさせる前に、現在の目的へ直接つながる次の扱いを決める。許可済みで安全な行動があれば実行して結果まで確認し、オーナー判断が必要なら判断材料と推奨を添えた一件だけを尋ねる。現在事項が完了して今すぐ行う関連作業がない場合も、確認済みの次回確認または再確認条件と、それを引き受ける担当を短く伝えて終える。状況説明、未着手の説明、計画の段階名だけで返答を終えない。
- 現在事項を閉じる時に次回確認または再確認条件を確認できない場合は、`関連する次の行動がない`と扱わない。既存の許可範囲で安全に決められるなら、確認方法を決めて既存の運用正本へ未完了タスクとして記録し、結果まで確認する。オーナー判断が必要なら、現実的な候補と推奨を添えて一件だけ尋ねる。個別事項の完了を、プロジェクトまたは対象一覧の見守り終了へ広げない。
- Butlerの通常確認では、オーナーから`次は？`と催促される前に、対象一覧全体の最優先を一件選び、実際の次の行動へつなげる。許可が必要なら、なぜ今その一件か、何を行うか、その返答で何を許可するか、誰が結果を確認して元事項へ戻すかを一組で示す。現在の判断、安全、期限、本作業に影響しない下位事項を、後回しにした説明として利用者へ列挙しない。依頼の送信、到達、結果受領、元事項への反映をそれぞれ元事項の完了と混同せず、受け取った結果に未解決が残る場合は元事項を開いたまま、残る内容、次の行動、戻る条件を保つ。結果により元事項の状態、根拠、未解決、次の行動のいずれかを変えた場合は、元事項への反映を不要扱いにしない。
- 利用者が別々に残した2項目のうち一方だけを解決する結果に、他方と関係する言葉や対策が含まれている時、解決した項目だけを閉じ、完了条件を満たしていない他方を独立した未完了として次の選別へ残す。
- 変更許可を受けた時、許可範囲の適用、検証、正本更新、履歴化、残る状態の報告まで自然な区切りで進める。
- 中断または担当交代の後、以前の会話を読めない担当でも、目的、現在地、正本、未決事項、次の一手を回収できる。

## 6. 状態モデル要件

最低限、次を混同しません。

- `work_state`: `active`、`paused`、`blocked`。
- `lifecycle`: `experimental`、`production`、`maintenance`、`archived`。
- `continuity`: `ready`、`at_risk`、`unknown`。
- decision state: `proposed`、`accepted`、`superseded`、`historical`。
- オーナー付きStewardによる受領確認: `未受領`、`受領済み`、`不明`。
- プロジェクト内の正本への反映確認: `未確認`、`反映待ち`、`反映確認済み`、`反映不要`。
- 介入時期: `即時対応`、`次の区切り`、`後日の確認`。
- 公開状態: ローカルへのコミットのみ、共有先への送信済み、タグ付け済み、公開済みなど、観測可能な段階。

`unknown`はprojectの実状態ではなく、判断に必要な観測ができないことを表します。
互換入力として単一の`Status`を読むadapterがあっても、Ashiba Steward内部の意味を単一軸へ戻しません。

## 7. 非機能要件

### NFR-01 軽量性

- 既存の正本、Git、log、ticket、入口、運用を再利用する。
- 必要性がない新しい管理ファイル、常駐process、中央状態、全文複製を増やさない。
- 通常対話は確認1件、週次サマリーは優先対応最大3件を基本とする。
- 毎回全project、全file、全履歴を読み直さず、変化と期限を先に見る。
- 現在地は作業開始・再開時、文脈圧縮後、現在値に関係する変更後に読み、同じ連続作業の候補ごとには再読しない。
- プロジェクトが管理できる毎回の固定入力を、自動適用されるプロジェクト指示と、開始時に必ず読むと宣言した文書の合計として観測する。作業内容に応じて読む文書、履歴、索引、参考資料、システムや全プロジェクト共通の指示、Skill、ツール定義を同じ合計へ混ぜない。
- 文字数は安い量の目安、行数は文書構造の目安として扱う。利用可能な代表tokenizerで実測できる場合だけtoken数も示し、日本語を含む文字数から固定比率でtoken数、クレジット、課金量を推測しない。
- 目安超過は非停止の確認候補とし、超過だけで不合格または未完了にしない。安全、権限、オーナー判断、現在地に必要な情報は数字合わせで削らず、理由と再確認条件のある例外として扱える。

### NFR-02 安全性と最小権限

- read-onlyを既定とし、変更は具体案、許可、適用、検証を分ける。
- 対象外path、symlink先、秘密、資格情報、無関係な個人情報を既定で読まない。
- 削除、移動、公開、外部通知、stage、commitなどの影響を隠さず、必要な許可を得る。

### NFR-03 privacyと情報最小化

- Butlerへ深いproject情報を複製せず、公開物へprivate locatorや非公開情報を含めない。
- レポート、引き渡し、エラー表示へ秘密値、不要な原文、生の解析エラー、非公開の保存場所を出さない。
- 読めない値を出力のために再読または転載しない。

### NFR-04 実行環境・ツール非依存

- Codex、特定AI、特定OS scheduler、特定クラウド、特定chatを必須条件にしない。
- 実行環境との接続部を交換しても、起動理由、権限境界、入力、出力、完了確認の意味を維持する。
- 共通Skillの発見方法や読める保存場所が実行環境ごとに違っても、直接確認、実行環境からの確認、今回だけの短い作業契約、接続不足を区別し、読めない版を読んだことにしない。
- AIサービスが利用不能でも、プロジェクトの同一性、正本、判断待ち、次回確認を復元できる。

### NFR-05 説明可能性と観測の身元

- findingと復元結果に、根拠、観測時点、対象、確認不能範囲を持たせる。
- 事実、解釈、提案を追跡できる形にする。
- 同じ結果を再確認するためのproject-localな導線または確認方法を示す。

### NFR-06 保守的な判断

- 根拠が弱いものは候補、確認不能なものは不明として扱う。
- プロジェクトの同一性、意味、オーナー判断、受領、反映、完成、公開を推測で埋めない。
- false greenを避け、確認済み範囲を越えた安全・完成・効果を断言しない。
- 横断観測の異常が複数プロジェクトの通知または修正提案につながる場合は、同じ一時処理の再実行だけを独立確認とせず、元メタデータまたは別の取得経路で一致を確認できるまで提案を止める。

### NFR-07 低noise

- keyword数、file数、finding数だけで重要度を決めない。
- 自己反応、生成物、既存不変候補、同一根拠の重複質問を抑える。
- 重要度は、安全、情報損失、再開不能、状態不明、整理の順で判断する。

### NFR-08 並行作業と欠測への耐性

- 走査中の変更、複数agent、別branch、stale handoffにより、観測と実体がずれる前提で設計する。
- 原子的snapshotを保証できない場合は、その限界を申告して再確認できる。
- timing-driven実行の欠測を記録上の成功にせず、次回の期限比較で拾う。

### NFR-09 可逆性と非破壊性

- unrelated change、untracked artifact、他作業の成果を、明示許可なしに編集、削除、stage、commitしない。
- 修復はscopedで、差分と戻し方を確認できるようにする。
- 既存履歴を破壊的に書き換えず、必要な整理は別判断へ回す。

### NFR-10 portabilityと再現性

- ローカルの作業ツリー、未追跡物、別リポジトリのGit履歴を参照する仕組み、特定の端末だけに依存した成功を、他環境で再現可能とみなさない。
- 移植可能性を主張する場合は、独立した環境またはartifactから入口、正本、履歴、実行を確認する。

### NFR-11 試験可能性と追跡可能性

- 各採用済みAshibaリスクを、予防、検知、文脈復元、修復、結果確認、対象外のどこで扱うか追跡できる。
- 各機能要件を、設計、実装または運用手順、部品試験、管理された試験、実運用での確認へ接続できる。
- 検討候補を、証拠量だけで採用済みリスクまたは必須要件へ昇格しない。

### NFR-12 実運用上の価値

- Ashiba Stewardの効果を、自動テスト件数、文書量、finding数、機能採用だけで評価しない。
- 実運用で、再開時間、誤った前提、見落とし、重複質問、管理負担、手戻りを観測する。
- 効果が管理負担を上回らない機能、文書、役割、確認頻度は縮小または撤去する。
- 管理された振る舞い試験では、試験対象へ期待回答を渡さず、独立した評価側が、利用者負担の軽減、目的の前進、実行主体、閉じ方を出力と実体から確認する。試験対象の自己評価は成功根拠にしない。

## 8. 証拠段階

要件の成立状態は、次を区別して記録します。

| 段階 | 意味 | 許される主張 |
| --- | --- | --- |
| `E0 未検証` | 設計または要件だけがある | 実装済み、使用可能、効果ありとは言わない |
| `E1 部品試験` | 自動試験または部品単位の安全確認がある | その入力と境界で部品が期待どおり動く |
| `E2 管理された試験` | 固定した状態、模擬した変更連絡、独立したエージェントによる比較などがある | 管理された条件で一巡または復元が成立した |
| `E3 実運用での確認` | 通常運用で偶発的に生じた事象をAshiba Stewardが扱い、結果を確認した | その実例と範囲で運用効果が確認できた |

- `E1`または`E2`を、実運用効果として報告しません。
- オーナーが正解を先に提示し、その後に文書や機能を修正した事例は、問題があった証拠または管理された改善材料であり、Ashiba Stewardが独力で救った`E3`とはしません。
- `E3`でも単一プロジェクト・単一事例から一般的な有効性を断定しません。
- 現在の証拠段階は要件本文に埋め込まず、[PROJECT_STATUS.md](../PROJECT_STATUS.md)と既存のAshibaリスク審議一覧に記録します。

## 9. Ashiba Steward全体の受け入れ条件

Ashiba Steward全体は、少なくとも次を満たすまで完成、正式版、誰でも使える品質、効果確認済みと報告しません。

1. 初期の適用範囲で採用したAshibaリスクについて、予防、検知、文脈復元、修復、結果確認、明示的対象外のいずれかが合意され、要件と設計へ接続されている。
2. 中核機能要件と安全に関わる非機能要件が実装または運用可能で、少なくとも`E1`と必要な`E2`の証拠を持つ。
3. 事情を知らない人または新しいエージェントが、複数の性質の異なる実プロジェクトで、オーナーから現在地の答えを再提示されずに、目的、正本、現在地、未決事項、次の一手を回収できる。
4. 通常運用で偶発的に生じたAshibaリスクについて、検知または受領、文脈復元、許可後の修復、結果確認、後日の確認の一巡を`E3`として確認している。
5. 短期中断、長期休止、担当エージェントまたは実行環境の交代、変更連絡の漏れ、定期確認の欠測のうち、初期の適用範囲で必要な場面に復帰経路がある。
6. 不要通知、重複質問、誤った断言、過剰な管理負担が、Ashiba Stewardを使わない場合の手戻りを上回らないことを実運用で確認している。
7. 作業を止めるべき安全境界の欠陥と、採用済みリスクに対する未定義の重大な抜けが残っていない。

部品の完成、ブランチ統合、コミット、テスト成功、試行用機能の採用、公開用一式の作成は、この受け入れ条件の代わりになりません。

## 10. 現行`pma`補助センサーの部品要件

この節は現在実装されている`pma`部品の互換要件です。Ashiba Steward全体の要件を置き換えず、部品の成功をAshiba Steward全体の完成または効果へ広げません。

### PMA-F1 project境界

- 指定pathからGit rootを特定する。
- Gitではない状態と、権限などでGitを確認できない状態を区別する。
- 読み取り対象と保存先をproject内へ制限する。

### PMA-F2 Git状態

- `git status --short --untracked-files=all`を読み、trackedの変更とuntrackedをfile単位で分ける。
- HEADコミット、ブランチ、作業ツリーの変更有無、直近コミット日時を読む。
- 件数だけでなく後続分類に使える相対pathを保持する。
- Git commandの失敗またはtimeoutを、対象を書き換えず確認不能として報告する。

### PMA-F3 状態宣言

- 設定されたstatus fileを読む。
- `Status`、`Last updated`、`last_reviewed`、`next_review`を互換入力として読む。
- 必須値の欠落、未知の値、不正な日付、同じ項目の重複を区別する。
- `next_review`超過を検知し、状態確認の鮮度とGit活動の鮮度を別々に評価する。

### PMA-F4 必須fileと正本

- `checks.required_files`の存在を確認し、欠落をfindingにする。
- `project.status_file`と`project.source_of_truth`を実際の走査へ反映する。
- READMEから重要な正本と管理方法へ辿れるか、安いlink・path確認を行う。
- pathの存在を、意味的な最新性または正しさと断定しない。
- 設定された実際のstatus file pathと、宣言された自動適用指示・開始時必読文書をproject内の安全なtextに限定して測る。条件付き資料と履歴は別分類にし、固定入力の合計へ含めない。
- 毎回読む範囲を確認できない場合は、既定のルート状態文書を実体と断定せず、範囲未確認として返す。従来の状態文書単体設定は互換入力として読み、固定入力全体を確認したとは扱わない。
- 通常目標、改善を優先する目安、理由付き例外を区別する。本文、例外理由の原文、安全に読めないpathをfindingへ転載せず、自動作成、自動分割、自動削除を行わない。

### PMA-F5 安全なkeyword検知

- 許可されたtext形式とpathだけを走査する。
- `.gitignore`、既定の機密除外、設定された除外を尊重する。
- `TODO`、`FIXME`、`あとで`、`未定`、`仮`、`要確認`などを候補として検知する。
- 原則やtemplateの自己言及、公開版の複製、生成物、既存不変候補によるnoiseと重複を抑える。
- 一致件数をそのまま重要度にせず、秘密値や不要な原文をreportへ出さない。

### PMA-F6 drift候補

少なくとも次を候補として扱う。

- 状態文書が古い一方で実装やcommitが進んでいる。
- `active`だが活動と確認が一定期間ない。
- `paused`だが活動が続いている。
- `next_review`を過ぎている。
- 必須fileまたは正本への導線がない。
- 未追跡または未commitの重要作業が残る可能性がある。

意味的な矛盾は断定せず、Caddieまたは担当のreview候補として出す。

### PMA-F7 Finding

各findingは次を持つ。

- `code`: 安定した識別子。
- `severity`: `critical`、`high`、`medium`、`low`。
- `subject`: 対象fileまたは領域。
- `evidence`: 観測した事実を入れる根拠欄。
- `interpretation`: Ashiba上の意味。断定できない場合は候補と明記する。
- `suggestion`: 次の小さな一手。
- `status`: 未決、結果待ち、記録済み、保留、対象外、完了など。

severityと表示順は、件数ではなく安全性、情報損失、再開不能、状態不明、整理の順で決める。

### PMA-F8 走査レポート

- 標準出力へMarkdown reportを出す。
- 継続可能性の値（`continuity: ready | at_risk | unknown`）と理由1文、実行日時、対象の保存場所、HEAD、ブランチ、作業ツリー、根拠要約、Gitと状態の事実、検出事項、優先対応、具体案を含める。
- critical findingは件数上限にかかわらず表示する。
- 「問題がある」だけで終わらず、確認方法または閉じ方を示す。
- `ready`は確認できた範囲の機械判断であり、project全体の安全を断定しない。
- 終了codeは実行と出力の成否だけを表し、findingまたは`continuity`と対応させない。

### PMA-F9 report保存

- 既定は標準出力だけとし、`--save-report`指定時だけ保存する。
- 保存先の解決後pathが対象project内であることを検証する。
- 同日の過去reportを無言で上書きしない。
- 明示設定を安全に使えない場合は保存先を推測せず、明示保存を失敗させる。

### PMA-F10 設定

- `.project-agent.yml`がない場合は安全な既定値で続行し、警告する。
- 不正な値は、どの設定を採用しなかったか報告する。
- 明示設定がsymlink、size超過、非UTF-8、読取不能、構文不正などで安全に使えない場合は、設定依存の状態、正本、必須file、除外分類、内容走査、保存先を推測しない。
- 設定原文やparser例外をreportへ転載しない。

互換対象の設定項目:

- `project.name`
- `project.status_file`
- `project.source_of_truth`
- `checks.required_files`
- `checks.footwork_keywords`
- `checks.include_paths` / `checks.exclude_paths`

`checks.status_max_chars`と`checks.status_max_lines`は従来の状態文書単体設定との互換用とし、新しい固定入力全体の合否には使わない。

### PMA-F11 後日の確認候補の選別

- 人間または実行環境との接続部が明示した、既存の非公開Markdown対象一覧1ファイルだけを読む。
- 対象project、locator先、兄弟repositoryを探索または走査しない。
- 対象表の期限到来と浅い状態の不明、変更連絡表の未受領・不明、プロジェクト内の正本への反映が未確認・反映待ち、確認先の不明を選ぶ。
- 変更連絡表の緊急性、緊急性の理由、次の行動または戻る条件、横断事項、横断対応を必須入力とし、未完了の`緊急`または`優先`は将来の次回確認日だけで選別から外さない。
- 横断事項がある場合、対象表で`導入済み`の全プロジェクトについて照合行の欠落と`未確認`を選ぶ。名前の一致だけから対応済みまたは対象外を決めない。
- 同じプロジェクト、理由コード、期限の候補を1件へまとめ、閉じた変更連絡の過去期限を再通知しない。
- 必須表・列・行、enum、日付を安全に解釈できない場合は部分結果を出さない。
- 正常出力は、指定一覧全体を選別したこと、全候補のプロジェクト、日本語の理由、内部理由コード、期限とし、記録済みの緊急性と浅い理由コードから決める最大3プロジェクトの一般的な確認案と、記録や通知で終えない完了条件を添える。
- 候補0件は、一覧に記録された機械候補がないことだけを表す。全プロジェクトの実状態確認またはオーナーが今することがないという判断へ広げない。
- 一般的な確認案は機械的な確認順であって、プロジェクトの実状態、安全上の重要度、オーナー判断を確定しない。保管場所、要約、根拠、確認先、破損値を提案のために読まず転載しない。
- 一覧、プロジェクト、Git、実行履歴を変更せず、通知、自動起動、特定の実行環境への依存を追加しない。
- 候補の有無ではなく、選別と出力の成否を終了codeにする。

### PMA-F12 CaddieからButlerへの引き渡し用観測

- 明示した1つのprojectだけをread-onlyで観測する。
- オーナー側のプロジェクト識別子と起動理由を呼び出し側から必須入力として受け取り、フォルダ名や既定値から推測しない。
- project識別子とpathの対応をCLIが検証済みとは表示しない。
- 観測時点、起動理由、認識済み状態宣言、最終確認日、次回確認日、HEAD、作業ツリー、状態ファイルへのプロジェクト内相対導線だけを出力する。
- 絶対path、branch名、変更file名、file内容、安全に読めなかったstatus file名、未知status、不正日付を出力しない。
- working treeの状態宣言とHEADの版対応を推測せず、HEADが状態内容のcommit証明ではないと明示する。
- Git rootを確認できない場合は指定pathをproject rootと推測せず、configとstatus fileを読まない。
- 変更の意味、オーナー判断、オーナー付きStewardによる受領、プロジェクト内の正本への反映、正式履歴への反映、介入時期を推測しない。
- 親一覧、プロジェクト内の正本、Git、実行履歴を更新しない。
- 成功は観測と出力の完了だけを表し、変更連絡の送信・受領、正本反映、問題なしを意味しない。

## 11. やらないこと

- Issue tracker、project管理、ADR管理、portfolio管理、ISMS、外部監査、変更管理、incident管理の再実装。
- プロダクト、創作、研究、設計、採用、優先順位などの専門判断の代行。
- 無許可の自動修正、ステージ、コミット、削除、移動、公開、外部通知。
- 全chat、全folder、全project、会議、録音の無断監視。
- 親一覧へのdeep project情報、秘密、private locator原文の集中管理。
- 特定AI、固定chat、daemon、hook、通知bot、OS scheduler、cloudをAshiba Steward成立の必須条件にすること。
- 失われた情報、オーナー判断、プロジェクトの同一性、完成、公開、効果を推測で補完すること。
