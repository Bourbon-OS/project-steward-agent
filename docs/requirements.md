# 要件

**公開状態:** v0.2（docs-only）

この文書は、[コンセプト](concept.md)で示した Project Steward Agent（PSA）に、何を期待し、何を任せないかを定めます。

v0.2 は考え方と設計を共有する文書版です。実行可能なエージェントやコードは含みません。また、ここでは PSA が最終的に満たすべき要件と、最初の MVP で検証する範囲を分けて扱います。

最初の MVP が読み取りと報告から始まっても、PSA の役割をそこで終わらせません。人間の指示と許可を受けた後に、必要な記録や修復を実際に行うことまでが、PSA の目標です。

## 対象とする範囲

PSA は、時間がたち、人が変わった後にも、プロジェクトやサービスの文脈と現在地をたどり直し、安全に次を選べる状態を整えます。

対象は、止まったプロジェクトだけではありません。進行中、安定稼働中、保守中、休止中、引き継ぎ中、再開を検討しているものを含みます。規模によって対象外にはせず、小さいものには小さい Ashiba を用います。

プロジェクト数が増えたとき、人間が各プロジェクトの PSA へ個別に確認し続けることを前提にはしません。将来は、複数プロジェクトの状況を浅くまとめる一つの相談窓口から、詳しく見る必要のあるプロジェクトの PSA へつなげられることを想定します。この窓口は、各 PSA や人間の判断を奪わず、全体の状況整理と取り次ぎを担います。

PSA が支援する「次」には、少なくとも次を含みます。

- 続ける
- 引き継ぐ
- 更新する
- 改善する
- 修復する
- 止める
- 再開する

これらの状態や遷移の厳密な定義は、v0.2 では確定しません。PSA は、状態を勝手に決めるのではなく、確認できる現在地と不足している判断材料を整えます。

## R1. 変更時に文脈を受け取る

通常の変更では、変更した人やエージェントから、必要な文脈を event-driven で受け取れることを要件とします。

受け取る内容は、決まった様式を埋めること自体を目的にしません。後から安全に扱うために必要な範囲で、たとえば次のような情報を扱います。

- 何を、なぜ変えたか
- 仮の対応か、正式な変更か
- 影響するものや依存するもの
- 未決のこと
- 次に確認すべき場所や条件

既存の Git、Issue、Pull Request、チケット、ログ、チャット、会議記録などに十分な情報があれば、同じ内容を別の文書へ書き直すことを求めません。PSA は短い連絡を、既に残る痕跡へつなぐ起点として使います。

障害対応などの緊急時は、必要な対処を優先します。その場で文脈を受け取れなかった場合は、落ち着いた後、timing-driven の見回りによって、記憶と痕跡が新しいうちに回収を試みます。

## R2. 軽く見回り、漏れとズレを拾う

PSA は timing-driven で軽く見回り、少なくとも次の兆候を拾えることを要件とします。

- 変更の痕跡はあるが、必要な文脈が渡されていない
- 宣言された状態や意図と、Git、チケット、ログなどの実態がずれている
- 仮の対応、保留、依存関係、再開条件などが失われそうになっている
- 正本や次に見る場所へたどる導線が古い、または切れている

見回りは、常時監視や全情報の再文書化を意味しません。運用としては継続し、実行は間欠的に行います。頻度は、変更の重さ、忘れやすさ、プロジェクトの状況に応じて調整できる必要があります。

PSA は、先に許可された範囲の痕跡を調べます。人へ確認するのは、将来の安全な判断に影響する曖昧さが残る場合に限り、分かっていることと記録案を添えて、短く具体的に行います。

見回りは、規則への適合や人の責任を判定する監査ではありません。漏れを責めるのではなく、将来困る可能性のある穴を見つけ、修復へつなげます。

PSAが確認するのは、変更や判断の理由であり、文脈を残せなかった理由ではありません。必要な文脈を回収し、次を安全に選べる状態へ戻すことを優先します。

## R3. 散在する痕跡から Ashiba を組む

PSA は、許可された範囲にある既存の痕跡と文脈を横断し、必要なときに Ashiba を組めることを要件とします。

情報源には、プロジェクトに応じて次のようなものを含みます。

- Git の履歴と差分
- Issue、Pull Request、チケット
- 既存の設計文書、決定記録、Runbook
- ログや監視記録
- 許可されたチャット、メール、会議記録
- 現在の状態、担当、依存関係、未決事項を示す既存の情報

PSA は、記録されていない理由を作りません。集めた情報を、確認できた事実、そこからの推測、まだ分からないことに分けます。痕跡だけでは復元できない場合も、「ここまでは確認でき、ここからは不明」と分かる状態を作ります。

誰に聞けるか分からない古いプロジェクトや、文脈が既に失われたプロジェクトも対象です。復元には限界があることを明示したうえで、残された痕跡から最善の Ashiba を組みます。

## R4. 人間の判断を残し、許可後は実行する

次のものは人間に残します。

- 何を目指すかという判断
- 続行、変更、休止、停止、再開などの重要な選択
- 許可
- リスクの受け入れ
- プロジェクト固有の価値判断や専門判断

PSA は、判断に必要な事実、推測、不明点、影響、具体的な選択肢や推奨案を整えます。「どうしますか」と判断材料のない質問を返すだけにはしません。

人間の指示と許可を受けた後は、許可された範囲で少なくとも次の処理を行えることを要件とします。

- 必要な文脈を、既存の適切な場所へ反映する
- 古くなった状態や未決の表示を更新する
- 正本、根拠、次に見る場所への導線を修復する
- 対応結果を確認し、何を行ったかを報告する

PSA は、問題を見つけて通知するだけで終わりません。判断待ちや保留になった事項は、記録しただけで終えず、確認先と、再び確認する条件または時期を残し、その時点でフォローします。結果が返ったら、必要な記録や状態へ反映します。

解決、継続、明示的な保留、停止、やらない、対象外など、人間が次の扱いを決めるまで追います。フォローの間隔は、重要度、期限、依存関係、状況の変化に応じて調整し、同じ確認を機械的に繰り返しません。

重要な変更、破壊的な変更、外部への通知や公開は、個別に明確な許可を必要とします。許可がない場合は、観測、整理、提案までにとどめます。

## R5. 既存の方法を生かし、記録を増やしすぎない

PSA は、Git、決定記録、Runbook、Issue 管理、プロジェクト管理、変更管理、インシデント対応などを置き換えません。既存の方法で十分に解けている問題は、その方法に任せます。

特定のファイル名、様式、管理方法を、すべてのプロジェクトへ一律に要求しません。プロジェクトが正本としている場所を尊重し、必要ならそこへの導線を直します。

新しい記録が必要な場合も、将来の安全な判断に必要な分だけを薄く残します。維持する負担に見合わない記録や見回りは、縮小または撤去できる必要があります。

## R6. 判断しやすく、行動へつながる形で示す

PSA の報告や相談は、少なくとも次を区別して示します。

- 確認できた事実と、その根拠
- 事実からの推測
- まだ分からないこと
- なぜ今扱う必要があるか
- 推奨する次の一手
- 人間に判断または許可してほしいこと
- 許可後に実行したことと、その確認結果

すべての観測を同じ重さで並べず、安全な次の選択に影響するものを優先します。人間へ管理作業の一覧を投げ返さず、通常の相談は小さく具体的にします。

活動の途絶や短い返答だけから、人の心理状態やプロジェクトの実際の状況を断定しません。活動や活動量の変化は、状態を確認するための兆候・手がかりとして扱います。

言葉は、短く、説明可能で、責めないものにします。ただし、相談しやすさを迎合と混同せず、必要な指摘とリスクは根拠とともに示します。

## R7. 安全な範囲で扱う

PSA は、与えられた権限とプロジェクト境界を守ります。

- 必要な情報だけを読む
- 機密情報や秘密値を既定で探索、表示、記録しない
- 許可なく対象外のプロジェクトや個人情報へ範囲を広げない
- 外部サービスの情報は、接続と利用が明示的に許可された場合だけ扱う
- チャット、メール、会議記録など他の人が関わる情報は、許可された範囲と適用される組織・プロジェクトのルールに従い、必要な部分だけを扱う
- 既存の変更を勝手に破棄または上書きしない
- 実行する変更は、範囲と理由を示し、確認可能にする
- 可能な場合は、取り消しや修正ができる方法を選ぶ

安全性を理由に仕事をすべて人間へ戻すのではなく、PSA ができる観測、整理、具体案の作成、許可された処理は自ら行います。

## 最初の MVP で検証する範囲

概念上の対象範囲と、最初に実装する範囲は分けます。

最初の MVP は、1つのローカル Git プロジェクトを対象に、明示的な起動から始めます。ホストサービス、常駐処理、ファイル監視、Git hook、OS のスケジューラを前提にしません。manual、event-driven、timing-driven は、PSA をいつ動かすかを表す三つの入口です。event-driven と timing-driven も、PSA 独自の常駐処理を作ることを意味しません。

段階的な検証では、まず安全な読み取り、根拠の収集、事実・推測・不明点の分離、短い報告、具体的な修復案を確認します。その後、人間の指示と許可を受けて、記録、状態、導線を実際に修復し、結果を確認するところまで広げます。

許可後の修復と結果の確認までを検証して、最初の MVP の完了とします。

最初の MVP の検証順序と運用上の入口は、[MVP計画](mvp_plan.md)で定めます。コマンド、設定、ファイル形式、検出規則、内部構成などの具体的な実装設計は、v0.2 では固定しません。この要件文書では、特定の実装方法を普遍的な PSA の定義にはしません。

## 受け入れ場面

PSA の有効性は、文書数や検出件数ではなく、実際の場面で確かめます。少なくとも、次の場面を扱えることを目指します。

1. **通常の変更:** 短い連絡を既存の痕跡へつなぎ、必要な文脈を過不足なく残せる。
2. **緊急対応後:** 対応を妨げず、落ち着いた後に漏れを拾い、記憶と痕跡が新しいうちに必要な文脈を回収できる。
3. **静かなズレ:** 宣言された状態や意図と、Git やチケットなどの実態のズレを根拠付きで示せる。
4. **長期稼働または休止:** Active であることや停止していることだけで健全性を決めず、次を安全に選ぶための情報を整えられる。
5. **担当者がいない古い仕事:** 残された痕跡から可能な範囲を復元し、分からないことを分かったふりで埋めない。
6. **許可後の処理:** 人間の判断後、許可された記録や導線の修復を実行し、結果まで確認できる。
7. **小さなプロジェクト:** 専用文書や重い運用を増やさず、必要な大きさの Ashiba を保てる。
8. **判断待ちのフォロー:** 判断待ちと記録して終わらず、適切な時点で再確認し、人間が続行、保留、停止、やらないなどの扱いを決め、結果を反映するまで追える。

## この文書で決めないこと

次の事項は、v0.2 の要件として固定しません。

- 状態名と状態遷移の完全な体系
- 見回りの一律の間隔
- 必須の専用ファイルやテンプレート
- 特定のコマンド名、設定形式、モジュール構成
- チャット、メール、会議、Git ホスティングサービスとの具体的な連携方法
- プロジェクト成果物や稼働中サービスを自動変更する仕組み
- 複数プロジェクトを横断する相談窓口の具体的な実装

PSA は、監査、プロジェクト管理、Issue 管理、インシデント対応、意思決定者の代替にはなりません。また、痕跡のない理由を推測で正解に変えられるとは主張しません。
